# 法律事项动态 Intake

## 目标

把「律师发来需求和文件 → 操作员交给模型 → 模型问清楚 → 律师补充 → 继续执行」做成可恢复的流程。两条原则：

- **先读材料再问。** 材料、会话和配置里已有的信息不问；问题是候选清单，不是固定问卷。
- **问与停分开。** 会改变成果的问题在起草前就问；只有必须确认项才停下来等答复。

操作员忘记如何发起、恢复或分派任务时，读取 [references/operator-quickstart.md](references/operator-quickstart.md)，其中有可直接复制的提示词。

## 为什么这样设计

v1.3.0 及以前，提问与暂停是一回事：只有「阻断项」才问，其余缺口一律写成条件句、列进《成稿说明》。结果是 2026-10-14 至 11-01 在 Claude Code 中执行的 11 项法律任务没有一次提问，`INTAKE_DECISION` 也从未出现在回复里，判断只在思考中完成；案例库 LWC-2026-0002、0005、0007、0009 的记录也写了漏输出。其中几处开场一句话就能问清的事，变成了返工或交付后的待确认项：律师给的租金基数有两种读法（0008）；律师已有自改稿，开工一小时后换了底稿（0009）；整份仲裁方案取决于原仲裁是否已出裁决；律师与操作员各给了一份模板。

## 执行时机

1. 先做只读的材料清点：目录、文件类型、律师指令、关键文件。资料包很大时不必读完全部细节，但要读到能判断每个候选问题在材料里有没有答案。
2. 在第一次实质检索、派出检索子代理或开始起草之前，完成第一步至第三步，在回复中输出 `INTAKE_DECISION`，再按第四步提问。
3. 律师中途发来自改稿、新材料或新指令，改变了底稿或任务时，重新执行一次。

下列情形仍输出区块，但不提问（`ask_mode: none`）：

- 纯格式转换、拆分、提取或机械校对，没有法律判断；
- 材料、会话与实践配置已覆盖第二步的全部问题来源；
- 操作员明确说「不用问」「直接写」，或律师授权「按你的判断处理」。问题照列，答不了的写进 `deferred_items` 与《成稿说明》。

## 第一步：重建已知事项

读取用户消息、全部指定文件、会话既有答复和适用实践配置，形成四组状态：

1. `known`：律师明确提供的事实和偏好；
2. `derived`：可从文件、文件名、上下文或配置可靠推出的信息；
3. `material_missing`：不同答案会改变法律路径、立场、修订力度、请求权、风险分配、数字或交付物；
4. `optional_missing`：只影响细节，可以使用配置默认值或保守默认值。

`derived` 不得再次询问。推断置信度不足的，改列 `material_missing`。

**数字对账。** 律师指令里的金额、单价、面积、期限、日期，逐一与原合同、原件或计算结果核对。对不上的，写出全部合理读法并量化差额，作为第二步的候选问题（LWC-2026-0008：「10 月份的租金标准」有两种读法，差额约 10 万元，起草者只记了「不一致」，另一读法由复核者发现）。

## 第二步：列出候选问题

按下列来源逐项找问题。每找到一个，先在材料里检索答案，有答案的不问。各来源的典型问题见 [references/question-routing.md](references/question-routing.md) 第 0 节。

1. **指令**：有两种以上合理读法；数字对不上；两个模板或格式指令冲突；「参考」「不要参考」的范围不清；
2. **底稿与版本**：律师是否已有自己的稿或修改稿，哪一份是基准，上一轮成果律师改过没有；
3. **只有律师或客户知道的状态**：程序进展（是否已裁决、撤回、反诉，举证期限）、对方当前的履约状态（是否已逾期、欠费多少、押金是否足额）、谈判进展、政府或对方的口头意见、内部决策与审批、关键文件是否存在；
4. **整份成果所依赖的前提**：方案或结论建立在一个尚未确认的事实上；
5. **客户目标与取舍**：偏好方案、可接受的风险、措辞语气、已锁定的条件；
6. **受众与交付**：直接发客户还是内部审阅，出具日期与落款，截止时间；
7. **材料缺口**：缺了会改变正文的文件。

每个问题归入一档：

| 档 | 判定 | 未答复时 |
|---|---|---|
| 必须确认 | 答错会让成果方向错误或不能用：我方身份、文书类型、适用程序；拟提交法院、仲裁机构、监管机关或供第三方依赖的文书的核心事实；硬时限；整份成果依赖的前提；差额重大且材料无法判定的读法 | 受影响部分暂停起草 |
| 建议确认 | 答案会改变具体章节、结论、数字或措辞，而且需要律师或客户取舍（我方让步、客户偏好、商业判断），或者只有他们知道；不问就只能写成条件句、两套方案或《成稿说明》待确认项 | 按推荐答案起草；没有推荐答案的（如只有客户知道的事实），正文用条件句或来源句。答复到达后修订 |
| 可按默认 | 有安全默认值：只影响细节，或者是对我方有利、律师几乎必然同意的起草选择（如明示排除对我方不利的原合同条款） | 采用默认值，在区块与《成稿说明》中写明 |
| 材料请求 | 提供后会改变正文的文件；先把资料包与材料中引用的文件对账，只请求缺失且影响正文的，通常不超过 5 项 | 正文用来源句、条件句处理 |

**《成稿说明》测试**：如果不问，这一项会不会写进《成稿说明》的「发送前请确认」，等律师或客户决定后再改正文？会，就至少是「建议确认」，应在起草前问，不要等交付时才问。对我方有利、答案可以预见的起草选择不算，按可默认处理，在《成稿说明》中说明即可。

两条边界：

- 材料里有相反说法（双方各执一词、同一份材料前后口径不一），而结论取决于哪个为真的，不算「材料已有答案」：律师或客户能确认的，列为建议确认；不能的，在分析中列明两种说法与证据；
- 能从指令或材料可靠推出的事项（落款、口吻、交付形式），不作为题目，写进问卷的「我们对材料的理解」，律师有异议时再改。

每个问题标明谁能回答：操作员、律师或客户。

## 第三步：决定是否暂停

```text
有必须确认项            → intake_status: clarify   提问；受影响部分暂停起草
无必须、有建议确认项    → intake_status: ask       起草前提问；等答复，或按推荐答案先写
只有可默认项或没有问题  → intake_status: ready     直接继续，写明采用的默认值
```

- `clarify` 期间可以继续不依赖答案的准备工作，例如材料提取、OCR、法条与原文核对；不得生成结论性文书，也不得声称文书已完成。必须确认项只能由答复或律师明确授权（`assumption_authorized`）解决。
- `ask` 时，操作员或律师回复「先写」，或者截止紧迫（政府、法院或交易设定的期限就在一两天内），按推荐答案起草，答复到达后修订（LWC-2026-0007：政府要求月底签约）。
- 拟提交法院、仲裁机构或监管机关的文书，向第三方出具、供其依赖的法律意见书，要求无保留结论，以及缺口会改变委托问题或我方身份的，核心缺口一律为必须确认。
- 既有文书的内部审阅和经律师转发客户的咨询型备忘录，可以用 `draft_mode: conditional` 写附条件结论。条件性继续回答的是「要不要停」，不是「要不要问」：会改变正文的缺口仍在起草前提问。

尽职调查 / 合规调查的必答与可后置事项见 `shared/references/due-diligence-playbook.md` 第 1 节。

## 第四步：选择提问方式并提问

| `ask_mode` | 做法 | 适合 |
|---|---|---|
| `interactive`（直接问） | 用宿主的提问工具逐题问，当场作答 | 操作员能回答；问题少；律师在线 |
| `questionnaire`（问卷文档） | 全部问题一次写成一份文档，操作员发给律师填写后粘贴回来 | 多数问题需律师或客户回答；经微信转达 |

选择顺序：

1. 操作员已经说明的照办：「直接问」「问我」用 `interactive`；「出问卷」「问题发给律师」「出问题清单」用 `questionnaire`；「不用问」「直接写」用 `none`。
2. 会话或实践配置中已有默认方式的，沿用。
3. 都没有时：
   - 问题全部是操作员能答的（哪份文件是基准、保存位置、律师原话的含义），直接问；
   - 否则，有提问工具的先用一道单选题请操作员选。前两个选项是「生成问卷文档」「直接问我」；第三个选项，没有必须确认项时是「不问，按推荐先写（问题列入《成稿说明》）」，有必须确认项时是「只问必须确认的 N 题，其余按推荐」。多数问题需律师或客户回答时推荐第一项。选第三项不等于授权，必须确认项仍须答复；
   - 没有提问工具时，输出下文的 `[CLARIFY:]` 清单，并说明「回复『出问卷』可生成 Word 问卷」。

先输出区块（此时 `ask_mode: pending`）再弹选择题；操作员选定后不必重出区块，在提问消息里写明所选方式即可。

### 直接问

- Claude Code 用 `AskUserQuestion`（如为延迟加载工具，先用 ToolSearch 加载）：每次 1—4 题，每题 2—4 个选项，推荐项放第一个并标「（推荐）」，「其他」由工具自动提供。题干写清所依据的材料事实，不依赖前文。先问必须确认，再问建议确认；超过 4 题分两次调用。可默认项不逐题问，在文字消息中列出「其余按默认：……」。
- 墨律桌面端用 `ask_user`，见 `shared/inkstatute-integration/ASK-USER-PROTOCOL.md`。
- 没有提问工具：输出 `[CLARIFY:]` 清单。
- 操作员对某题答「不确定」「问律师」的，把这些题汇总成一份只含这些题的问卷文档。

### 问卷文档

按 [references/questionnaire-mode.md](references/questionnaire-mode.md) 生成。文档包含全部问题（必须确认、建议确认、可按默认、材料请求）和「我们对材料的理解」，保存在事项资料目录，不进任何 git 仓库。回复中给出文件路径、可直接转发律师的一两句话、题量，以及等待期间做什么；同时贴出内容相同的 `[CLARIFY:]` 文本，便于直接粘贴微信。

生成问卷后可以继续不依赖答案的准备工作，做完即停下等答复；`ask` 且截止紧迫的，按推荐答案继续起草。

### `[CLARIFY:]` 文本清单

```text
[CLARIFY:]
给律师确认（请按序号回复即可）：

必须确认
1. [问题]
   影响：[为何会改变成果]
   A. ……（推荐）　B. ……

建议确认（不回复则按推荐处理）
2. [问题]
   推荐：[推荐答案；没有推荐的写「未答复时：……」]

可按默认值处理
3. [问题]
   默认：[默认值]

请提供的材料
4. [文件] —— [用途]

我们对材料的理解（如有误请指出）：[不超过五条]
[/CLARIFY]
```

`[CLARIFY:]` 中有必须确认项未解决前，不得生成结论性文书，也不得声称文书已完成。

### 题量与写法

- 直接问每轮 2—6 题。问卷文档一次列全：必须确认加建议确认通常不超过 10 题，可默认不超过 5 题；超过时合并同类，删去能从材料推出的。
- 每题只解决一个决定，有稳定编号，写明影响什么。可以标出推荐答案（起草者认为更合理的读法或做法），排在第一个；必须确认题也可以标推荐，但推荐不是默认，未答复不按推荐处理。拿不准哪个更合理时不标推荐，不诱导答案。
- 不问材料里已有答案的事，不问「还有其他要求吗」，不为凑题数或展示区块而制造问题。
- 第一轮答复后，只有新事实暴露新的关键分支时再问一次。通常最多两轮。

## 第五步：合并答复并恢复

操作员带回答复后（粘贴的微信文字、律师回填的问卷文本或文件路径，或宿主返回的 `ask_user` / `AskUserQuestion` 结果）：

1. 按题号合并到事项摘要。只给字母的按选项解释；对某一题回复「同意」「按推荐」，就是选了该题的推荐项，必须确认题也一样。笼统的「其余按默认」「都按建议」只覆盖建议确认题和可按默认题，必须确认题须逐题答复。
2. 在回复中列一张简短的合并表：题号｜答复要点｜处理（采纳 / 按默认 / 仍缺 / 与材料不一致）。
3. 仍缺的必须确认题和与材料矛盾的答复，只就这些追问一轮。
4. 必须确认项解决后，从暂停处继续：不重新清点材料，不重复问已答的题。
5. 律师明确交由模型判断的事项，记为 `assumption_authorized`，并写明采用的假设。
6. 答复带来新材料，或改变了底稿、任务的，重新输出 `INTAKE_DECISION`。

恢复后维护一份会话内摘要：

```yaml
intake_status: ready | ask | clarify
ask_mode: interactive | questionnaire | none
task_type: contract_review | contract_drafting | litigation | opinion | correspondence | research
draft_mode: complete | conditional | not_applicable
execution_profile: standard | high | critical
deliverable: "..."
party_role: "..."
audience: internal | external | mixed
questions:
  - {id: 1, tier: must | should | default | request, status: answered | defaulted | open}
confirmed: []
assumptions_authorized: []
deferred_items: []
open_items: []
```

该摘要只用于会话连续性。客户原文、律师答复原文和敏感材料不得写入日志、案例库或遥测。

## 可观察的 Intake 决策（必须）

完成第一步至第三步后、进入实质研究或正文之前（包括派出检索子代理之前），在回复正文中输出：

```text
[INTAKE_DECISION]
intake_status: ready | ask | clarify
reason: [一句话说明为什么继续、提问或暂停]
questions: 必须确认 N · 建议确认 N · 可按默认 N · 材料请求 N
ask_mode: interactive | questionnaire | none | pending（等操作员选择方式）
draft_mode: complete | conditional | not_applicable
execution_profile: standard | high | critical
deferred_items:
  - [不阻断、将在正文、批注或《成稿说明》处理的事项；没有则写 none]
[/INTAKE_DECISION]
```

要求：

- 区块写在给用户看的回复里。只在思考中作出判断不算输出：LWC-2026-0008 的记录写「已按时输出」，转录显示判断只出现在思考中。
- 区块之后紧接着提问：`interactive` 调用提问工具，`questionnaire` 生成文档，没有工具时输出 `[CLARIFY:]`。
- 任务属于起草、出具意见、诉讼文书或尽调，而 `questions` 全为 0 的，在 `reason` 中写明材料已覆盖哪些问题来源。
- 有必须确认或建议确认项而 `ask_mode: none` 的，在 `reason` 中写明原因，如「操作员要求不问」。
- 这是操作员可见的流程凭证，不写入最终法律文书；不复制客户原文，每项只写脱敏短语。
- `execution_profile` 按下文「执行档」判定并写入；正式法律意见书、对外尽调 / 合规调查报告、拟提交法院 / 仲裁机构 / 监管机关的文书默认 `critical`。

## 执行档（必须判定）

每个事项在 `INTAKE_DECISION` 中写入与品牌无关的 `execution_profile`：

- `standard`：单一主模型 + 自检；
- `high`：强主模型起草 + 不同模型独立复核；
- `critical`：材料提取、权威检索、起草、独立复核分角色执行，最后仍由律师人审。

默认 `critical` 的任务：正式法律意见书；对外尽调报告 / 合规调查报告；拟提交法院、仲裁机构或监管机关的文书；涉及行刑衔接、上市公司或国资主体的事项（指我方或客户是上市公司、国资主体，或事项可能使我方或客户承担行政、刑事责任，包括对方提出的此类指控）。存在大额、特殊主体、担保、客户敏感数据、不可逆外部发送或重大期限时不低于 `high`。

不要猜测用户额度，也不要硬编码模型品牌。宿主提供复核工具（如独立复核子代理）时，`high` / `critical` 的复核经该工具执行；人工操作员模式下由不同模型盲审。需要规划时读取
[references/operator-orchestration.md](references/operator-orchestration.md)。

## 交付前可观察的复核状态（必须）

`execution_profile` 为 `high` 或 `critical` 的事项，在交付成果的进度消息中输出：

```text
[REVIEW_STATUS]
execution_profile: high | critical
independent_review: done | skipped
reviewer: [不同模型 / 不同厂商复核者的脱敏标识，或 none]
disagreements_unresolved: [数量，或 none]
reason: [为何跳过，或复核如何执行（新鲜上下文、传入案情与初稿）]
[/REVIEW_STATUS]
```

要求：

- 与 `INTAKE_DECISION` 同理，**没有做独立复核必须是一个可观察的决定**，不得沉默交付。案例库 LWC-2026-0004 / 0005 / 0006 三件 `critical` 任务均未做独立复核且未显式声明，是最常见的流程缺口；LWC-2026-0007 首次执行（不同模型、新上下文），复核发现 1 处金额口径错误与 3 处论证缺口，均在交付前修正；
- 原定复核模型不可用（额度、限流）时，换另一个不同模型执行，`reviewer` 写实际复核者；按复核意见修改后未再做第二轮复核的，在 `reason` 中写明；
- 复核者在新鲜上下文中工作，只接收案情事实、已确认事项与候选成果，不接收起草者的推理过程；
- 复核者引入的法律依据同样经研究闸门核验后才能写入成果；
- 未消解的分歧逐条列入成果并标 `[HUMAN_REVIEW: 模型间存在未消解分歧 —— <争点>]`；客户成稿模式下列入给律师的《成稿说明》，不进客户正文；
- 该区块不写入最终法律文书，可写入交付说明。
