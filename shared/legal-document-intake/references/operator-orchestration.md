# 多模型操作员执行建议

当用户像项目经理一样在多个 LLM/agent 间分配任务时使用。本参考只给能力与角色建议，不绑定模型品牌或额度。

## 1. 先分阶段，不先分模型

建议把法律任务拆为：

1. 材料清点与事实提取；
2. 动态 intake 与律师补充；
3. 权威法源与反向依据检索；
4. 主成果起草/修订；
5. 独立法律审查；
6. Word/PDF 结构和视觉 QA；
7. 律师人审与反馈记录。

先确定每阶段产物和门槛，再把角色映射到当时有额度的模型。

## 2. 复杂度分级

| 等级 | 典型任务 | 建议执行 |
|---|---|---|
| `standard` | 机械整理、低风险摘要、明确模板的简单文件 | 一个合适模型完成并自检 |
| `high` | 合同全文审查、重要律师函、一般诉讼文书 | 强主模型 + 不同模型独立复核 |
| `critical` | 重大交易、时效紧急、陌生法域、关键法律意见 | 提取/检索/起草/复核分工，最强模型做最终综合，律师硬门槛 |

存在大额、特殊主体、担保、在先抵押、客户敏感数据、不可逆外部发送或重大期限时，不低于 `high`。

## 3. 额度使用策略

- 快速/低成本模型：材料目录、事实表、条款定位、格式检查；
- 强推理模型：问题识别、反例、策略、正文起草与综合；
- 有可靠检索能力的模型：权威源全文和引用核验；
- 不同强模型：盲审主稿，重点找遗漏、错误法条、立场偏移和不可执行措辞。

若只有一次高端模型额度，优先留给「基于已整理材料和检索底稿的最终综合」，不要消耗在原始文件摘录。

## 4. 不要把同一提示词盲发给所有模型

并行生成多份完整稿会增加比较成本，且难以判断谁遗漏了什么。更高效的分工：

- Agent A：事实与缺口；
- Agent B：法源、反例和程序陷阱；
- Agent C：按明确立场起草；
- Agent D：以对方律师/审判者视角质检；
- 主模型：综合修正并生成最终文件。

只有在建立基准评测时，才给不同模型同一任务；必须共享相同输入、实践配置、输出要求和评分维度。

## 5. 推荐的中间交付契约

每个 agent 交付以下最小结构，便于换模型继续：

```yaml
task_stage: extract | research | draft | review | document_qa
source_version: "hash-or-label"
party_role: "..."
confirmed_facts: []
assumptions: []
open_questions: []
findings: []
citations: []
artifact_path: "optional"
requires_human_review: true
```

不得在中间产物中复制不必要的客户全文。优先保存引用位置、文件哈希和脱敏摘要。

## 6. 律师反馈闭环

记录：任务类型、输入指纹、模型/推理档、结构指标、律师定性评价、被接受/拒绝原因和可复用规则。结构指标不能替代律师评价；律师评价是成果质量的最高权重标签。

将单次反馈转为窄规则。例如「乙方立场不够强」应落到具体触发项（在先抵押、自力救济、保证金重复受偿等），而不是把所有合同一律改成极端强硬。
