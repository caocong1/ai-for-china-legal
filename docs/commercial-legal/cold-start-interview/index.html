01概要

通过五步结构化访谈，收集律师的执业身份与团队层级、甲乙方双立场六维度审查立场、升级矩阵、文书风格与提问渠道、管辖法律与行业监管偏好，完整初始化实践配置文件 commercial-legal/CLAUDE.md。配置完成后，合同审查、合同起草、违约责任分析等全部商事合同流程都从这份文件读取个性化设置；配置缺失时各流程以「临时模式」降级运行。五步各自可以单独运行，只更新配置文件对应章节，无需重跑整个访谈。写入前按 practice-profile-schema.md 第 5 节对口述的条文号、阈值做合理性检查，发现矛盾先确认再写入。完整访谈约 5-10 分钟，单步约 2-3 分钟。

02适用与边界

适用场景

  • 首次安装商事合同工具，commercial-legal/CLAUDE.md 缺失或仍为占位符。
  • 合同审查等流程提示「尚未配置实践档案」，律师不想用通用默认值的临时模式。
  • 审批人、审查立场、文书风格或业务地域发生变化，需要整体重跑或只更新某一章节（如只更新升级矩阵、只更新管辖偏好）。
  • 开展新业务线（如新增涉港澳业务），需要单独补充管辖法律与行业合规提示。

不做什么

  • 不审查、不起草合同，不给出任何具体法律结论。
  • 不支持多套配置（不同事项扮演不同角色）；只能按最常用身份填写，特殊事项在事项工作区覆盖。
  • 不写入 commercial-legal/CLAUDE.md 以外的文件；目标不明时才按通用确认流程询问。
  • 不替代直接编辑：律师可直接修改配置文件，编辑后即时生效。

03输入与产出

需要律师提供

  • 律师对五组访谈问题的口述回答必需
    可跳过任一问题，跳过项保留 [PLACEHOLDER]
  • 既有的 commercial-legal/CLAUDE.md（含占位符或旧配置）可选
    已填章节只展示确认；写入时只更新本次访谈对应章节，保留其他未提交改动
  • 第一步填写的团队层级与审批人概览可选
    第三步升级规则直接展示供确认，不重问

产出

  • commercial-legal/CLAUDE.md（唯一真相来源）给律师内部
    章节：我们是谁 / 谁在使用 / 可用集成（第一步）；审查立场含整体风险偏好、甲方与乙方各六维度及交易破坏者（第二步）；升级矩阵：审批权限表、阈值、自动升级触发条件（第三步）；文书风格 / 输出 / 事项级动态确认策略（第四步）；共享护栏 → 管辖识别 → 律师专项管辖配置（第五步）
  • 每步结束的配置摘要给律师内部
    对话中展示 4-8 行要点（如执业身份、团队、升级路径、可用集成），并提示下一步要运行的命令

04开始前

前置条件

  • 访谈固定写入 commercial-legal/CLAUDE.md，无需反复询问输出格式与保存位置；只有用户要求写入其他配置文件或目标不明时，才按 shared/legal-document-intake/SKILL.md 确认。
  • 读取既有配置文件，已填章节只展示确认；写入时仅更新本次访谈对应章节。
  • 字段映射、读取契约、重跑/编辑/版本控制规则、法律事实合理性检查规则以 commercial-legal/skills/_shared/practice-profile-schema.md 为准。
  • 五步按身份 → 审查立场 → 升级规则 → 文书风格 → 管辖法律的顺序执行：身份先建立上下文，审查立场最核心，升级规则依赖前两步的层级和立场，文书风格独立性强，管辖法律最后补地域与行业维度。

硬性规则

固定写入目标
只写 commercial-legal/CLAUDE.md；写入时仅替换本次访谈覆盖的字段占位符，不覆盖其他章节。
先检索、后结论
给出任何法律结论、条款建议或风险判断前，优先用检索工具核对现行有效的法律法规、司法解释及指导性案例（注意修订、修正与废止）；无法核实时在结论处标注「未经检索核实，请以现行有效文本为准」；禁止凭记忆断言法条编号、发文文号或生效日期。
法律事实合理性检查
用户口述条文号、截止日期、阈值时，写入前交叉核对；有冲突时提示「你说的是 X；我的理解是 Y — 请确认哪个写入配置文件？[前提 flagged — 需验证]」。
占位符保留
用户跳过的问题保留 [PLACEHOLDER]，不强制填写；后续流程读到占位符时对该字段使用临时模式默认值（practice-profile-schema 第 3.2 节）。
版本控制与迁移
配置文件与代码同仓库纳入版本控制，可用 git log / git diff / git checkout 查看与回滚；复制该文件到其他项目或同事工作目录即完成迁移。

05执行步骤

共 5 步，按执行顺序。每步旁边（窄屏在步骤说明之后）是请律师核对的内置假设，可逐条复制。页面里的英文标记见首页「标记与术语」。

  1. 身份与团队

    /commercial-legal:identity-team可单独运行

    建立后续所有流程运行的基础上下文：谁在用（律师还是法务）、团队层级与审批人框架、执业环境、已接入的系统；决定输出标题是「律师工作产物」还是「研究笔记」。

    请律师核对

    • 核对 1.1执业身份三分法（律所 / 企业法务 / 其他）是否覆盖贵所情形，例如公职律师、公司律师。
    • 核对 1.2「非律师且无律师可咨询」即自动把全部输出降级为「研究笔记—非法律建议」，是否符合贵所对法务产出的定位。
    • 核对 1.3团队规模以 2-5 人 / 6 人以上分档，是否与贵所实际审批层级对应。

    做法

    1. 第一组「基本身份」四问：执业身份（律所执业律师 / 企业法务 / 其他如政府法务、学术机构）；角色与年限（合伙人、资深律师、主办律师、初级律师、法务总监、法务经理、法务专员等）；主要处理的合同类型（买卖、技术服务、租赁、建设工程、知识产权许可、投融资、劳动合同等，按频率排序）；主要交易对手类型（央企/国企/跨国公司、中小企业、个人、混合）。
    2. 若选企业法务，追问「是否可以随时咨询执业律师」，答案决定输出是否加「研究笔记—非法律建议」标注；若选其他，请对方简述工作性质后归类。
    3. 若为合伙人或法务总监，预先记录「最终升级联系人可能是本人」，留给第三步升级规则特别处理。
    4. 第二组「组织与团队」：团队规模三档（独立执业 / 小团队 2-5 人 / 大团队 6 人以上）；有团队时追问层级路径（示例：初级律师 → 主办律师 → 合伙人）和各层级可独立决定的合同金额粗略范围，具体阈值留给第三步收集。
    5. 独立执业时跳过层级两问，配置写「独立执业—无团队升级路径，最终升级联系人：[本人]」。
    6. 第三组「机构信息」：机构名称与实体类型（有限责任公司、股份有限公司、合伙企业、律师事务所普通合伙/有限责任、政府机关等）；每月合同处理量（选填，不影响行为）；最大痛点（开放题，常见答案如审查速度慢、找依据耗时、团队立场不统一，只用于调整后续重点，不写入特定字段）。
    7. 第四组「可用集成」：合同管理系统（法大大、合同在线、自研等，已连接时记录名称供输出路由）；电子签名（e签宝、法大大签名、Adobe Sign 等）；接收工作产物的通讯工具（企业微信 / 钉钉 / 飞书 / 邮件 / 其他）。
    8. 用答案替换「我们是谁」「谁在使用」「可用集成」三章节的占位符，不碰审查立场、升级矩阵、文书风格；结束时展示「身份与团队信息已配置」摘要并提示下一步运行 /commercial-legal:review-stance。

    内置规则

    • 机构名称后缀与口述实体类型不符（如名称含「有限公司」却说「合伙企业」）时温和确认，标 [前提 flagged — 需验证]。
    • 执业年限明显异常（如 50 年）不拒绝，只记录并提示「这意味着你的经验超过行业大多数人」。
    • 机构名称含特殊字符时按用户原始输入保存，不做字符清洗。
    • 非律师且无律师可咨询：在「谁在使用」写入提醒，所有输出自动附加「研究笔记—非法律建议，供律师审查」。
    • 用户跳过某问题保留 [PLACEHOLDER]，后续流程读取时触发该字段的临时模式。
    • 当前版本不支持多套配置；建议按最常用身份填写，特殊事项在事项工作区覆盖。
    • 合伙人或法务总监本人为最终升级联系人时标注「最终决策人为本人」，第三步将设置为「无需外部升级」。

    产出

    更新 commercial-legal/CLAUDE.md 的「我们是谁」（机构名称、实体类型、团队规模、升级联系人概览、月合同量、交易对手类型、合同管理系统、最大痛点）、「谁在使用」（角色、是否有律师可咨询）、「可用集成」三章节；对话中输出四行摘要。

  2. 审查立场

    /commercial-legal:review-stance可单独运行

    收集最核心、最影响审查行为的配置：整体风险偏好、我方为甲方和为乙方时六个维度各自的「标准立场 / 可接受备选 / 绝不接受」、无论金额大小都不能接受的交易破坏者。

    请律师核对

    • 核对 2.1以「实际损失的 130%」作为《民法典》第585条合理调整上限（示例立场写「不超过实际损失的 30%」）——是否符合贵所理解与现行司法解释口径。
    • 核对 2.2进取型「典型 1-2 项交易破坏者、超过 5 项即提示矛盾」这一经验阈值是否合理。
    • 核对 2.3六个维度是否遗漏贵所常见维度，如付款与验收、保密、不可抗力、担保、合同转让。
    • 核对 2.4示例交易破坏者清单（甲方 5 项、乙方 4 项）是否符合贵所底线，是否需要替换成贵所自己的清单。

    做法

    1. 整体风险偏好三选一（保守型 / 平衡型 / 进取型），同时说明每档对应的标记行为；无法选择时引导「更倾向全面保护，还是维护关系推进交易」；大型企业法务常见甲乙方偏好不同，可分别记录两个偏好。
    2. 甲方立场（我方为买方/委托方）逐维度提问。责任限制：直接损害赔偿上限（合同总价的 100%、200%、无上限等）、间接/后果性损害（利润损失、商誉损失）排除还是允许、例外情形（故意、重大过失、知识产权侵权、数据泄露、保密义务违反）；追问数据处理合同等高风险供应商是否要求不同上限。
    3. 甲方违约金：标准立场示例「按实际损失计算，违约金不超过实际损失的 30%（依《民法典》第 585 条）」，可接受备选示例「固定违约金，但不超过合同总价的 20%」，绝不接受示例「无违约金或违约金仅象征性条款」。
    4. 甲方知识产权（委托开发成果归甲方完全所有 / 双方共有 / 甲方独家使用权而著作权归乙方；追问软件开发合同与一般服务合同是否不同）；数据保护（乙方遵守《个人信息保护法》《数据安全法》、数据出境限制、泄露通知时限如 24 小时内、到期删除/返还；追问金融、医疗、教育等行业特殊数据监管）。
    5. 甲方期限与终止（固定期限还是长期；是否要求便利终止权及提前通知期；是否接受自动续约及通知义务；绝不接受示例「无通知自动续约」「最短期限超过 5 年无终止权」）；管辖与争议解决（首选如「中国法律，甲方所在地人民法院」，可接受如被告所在地/合同履行地法院，是否接受仲裁及机构偏好，绝不接受如境外管辖法律、未经特别授权的境外仲裁）。
    6. 甲方交易破坏者，参考示例 5 项：乙方不承担数据泄露责任、知识产权全部保留给乙方、甲方承担无限责任、未经特别授权的境外法律管辖、乙方有权单方面修改合同。
    7. 乙方立场（我方为卖方/受托方）同样六维度：责任限制上限（合同总价 100% 或合同期内已收取费用总额）、是否排除间接损失、绝不接受「无责任上限」「承担买方所有间接损失」；违约金（以实际损失为基准不设惩罚性违约金，逾期付款违约金如日利率 0.05%）；知识产权（既有知识产权各自所有不发生转让、新开发成果归属、绝不接受「所有技术成果含既有技术完全转让」）。
    8. 乙方数据保护（是否有 DPA 模板、能否接受超出《个保法》最低要求的义务、数据本地化如境内服务器）；期限与终止（最短运行期、甲方便利终止时的通知期/终止补偿金、自动续约、绝不接受「甲方可随时无偿终止且不补偿已完成工作」）；管辖（乙方所在地法院或协商确定、被告所在地对乙方是双刃剑、仲裁不公开利于商业声誉、绝不接受未经集团总部批准的境外仲裁）。
    9. 乙方交易破坏者，参考示例 4 项：甲方无任何赔偿随时终止、乙方对甲方所有损失含间接损失承担无限责任、甲方可随意把合同权利义务转让给第三方含竞争对手、甲方不付款时暂停后续合同的捆绑条款。
    10. 可接受备选：从前面回答直接提取，或逐维度追问「理想方案是 [X]，对方不接受时最低可接受的备选是什么」。
    11. 写入「审查立场」全部字段，并在章节顶部新增「整体风险偏好」一行（模板原本没有这个字段）；甲乙方不同则写「甲方风险偏好」「乙方风险偏好」两行。

    内置规则

    • 保守型：标记所有偏离标准立场的条款，中等及以上问题均标记并建议修改；平衡型：高及以上标记并修改，中等只备注不要求修改；进取型：仅关键级交易破坏者强制处理，其余标记不强推。
    • 违约金比率高于《民法典》第585条合理调整上限（通常为实际损失的 130%）时提示潜在可调整风险，标 [前提 flagged — 需验证]（规则来自 practice-profile-schema 第 5.2 节）。
    • 进取型但交易破坏者清单超过 5 项（进取型典型范围为 1-2 项核心利益）时，写入前提示二选一：保持进取型并照写，或将风险偏好调整为平衡型/保守型。
    • 责任限制例外清单含含糊措辞（如「一切重大过失」）时建议澄清认定标准；设置「绝不接受境外管辖」时确认是否同样适用于在华外资企业合同。
    • 「只做甲方」或「只做乙方」时，另一方立场保留 [PLACEHOLDER]，读取时提示选择「临时模式—通用默认值」；跳过的维度不强制填写。
    • 只给交易破坏者不愿细化备选时，备选留空不强求；甲乙方某维度相同时分别写入两章节，不合并。
    • 用户答「不确定 / 视情况而定」时确认是否跳过：留空，需要时在临时模式下处理，或日后重跑本步更新。

    法律依据

    • 《民法典》第585条 — 违约金比率合理性检查（口述上限超过实际损失 130% 时提示）
    • 《个人信息保护法》 — 数据保护维度提问基准
    • 《数据安全法》 — 数据保护维度提问基准

    产出

    更新「审查立场」章节：甲方 7 项（责任限制、违约金、知识产权、数据保护、期限与终止、管辖与争议解决、交易破坏者）+ 乙方 7 项，顶部加整体风险偏好；对话中输出摘要（风险偏好、甲乙方核心立场与交易破坏者数量、已覆盖六维度）。

  3. 升级规则

    /commercial-legal:escalation-rules可单独运行

    定义何种金额、风险等级或特定条款一经发现必须上报更高层审批人，让审查输出能直接指向正确的审批人。

    请律师核对

    • 核对 3.1示例金额区间（50 万 / 200 万 / 500 万）与贵所合同分级是否一致。
    • 核对 3.29 项自动升级触发示例是否符合贵所；「对方为监管机构或政府部门」「潜在刑事合规风险」是否应一律自动升级。
    • 核对 3.3「发现关键级问题无论金额大小必须升级」是否过严，是否应允许主办律师层级处理部分关键级问题。

    做法

    1. 先确认团队层级：第一步已填则直接展示供确认或更新；常见结构为独立执业无需升级 / 律所小团队「初级律师 → 主办律师/合伙人」/ 大型法务团队「法务专员 → 法务经理 → 法务总监 → 总法律顾问/CEO」。
    2. 按层级依次收集可独立审批金额上限，表格含「需升级条件」（初级：超过上限或有关键风险问题；中级：超过上限或有交易破坏者；最高层：无上限）；用户不确定时先填常见参考值，日后重跑更新；用户说「没有金额阈值，按风险等级升级」则跳过。
    3. 询问是否有固定金额区间（示例：小额合同 ¥50 万以下、中型 ¥50 万—¥200 万、大额 ¥200 万—¥500 万、重大 ¥500 万以上）；没有则直接用层级上限。
    4. 风险等级升级规则：发现关键级问题无论金额必须升级；高风险超过 [N] 项需升级；交易破坏者触发直接升级到最终审批人，不在初级层级处理；追问关键级是升给主办律师/法务经理还是直接合伙人/法务总监。
    5. 自动升级触发清单：结合第二步的交易破坏者确认范围，参考 9 项（无限责任、知识产权全部转让含既有、数据出境条款、管辖法律为境外法律、对方可单方修改合同、金额超过审批权限上限、关系到上市/融资合规、对方为监管机构或政府部门、潜在刑事合规风险如不寻常资金流向）；追问行业特有条件（金融牌照、医疗器械资质等）。
    6. 审批人信息：姓名、角色、联系方式、可审批范围，分一级审批与最终审批（无上限）；说明联系方式写入本地配置文件不对外发布，不愿写具体号码可填「内部通讯渠道」。
    7. 写入「升级矩阵」：审批权限表、阈值（模板章节名为「美元阈值」，实为人民币）、自动升级触发条件逐条；若第一步「最终升级联系人」仍为占位符，同步写入审批人姓名与联系方式。

    内置规则

    • 金额阈值逻辑矛盾（如初级律师上限 ¥[A] 高于主办律师上限 ¥[B]）时提示确认，标 [前提 flagged — 需验证]。
    • 进取型风险偏好但自动触发条件超过 10 项时提示矛盾：几乎所有风险都自动升级，实际接近保守型操作。
    • 独立执业：所有升级矩阵字段填「独立执业—无需外部升级，本人为最终决策人」；自动触发条件仍保留，用于提示律师特别审慎处理。
    • 合伙人/法务总监本人就是最终审批人时标注「最终决策人为本人」，输出中的升级提示改为「建议寻求外部法律意见」。
    • 审批人联系方式缺失保留 [PLACEHOLDER]，升级路由时提示「请将此问题升级给 [角色]，联系方式待配置」。
    • 自动触发条件与第二步交易破坏者重叠时两处均写入，读取时效果相同（都触发升级提示）。

    产出

    更新「升级矩阵」章节（审批权限表、各层级人民币阈值、自动升级触发条件）；对话中输出摘要（层级结构、初级/中级/最终审批阈值、触发条件数量、审批人已配置或待配置）。

  4. 文书风格与确认策略

    /commercial-legal:document-style可单独运行

    决定输出的形式、语气、引用深度、工作产物存放、律师答复渠道与提问预算、多模型复核强度，使交付物不需要律师二次大幅改格式即可使用。

    请律师核对

    • 核对 4.1业务方摘要「200-300 字以内」是否符合贵所业务方的阅读习惯。
    • 核对 4.2「每轮 2–5 题、通常最多两轮」的提问预算在复杂合同上是否够用。
    • 核对 4.3三档复核强度中「重要合同/律师函」「重大或陌生事项」由谁判定、按什么标准判定，文件未规定。

    做法

    1. 默认输出类型四选一：完整审查备忘录（含风险标记、修改建议、法律依据、谈判要点，内部留底）/ 管理层或业务方摘要（聚焦商业影响，减少术语，200-300 字以内）/ 修订标记文档（直接在合同上标注，发回对方）/ 组合输出；追问是先收完整版再决定要否摘要，还是默认每次组合。
    2. 修订建议语气三选一：强硬立场（示例「本条款赋予乙方单方面修改价格的权利，应予删除。」）/ 温和但有立场（示例「建议在本条款中增加价格变更的书面通知要求。」）/ 协商式（示例「在不改变整体结构的前提下，建议对第 X 条作如下调整……」）；追问是否因合同类型而变（框架合同强硬、短期采购协商式）。
    3. 法条引用四选一：逐条附（按 legal-basis-conventions.md 格式）/ 仅关键与高风险问题附，中等问题简述 / 不附 / 完整备忘录附而业务摘要不附。
    4. 案例引用四选一：最高院指导性案例（有参考效力，非约束力）/ 典型裁判观点（标注「非约束力」）/ 不引用 / 仅限争议焦点；始终标注「参考」性质。双语输出三选一：全部双语 / 仅在对方要求时切换 / 默认中文。
    5. 工作产物存放位置（合同管理系统 / 本地文件夹按事项分类 / 企业共享盘如腾讯文档、飞书文档、钉钉盘 / 不固定）；续约/期限提醒接收人与抄送人，或不需要自动提醒。
    6. 常用合同模板库（类型简述，起草时会询问是否参考）与常用修改建议语言库（存放位置、获取方式、使用最多的前 3 类条款）。
    7. 事项级确认：律师答复渠道（App 内 ask_user 卡片 / 操作员复制问题到微信再带回 / 两者均可能以宿主能力为准）；动态问题偏好，建议默认「先读材料，每轮 2–5 个会改变成果的问题，通常最多两轮」，可用默认值的事项单列并允许一次性回复「按建议默认」。
    8. 同时确认四项语义：「视情况而定」是否表示相关时逐项问律师；用户已明确 Word、文件路径和保存位置时是否禁止重复确认；Word 修订稿是否默认保存至源文件同目录、使用新后缀且永不覆盖原件；外部发送版本是否默认去除内部评级和特权说明。
    9. 重要事项的复核强度三档：普通任务「单模型 + 自检」；重要合同/律师函「主模型 + 不同模型独立复核」；重大或陌生事项「提取、检索、起草、复核分角色，律师最终人审」；配置只记录 standard / high / critical 等级，模型品牌和额度由操作员每次执行时决定。
    10. 写入「文书风格」（语气、摘要要求、存放位置、提醒接收人）、「输出」（默认格式、法条/案例引用、双语、模板与语言库备注；不覆盖已有的工作产物标题和审查者注释块模板）、「事项级动态确认策略」（答复渠道、问题预算与轮次、默认授权、「视情况而定」语义、输出/路径安全默认、复核强度）。

    内置规则

    • 默认值：输出类型缺省「完整审查备忘录」；法条引用缺省「是，仅在重要问题时附」；案例引用缺省「仅限争议焦点」。
    • 第二步选了「保守型」却选「协商式」语气时提示矛盾（风险标记很多但措辞温和），二选一：保持两者并明确列出所有风险，或改为「温和但有立场」。
    • 纯国内业务却选「全部输出双语」时温和确认，建议改为「仅在对方要求时切换」。
    • 用户要求引用「判例」时纠正措辞：中国以成文法为主，法院判决不具正式判例法约束力，只引用最高院指导性案例与典型裁判观点并标注「参考价值，非法律约束力」。
    • 没有模板写「无现有模板，从头起草」，起草流程默认使用民法典标准框架；语言库不在数字化工具中则备注「存储于 [位置]，每次手动提供」。
    • 通过操作员微信沟通时输出可直接复制的 [CLARIFY:] 清单，收到答复后从事项摘要继续，不重问。
    • 多个模型套餐但额度波动时只记录 standard / high / critical，不绑定模型名，由操作员当次映射。

    产出

    更新「文书风格」「输出」「事项级动态确认策略」三章节；对话中输出八行摘要（默认输出、修订语气、法条引用、案例引用、双语、补充信息渠道、每轮 N 题最多 N 轮、独立复核等级）。

  5. 管辖法律

    /commercial-legal:jurisdiction-profile可单独运行

    让审查流程知道律师的主要法域、常涉的特别管辖区、争议解决偏好和行业监管要求，并在具体合同中正确标记特殊管辖情形。

    请律师核对

    • 核对 5.1法院层级金额参考表（500 万 / 1 亿）只作访谈提示、不写入配置，是否同意这种不固化的处理。
    • 核对 5.2对境外仲裁机构偏好的立场「纯境内合同优先境内机构」是否符合贵所意见。
    • 核对 5.38 行业监管表是否覆盖贵所主要客户行业（如能源、交通、房地产开发），是否需补充。
    • 核对 5.4专属管辖合同举例（保险、海事、铁路/航空）是否准确、是否需补充其他类型。

    做法

    1. 主要法律体系四选一：中国大陆法律 / 大陆为主偶涉港澳台 / 大陆为主偶涉跨境或外资合同 / 混合法律体系；涉外时追问是「内部分析后转外部律师」还是「自己直接处理」。
    2. 业务地域分布，对照六类地区表：普通省市（适用地方性法规，通常无特别立法）/ 经济特区（深圳、珠海、汕头、厦门，有特别立法权）/ 海南自由贸易港（自贸港法规体系）/ 自由贸易试验区（负面清单等特别监管）/ 民族自治地方（自治条例和单行条例）/ 港澳台（不同法域）；追问是否经常涉及经济特区当事人。
    3. 法院管辖首选（甲方所在地 / 乙方所在地 / 被告所在地即默认规则 / 合同履行地 / 具体城市）；法院级别偏好对照参考表（基层法院：争议标的 500 万以下；中级法院：500 万—1 亿；高级法院：1 亿以上或重大复杂案件；最高人民法院：特别重大民事案件；均以北京/上海为例，各地标准不同）；追问常处理的合同金额范围，用于核对自动升级阈值与法院级别是否匹配。
    4. 仲裁还是诉讼：仲裁为主（保密性强但执行可能更久）/ 诉讼为主（执行力明确，适合追偿金额确定的违约）/ 视合同类型；倾向仲裁时追问机构（中国国际经济贸易仲裁委员会 CIETAC 为涉外首选、北京仲裁委员会 BAC、上海国际仲裁中心 SHIAC、广州仲裁委员会、各省市地方仲裁委）。
    5. 特别管辖情形逐项问「经常 / 偶尔 / 基本不涉及」：经济特区（深圳商事登记、知识产权、数据条例有特别规定；海南税收与跨境数据流动特别政策）、自贸区（负面清单、特别监管规定、数据跨境试点）、民族自治地方（自治条例与单行条例、民族区域商业习惯）、港澳台（香港普通法体系、澳门葡法系民法典、台湾不同法域）；涉港澳台追问自己处理还是转专项律师。
    6. 主要服务行业对照 8 行业监管表：金融（人民银行、金融监管总局、证监会；资管规定、金融消费者保护）/ 互联网科技（网信办；《数据安全法》《个保法》《网络安全法》）/ 电信（工信部；电信业务许可与数据保护）/ 医疗医药（卫健委、药监局；器械许可、药品流通）/ 教育（教育部、地方教育局；培训机构资质）/ 建设工程（住建部；施工许可、监理、安全生产）/ 食品（市场监管总局；食品安全标准、生产许可）/ 消费品零售（市场监管总局、海关总署；产品质量、进出口）；追问最常需要提示的合规要求。
    7. 客户特殊要求：上市公司或国企（信息披露、关联交易审批）、外资企业总部合规政策、跨境合同出口管制（科技产品、军民两用技术）。
    8. 写入「共享护栏 → 管辖识别」：确认模板既有的标准触发规则（通常不改），在其下新增「律师专项管辖配置」子节（法律体系、业务地域与特别管辖区、争议解决偏好、特别管辖情形标注、行业合规提示点）；不覆盖模板已有的经济特区/民族自治/自贸区/港澳台触发标记规则。结束时宣告访谈全部完成，可运行 /commercial-legal:contract-review。

    内置规则

    • 全部业务在大陆、无特殊管辖：配置「主要管辖：中国大陆法律；无特别管辖区需关注」，管辖识别保持模板默认规则。
    • 不确定是否涉特别管辖区：保持模板默认触发规则，遇到即标「管辖 flagged」。
    • 涉港澳台但由外部律师处理：配置「港澳台合同转专项律师」，审查中只标「涉港澳台 — 需专项核查」。
    • 多行业律师逐行业列提示点，流程识别合同行业特征后读取对应提示；仲裁/诉讼偏好因合同类型不同时分类型记录。
    • 管辖偏好与法律强制性规定可能冲突（如保险合同、海事合同、铁路/航空合同已有法定专属管辖，当事人不得协议变更）时提示并标 [前提 flagged — 需验证]。
    • 用户提及的行业监管要求距最后更新超过 6 个月时，标 [时效性 flagged — 需验证最新法规：网信办/工信部/市场监管总局最新规定]（practice-profile-schema 第 5.1 节）。
    • 设置境外仲裁机构（ICC、HKIAC、SIAC）为偏好时提示：中国法院承认和执行境外仲裁裁决依据《纽约公约》，实践中存在一定不确定性；建议纯境内当事人合同优先境内仲裁机构，涉外合同按对方接受情况灵活处理；确认是否保留，标 [前提 flagged — 需验证适用场景]。
    • 法院层级管辖金额标准因地区而异且可能调整，不在配置文件中固化；分析具体合同时按当事人所在地适用标准判断。

    法律依据

    • 《纽约公约》 — 境外仲裁裁决在中国的承认与执行提示
    • 《数据安全法》《个人信息保护法》《网络安全法》 — 互联网/科技行业合规提示
    • 经济特区条例（特别立法权） — 深圳、珠海、汕头、厦门、海南特别规定提示

    产出

    更新「共享护栏 → 管辖识别」章节的律师专项管辖配置；对话中输出五行摘要（主要法律体系、业务主要地域、争议解决偏好、特别管辖区关注、主要行业合规点）。

  • 机构名称后缀与实体类型一致性；执业年限异常提示。
  • 整体风险偏好与交易破坏者数量（进取型超过 5 项）、与自动升级触发条件数量（进取型超过 10 项）、与修订语气（保守型 + 协商式）三组一致性检查。
  • 金额阈值层级逻辑（下级上限不得高于上级）。
  • 口述违约金比率是否超过《民法典》第585条合理调整上限（实际损失的 130%）。
  • 管辖偏好与法定专属管辖是否冲突；境外仲裁机构偏好是否确认。
  • 行业监管要求距最后更新超过 6 个月时加时效性标记。
  • 写入时只替换本次访谈覆盖的字段，其他章节原样保留。

09何时暂停或升级

  • 整体风险偏好与后续回答矛盾时，写入前暂停，二选一后再写。
  • 用户口述条文号或阈值与理解冲突时暂停确认，标 [前提 flagged — 需验证]。
  • 设置境外仲裁机构偏好时暂停提示《纽约公约》执行不确定性，确认是否保留。
  • 用户要求写入 commercial-legal/CLAUDE.md 以外的文件或目标不明时，按通用确认流程询问。
  • 用户现在无法提供审批人信息：金额与风险规则先写入，审批人字段保留占位，提示日后重跑 /commercial-legal:escalation-rules。
  • 用户对某维度答「不确定」：确认后跳过，留空等待临时模式处理或日后重跑。

10请律师重点核对

下面是这个流程内置的法律假设、立场、阈值和清单，每一条都可以同意、反对或补充。条目下的「相关批注」按文字重合自动匹配到步骤旁的核对条目，可能不全。

  1. 风险偏好三档决定标记门槛：保守型标记所有中等及以上问题并建议修改；平衡型高及以上标记并修改、中等仅备注；进取型只强制处理关键级交易破坏者。三档定义是否够用？贵所是否需要甲乙方分别设置？
  2. 违约金合理性检查以「实际损失的 130%」作为《民法典》第585条的合理调整上限，示例标准立场写「不超过实际损失的 30%」，共享规则还提到「市场惯例通常为 30%~100%」。这些数字是否符合贵所实践与现行司法解释口径？相关批注：核对 2.1
  3. 矛盾检测阈值：进取型 + 交易破坏者超过 5 项（典型 1-2 项）、进取型 + 自动升级触发条件超过 10 项、保守型 + 协商式语气，均会触发写入前提示。这三条经验规则是否合理？相关批注：核对 2.2
  4. 升级矩阵的金额区间示例（小额 ¥50 万以下 / 中型 ¥50 万—¥200 万 / 大额 ¥200 万—¥500 万 / 重大 ¥500 万以上）和 9 项自动升级触发示例（含「对方为监管机构或政府部门」「潜在刑事合规风险」）是否符合贵所？另外「发现关键级问题无论金额大小必须升级」「交易破坏者直接升到最终审批人」是否过严，是否应允许主办律师层级消化部分关键级问题？相关批注：核对 3.3、核对 3.2
  5. 法院层级管辖金额参考表（基层 500 万以下 / 中级 500 万—1 亿 / 高级 1 亿以上，以北京/上海为例）只作提示、不写入配置，分析时按当事人所在地标准判断。是否同意不固化？相关批注：核对 5.1
  6. 境外仲裁机构（ICC、HKIAC、SIAC）偏好会触发提示：依《纽约公约》承认执行有不确定性，建议纯境内合同优先境内机构。贵所是否同意这一立场？相关批注：核对 5.2
  7. 案例引用立场：用户要求引用「判例」时流程会纠正措辞，所有案例（含最高院指导性案例）只标「参考价值，非法律约束力」。默认值为法条引用「仅在重要问题时附」、案例引用「仅限争议焦点」、输出类型「完整审查备忘录」。这些默认是否合适？
  8. 非律师且无律师可咨询时，所有输出自动附加「研究笔记—非法律建议，供律师审查」；律师角色则为「律师工作产物 — 受律师-当事人特权保护」。这一二分是否符合贵所对法务产出的定位？相关批注：核对 1.2
  9. 六个审查维度（责任限制 / 违约金 / 知识产权 / 数据保护 / 期限终止 / 管辖争议）是否遗漏贵所常见维度（如付款与验收、保密、不可抗力、担保、合同转让）？SKILL.md 未规定如何新增维度。相关批注：核对 2.3
  10. 行业监管表只列 8 个行业（金融、互联网、电信、医疗、教育、建设工程、食品、消费品），专属管辖举例只有保险、海事、铁路/航空合同。是否需补充贵所主要行业与其他专属管辖情形？相关批注：核对 5.4
