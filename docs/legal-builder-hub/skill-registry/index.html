01概要

管理技能从登记到发布的全过程：校验或生成技能的 SKILL.md 与 plugin.json 元数据，按语义化版本（SemVer）升版并生成变更日志，解析依赖树、检测版本冲突与循环依赖并核对许可证兼容性，最后在注册表中查询技能或发布新版本，管理发布状态与撤销、废弃。技能开发者发布时按四步顺序走（清单管理 → 版本发布 → 依赖解析 → 注册表查询与发布），技能使用者查询时可直接用第四步。流程先读取 legal-builder-hub/CLAUDE.md 中的注册表类型、注册表地址、发布审核流程、用户角色与技术背景，未配置时按本地注册表、人工审核的临时模式运行。总流程规定发布前须已通过安全审查、已发布版本不可覆盖、依赖须用版本范围声明且禁止循环依赖；法律层面只引用《著作权法》（2021年修正，未写条号）、《个人信息保护法》第13条（开发者注册信息）和平台技术规范。

02适用与边界

适用场景

  • 技能开发者准备把新技能或新版本提交到本地、组织内部或公共社区注册表
  • 需要检查一个技能目录的 SKILL.md 与 plugin.json 是否格式合规、字段完整、名称一致，或为新技能生成 SKILL.md 骨架
  • 需要判断本次变更应升 MAJOR、MINOR 还是 PATCH，并生成变更日志和发布前检查清单
  • 技能依赖其他技能、第三方库、平台版本或数据源，需要检查版本冲突、循环依赖和许可证兼容性
  • 技能使用者想按名称、领域、版本、安全状态、许可证、作者或依赖关系查询注册表中的技能
  • 已发布版本发现严重问题需要撤销，或技能不再维护需要标记废弃

不做什么

  • 不做安全审查本身：发布前要求安全审查已通过，审查转 /legal-builder-hub:security-review
  • 不负责安装和发现：安装已发布技能转 /legal-builder-hub:installation，发现新技能转 /legal-builder-hub:skill-discovery
  • 不覆盖已发布版本：已发布版本有问题只能撤销后以新版本号发布
  • 依赖解析只出报告，不修改依赖项
  • 元数据不完整的技能不发布到公共注册表；路径不一致、描述含占位符不自动修复，须手动修复或由开发者补充

03输入与产出

需要律师提供

  • 操作类型（查询 / 发布 / 版本管理 / 依赖检查）及技能名称必需
    单独做清单管理时为校验 / 生成 / 修复，并提供技能目录路径
  • 技能目录（SKILL.md 与 plugin.json，含当前版本号、技能注册条目和依赖声明）可选
    清单校验、版本管理、依赖解析需要；只做注册表查询时不需要
  • 变更内容：Git 提交历史或手动输入的变更说明可选
    版本发布时用来确定升级类型并生成变更日志；为空时只警告、不阻止
  • 安全审查报告编号可选
    发布时关联到注册表记录；安全审查未通过则阻止发布
  • legal-builder-hub/CLAUDE.md 实践配置（注册表类型、注册表地址、发布审核流程、用户角色、技术背景）可选
    缺失或为 PLACEHOLDER 时进入临时模式：本地注册表、人工审核

产出

  • 技能清单校验报告给技能开发者
    SKILL.md 校验表（YAML frontmatter、name、description、命名规范、目的/工作流/输出章节，逐项通过或不通过并说明）；plugin.json 校验表（必填字段、版本号格式、技能路径存在、两处 name 是否一致）；综合结论（全部通过 / 存在问题（可修复）/ 严重问题）与须修复项清单；新技能可另附 SKILL.md 骨架
  • 变更日志与发布前检查清单给技能开发者 / 审核员
    变更日志以「## [版本号] - [发布日期]」为题，分新增、改进、修复、安全（附 CVE 编号）、废弃、依赖；发布前检查清单分代码质量、元数据、安全审查、依赖、文档五组勾选项；发布后验证表（注册表记录、下载测试、安装测试、基础功能）
  • 依赖解析报告给技能开发者
    依赖树（直接与传递依赖及解析版本）；冲突检测表；循环依赖检测；许可证兼容性表；依赖安全状态表；解析摘要（直接依赖、传递依赖、版本冲突、循环依赖、许可证风险、安全漏洞）；综合结论（依赖可解析 / 存在冲突或风险 / 不可解析）与须处理项
  • 注册表查询结果给技能使用者
    注册表（本地/组织/公共及地址）、查询条件、匹配数量；结果表列技能名称、最新版本、安全状态、许可证、发布时间
  • 发布结果与发布状态表给技能开发者 / 注册表管理员
    技能包上传、元数据注册、安全状态关联、审核状态（自动通过 / 待审核 / 已批准）、发布状态（已发布 / 待审核 / 发布失败）；注册表查询地址与安装命令；发布状态表（技能、版本、状态、更新日期、说明）

04开始前

前置条件

  • 读取 legal-builder-hub/CLAUDE.md 五项配置：注册表类型（本地/组织/公共，决定注册表操作范围）、注册表地址（远程注册表连接）、发布审核流程（发布审批要求）、用户角色（可执行的操作类型）、技术背景（操作指导详细程度）
  • 配置缺失或为 PLACEHOLDER 时进入临时模式 [临时模式]：注册表类型按本地注册表、发布审核按人工审核，并建议运行 /legal-builder-hub:cold-start-interview 完善配置
  • 发布前须确保技能已通过安全审查（/legal-builder-hub:security-review）
  • 清单校验前加载平台技术规范（SKILL.md 与 plugin.json 格式规范）；依赖解析和发布前连接注册表（本地或远程）
  • 法条引用按 legal-builder-hub/skills/_shared/legal-basis-conventions.md 的规范，引用库为 legal-builder-hub/skills/_shared/skill-hub-citations.md

硬性规则

元数据完整性
发布到注册表的技能须具备完整的元数据（SKILL.md + plugin.json 中的技能注册）；元数据不完整的不得发布到公共注册表；本地注册表可接受开发中版本（标注 [开发中]）
版本规范
版本号须遵循语义化版本（SemVer）MAJOR.MINOR.PATCH：MAJOR 升级表示不兼容变更，MINOR 升级表示向后兼容的功能新增，PATCH 升级表示向后兼容的问题修复
发布安全
发布前须确保技能已通过安全审查；发布后不可覆盖已发布版本，只能发布新版本号；发布操作须记录审计日志；撤销发布须标注原因并通知已安装用户
依赖管理
技能须声明所有外部依赖（其他技能/库/工具）；依赖版本须使用范围声明（如 >=1.0.0 <2.0.0），不使用精确版本锁定；禁止循环依赖；须检查依赖项的许可证兼容性
两种使用路径
技能开发者发布：步骤 1 → 2 → 3 → 4；技能使用者查询：直接触发步骤 4；各步骤均可单独触发

05执行步骤

共 4 步，按执行顺序。每步旁边（窄屏在步骤说明之后）是请律师核对的内置假设，可逐条复制。页面里的英文标记见首页「标记与术语」。

  1. 技能清单管理

    /legal-builder-hub:skill-manifest-management可单独运行

    确保技能的 SKILL.md 和 plugin.json 中的技能注册条目符合平台技术规范：格式正确、必填字段完整、命名合规、描述清晰，为发布提供元数据质量保障。

    请律师核对

    • 核对 1.1命名冲突检查的依据写为《著作权法》（2021年修正）「技能命名和描述不侵犯他人著作权」，未写条号；以著作权作为名称冲突的判断依据是否恰当，请律师核对
    • 核对 1.2自动修复中只有「命名不规范 → 转换为 kebab-case」写明须确认，生成 frontmatter、添加章节占位符会直接改动开发者的文件，是否应一律先征得确认？
    • 核对 1.3描述长度前后两条规则（不超过 200 字 / 50–200 字）并存，不足 50 字是否判为不通过，SKILL.md 未说明

    做法

    1. 获取技能目录路径，加载平台技术规范（SKILL.md 格式规范、plugin.json 格式规范）
    2. 校验 SKILL.md 必填结构：以 --- 开头和结尾的 YAML frontmatter；name 字段为小写字母加连字符（kebab-case）；description 非空、不超过 200 字、中文或英文；argument-hint 建议存在；须有以「# 」开头的一级标题，以及「## 目的 / ## Purpose」「## 工作流 / ## Workflow」「## 输出 / ## Output」三个章节
    3. 校验命名：contract-review、pia-generation、skill-search-browse 这类写法为正确，ContractReview、contract_review、contract.review 判为错误
    4. 检查描述质量：长度 50–200 字，能清晰说明功能；须包含功能描述和适用场景；不得含 TODO、PLACEHOLDER 等占位符
    5. 校验 plugin.json 插件级字段：name（kebab-case，与目录名一致）、version（MAJOR.MINOR.PATCH）、description（非空）、author（含 name 字段）、skills（数组，每个元素含 name、path、description）
    6. 校验每条技能注册条目：name 与 SKILL.md 中的 name 一致；path 相对插件根目录，且指向的 SKILL.md 必须存在，下级目录中的技能 path 须正确指向其 SKILL.md；_shared/ 下的共享文件不须注册在 skills 数组中
    7. 处理边界情形：SKILL.md 不存在 → 提示创建并提供骨架；plugin.json 不是合法 JSON → 报告解析错误位置、建议修复语法；技能名称冲突 → 提示已有同名技能、建议换名；描述为空 → 阻止发布、要求补充
    8. 新建技能可按规范生成 SKILL.md 骨架（frontmatter 含 name、description、argument-hint，正文含目的、前置、工作流、输出）；可自动修复的问题直接修复，其余列入须修复项
    9. 输出《技能清单校验报告》：SKILL.md 与 plugin.json 两张逐项结果表（通过 / 不通过并附说明）、综合结论三选一（全部通过 / 存在问题（可修复）/ 严重问题）和须修复项清单

    内置规则

    • 可自动修复：缺少 YAML frontmatter（生成基础 frontmatter）、命名不规范（转换为 kebab-case，须确认）、缺少章节（添加章节占位符）
    • 不可自动修复：路径不一致（须手动修复）、描述含占位符（须开发者补充）
    • 描述为空 → 阻止发布
    • plugin.json 的 name 须与目录名一致；技能注册条目的 name 须与 SKILL.md 的 name 一致；path 指向的文件须存在
    • description：必填结构要求不超过 200 字，描述质量要求 50–200 字
    • 本步骤可以读取并修改技能元数据文件

    法律依据

    • 平台技术规范 — SKILL.md/plugin.json 格式规范，作为元数据校验标准
    • 《著作权法》（2021年修正） — 技能命名和描述不侵犯他人著作权，用于命名冲突检查（原文未写条号）

    产出

    《技能清单校验报告》（SKILL.md 校验、plugin.json 校验、综合结论、须修复项）；需要时附 SKILL.md 骨架或经自动修复的元数据文件

  2. 版本发布管理

    /legal-builder-hub:version-release-management可单独运行

    管理技能版本的完整生命周期：按语义化版本（SemVer）确定版本号、生成变更日志、执行发布前检查与发布流程、做发布后验证，必要时撤销版本，确保版本可追溯、变更可回溯。

    请律师核对

    • 核对 2.1社区审核在本步骤是「等待社区投票」，在注册表查询与发布步骤是「公示期无异议」，通过条件须统一，投票门槛或公示期长度均未规定
    • 核对 2.2撤销版本须「通知已安装用户」，SKILL.md 未规定通知方式和时限
    • 核对 2.3版本发布的法律依据写为《著作权法》（2021年修正）「软件版本变更的权利义务」，未写条号，也未说明涉及哪些权利义务
    • 核对 2.4变更日志为空只警告、不阻止发布，含安全修复的版本是否应强制写明变更说明？

    做法

    1. 从 plugin.json 读取当前版本号，从 Git 提交历史或手动输入的变更说明获取变更内容，读取实践配置中的发布审核流程
    2. 按决策树确定升级类型：含不兼容的 API 变更 → MAJOR+1，MINOR、PATCH 归零；否则含新功能 → MINOR+1，PATCH 归零；否则 → PATCH+1；属预发布则添加或更新 pre-release 标识（如 1.0.0-alpha.1、1.0.0-beta.2），否则移除
    3. 生成变更日志：以「## [版本号] - [发布日期]」为标题，按新增、改进、修复、安全、废弃、依赖六类归类，条目关联 issue 编号，安全类附 CVE 编号
    4. 执行发布前检查清单五组：代码质量（变更已合并到发布分支、代码审查已通过、测试全部通过）；元数据（SKILL.md 通过清单校验、plugin.json 版本号已更新、变更日志已生成）；安全审查（已通过，审查报告编号已记录）；依赖（版本冲突已解决、许可证兼容性已确认）；文档（README.md 和技能描述按需更新）
    5. 发布流程步骤一 版本升级：确认变更类型，更新 plugin.json 的 version 字段，生成变更日志条目，提交版本变更
    6. 步骤二 发布审核：按配置执行——自动审核（通过检查清单后自动发布）、人工审核（提交审核请求，等待审核员批准）、社区审核（发布到社区，等待社区投票）
    7. 步骤三 执行发布：创建 Git 版本标签、打包发布产物、推送到注册表（转注册表查询与发布步骤）、记录发布日志
    8. 步骤四 发布后验证：逐项确认注册表记录、下载测试、安装测试、基础功能四项
    9. 版本撤销：已发布版本有严重问题时，在注册表标注「已撤销」、记录撤销原因、通知已安装用户、建议升级到修复版本

    内置规则

    • 版本号格式：MAJOR.MINOR.PATCH[-pre-release][+build-metadata]
    • MAJOR 表示不兼容的 API 变更（1.0.0 → 2.0.0）；MINOR 表示向后兼容的功能新增（1.0.0 → 1.1.0）；PATCH 表示向后兼容的问题修复（1.0.0 → 1.0.1）
    • 已发布版本不可覆盖，只能撤销后发布新版本号
    • 版本号已被使用 → 阻止发布，建议使用更高版本号
    • 安全审查未通过 → 阻止发布，建议先完成安全审查
    • 变更日志为空 → 警告但不阻止，建议补充变更说明
    • 发布到远程注册表失败 → 重试，并保留本地发布记录

    法律依据

    • 平台技术规范 — 语义化版本规范，用于版本号管理
    • 《著作权法》（2021年修正） — 软件版本变更的权利义务，用于版本发布（原文未写条号）

    产出

    更新后的 plugin.json 版本号、变更日志条目、发布前检查清单、Git 版本标签与发布产物、发布日志与发布验证表；撤销时另有撤销记录

  3. 依赖解析

    /legal-builder-hub:dependency-resolution可单独运行

    解析技能的依赖关系树，检测版本冲突和循环依赖，核对依赖项的兼容性、许可证一致性和安全状态，生成依赖报告和依赖图，确保依赖完整、可解析、无冲突。

    请律师核对

    • 核对 3.1许可证兼容性只举了 MIT、Apache 2.0（兼容）和 GPL（传染性，须确认主技能许可证）三例，没有完整的判断规则，其他许可证如何判断有待律师补充
    • 核对 3.2依赖项存在已知漏洞时只标警示（示例为低危 CVE），SKILL.md 未规定何种漏洞等级会阻止发布
    • 核对 3.3总流程写依赖「不使用精确版本锁定」，本步骤写「不推荐」，是强制要求还是建议须统一

    做法

    1. 读取 plugin.json 中的依赖声明，连接注册表获取依赖项的版本信息，读取实践配置中的注册表类型
    2. 按四类识别依赖：技能依赖（如依赖 contract-review 的合同解析能力）、库依赖（第三方库或工具，如 Python 库、Node.js 包）、平台依赖（如需要平台 API v2.0+）、数据依赖（如法律法规数据库连接）
    3. 解读版本范围：^1.2.3 为兼容 1.2.3 及以上（<2.0.0）；~1.2.3 为兼容 1.2.x 及以上（<1.3.0）；>=1.0.0 <2.0.0 为明确范围；* 为任意版本（不推荐）
    4. 步骤一 构建依赖树：逐层写出每个依赖的版本要求与解析版本，标出被多个依赖共享的下级依赖，统计直接依赖与传递依赖数量
    5. 步骤二 版本冲突检测：同一依赖被多个来源要求时，列出各来源的版本要求与解析结果，判断是否兼容
    6. 步骤三 循环依赖检测：出现 A → B → C → A 这类闭环即判为检测到循环依赖
    7. 步骤四 许可证兼容性：逐项列出依赖项许可证与主技能的兼容性，示例中 MIT、Apache 2.0 为兼容，GPL 标「传染性」、须确认主技能许可证
    8. 步骤五 依赖安全状态：列出各依赖版本的已知漏洞（CVE 编号及等级）与安全状态
    9. 冲突解决：约束可兼容时选满足所有约束的最高版本；约束较紧时选最少数量的版本满足所有约束；自动解决失败时展示冲突详情，由用户决定
    10. 输出《依赖解析报告》：解析摘要（直接依赖、传递依赖、版本冲突、是否循环、许可证风险、安全漏洞六项指标）、综合结论三选一（依赖可解析 / 存在冲突或风险 / 不可解析）及须处理项

    内置规则

    • 依赖版本须使用范围声明，不推荐精确版本锁定；* 任意版本不推荐
    • 依赖项不在注册表中 → 标注缺失，建议手动指定路径
    • 版本约束不可满足 → 报告冲突详情，建议调整版本约束
    • 依赖树过深（>5 层）→ 警告性能风险，建议扁平化
    • 注册表不可达 → 使用本地缓存，并标注缓存可能过期
    • 本步骤只出依赖解析报告，不修改依赖项

    法律依据

    • 《著作权法》（2021年修正） — 开源许可证法律效力，用于许可证兼容性（原文未写条号）
    • 平台技术规范 — 依赖声明格式规范，用于依赖声明校验

    产出

    《依赖解析报告》：依赖树、冲突检测表、循环依赖检测结果、许可证兼容性表、依赖安全状态表、解析摘要、综合结论与须处理项

  4. 注册表查询与发布

    /legal-builder-hub:registry-search-publish可单独运行

    在技能注册表中查询技能的元数据和版本信息；把新版本发布到注册表，并管理审核流程、发布状态以及撤销与废弃。

    请律师核对

    • 核对 4.1注册表类型对比表写本地注册表「安全审查建议但非强制」，与总流程「发布前须确保技能已通过安全审查」和本步骤发布前检查的「安全审查已通过」相冲突，本地注册表是否豁免须明确
    • 核对 4.2以《著作权法》确认「发布权利」，但发布前检查的六项中没有核对发布者权利或技能许可证声明的项目
    • 核对 4.3收集开发者信息引用《个人信息保护法》第13条，但 SKILL.md 未列明收集哪些信息、依据哪一项合法性基础、保存多久
    • 核对 4.4社区审核以「公示期无异议」为通过条件，公示期长度和异议处理程序均未规定

    做法

    1. 读取实践配置中的注册表类型、注册表地址、发布审核流程和用户角色，按注册表类型连接本地或远程注册表
    2. 查询：可按名称（精确或模糊）、法律领域、版本（如 contract-review@1.2.0）、安全审查状态（如仅显示已审查通过的技能）、许可证、作者、依赖关系（如哪些技能依赖 legal-search）七个维度检索；结果表列技能名称、最新版本、安全状态、许可证、发布时间
    3. 发布前逐项确认六个条件：SKILL.md 通过规范校验、版本号符合 SemVer、安全审查已通过、依赖关系可解析、变更日志已生成、用户有发布权限
    4. 按五步发布：上传技能包 → 把技能元数据写入注册表索引 → 关联安全审查报告编号 → 按发布审核流程审核（如需要）→ 发布确认通知
    5. 按配置的审核流程决定能否发布：自动审核（所有前检查项通过即发布）、人工审核（审核员批准）、社区审核（发布到社区公示期，公示期无异议）
    6. 输出发布结果：技能包上传、元数据注册、安全状态关联、审核状态（自动通过 / 待审核 / 已批准）、发布状态（已发布 / 待审核 / 发布失败），并给出查询地址和安装命令 /legal-builder-hub:installation-execution [名称]@[版本]
    7. 管理状态流转：开发中 → 待审核 → 审核中 → 已批准或已拒绝 → 已发布或重新提交；已发布的可转为已撤销（发现问题时）或已废弃（不再维护时）
    8. 撤销版本：标注「已撤销」、记录原因、通知已安装用户，不影响历史审计记录；废弃技能：标注「已废弃」、记录原因和建议替代方案、在搜索结果中标注废弃状态、不再接受新安装（已安装的可继续使用）
    9. 处理边界情形：注册表不可达 → 提示检查网络和配置并给出离线操作建议；版本号已存在 → 阻止发布、建议使用更高版本号；发布权限不足 → 提示联系注册表管理员；审核被拒绝 → 展示拒绝原因并给出修改建议；技能名称已被占用 → 提示冲突、建议换名

    内置规则

    • 本地注册表：仅本地访问，无审核要求，安全审查建议但非强制，版本自主管理
    • 组织内部注册表：组织内部访问，审核要求由组织自定义，通常要求安全审查，版本由组织管理
    • 公共社区注册表：公开访问，社区审核，强制要求安全审查，版本由平台管理
    • 版本号已存在 → 阻止发布
    • 废弃技能不再接受新安装，已安装的可继续使用；撤销不影响历史审计记录
    • 发布操作时本步骤可修改注册表数据

    法律依据

    • 《著作权法》（2021年修正） — 软件作品发布权利，用于发布权利确认（原文未写条号）
    • 《个人信息保护法》（2021年）第13条 — 注册表收集开发者信息须有合法性基础
    • 平台技术规范 — 发布流程规范，作为发布操作标准

    产出

    注册表查询结果表；发布结果（各环节状态、查询地址、安装命令）；发布状态表；撤销或废弃记录

09何时暂停或升级

  • 安全审查未通过 → 阻止发布，先完成 /legal-builder-hub:security-review
  • 版本号已被使用 → 阻止发布，改用更高版本号
  • 描述为空 → 阻止发布，要求补充描述；技能名称已被占用 → 提示冲突，建议换名
  • 发布权限不足 → 提示联系注册表管理员获取权限
  • 人工审核 → 提交审核请求，等待审核员批准；审核被拒绝 → 展示拒绝原因并给出修改建议
  • 依赖冲突自动解决失败 → 展示冲突详情，由用户决定；版本约束不可满足 → 建议调整约束
  • 已发布版本存在严重问题 → 标注已撤销、记录原因、通知已安装用户、建议升级到修复版本
  • 注册表不可达 → 依赖解析改用本地缓存并标注可能过期；发布失败则重试并保留本地发布记录，并给出离线操作建议
  • 配置缺失或为 PLACEHOLDER → 临时模式（本地注册表、人工审核），建议运行 /legal-builder-hub:cold-start-interview
