01概要

通过四段结构化访谈，把使用者的组织与角色画像、技能管理与发现 / 安装偏好、注册表配置、安全审查级别与零容忍权限、风险等级与升级规则、报告风格与工作产物标题写入 legal-builder-hub/CLAUDE.md，完成法律技能中心实践档案的初始化；之后技能发现、安装、安全审查和注册表四个流程都从这份文件读取个性化设置。访谈按「身份与角色画像 → 偏好与范围 → 安全策略与升级 → 风格与资源」顺序进行，共 33 问（10 + 11 + 7 + 5），多数问题给出固定选项。每步先读取现有配置和实践配置契约的字段映射表，写入前以 markdown 代码块展示填充预览，确认后才写入，不另存独立文件；安全策略变更另记审计日志。四步各可单独触发，只更新对应章节；也可直接编辑配置文件；未完成访谈时可说「临时模式」，按默认值运行并在输出标 [临时模式]。

02适用与边界

适用场景

  • 首次使用法律技能中心，legal-builder-hub/CLAUDE.md 仍是带 [PLACEHOLDER] 的模板
  • 技能发现、安装等流程检测到配置缺失或含占位符，提示「运行冷启动访谈或说临时模式」时
  • 组织、角色、集成工具或安全策略发生较大变化，需要全量更新配置时重跑完整访谈
  • 只需更新某一部分：身份画像、技能偏好、安全策略、风格资源各自单独重跑对应步骤

不做什么

  • 不做技能搜索、安装、安全审查或注册表操作，只收集答案并写入配置
  • 不另存独立文件；legal-builder-hub/CLAUDE.md 是唯一真相来源
  • 完成标准只覆盖九章；「共享护栏」「事项工作区」「审查过的技能」三章不在访谈填充范围内
  • 不就算法备案、生成式 AI 服务合规等义务作出判断：只记录「是否为法律科技产品提供方」，并提示须额外关注（配置模板对此标 [待验证]）
  • 小改动不必重跑访谈，可直接编辑 legal-builder-hub/CLAUDE.md；但安全策略变更建议走访谈流程

04开始前

前置条件

  • 每步开始先读取 legal-builder-hub/CLAUDE.md，检查目标章节是否已有非占位符内容
  • 每步读取 legal-builder-hub/skills/_shared/practice-profile-schema.md 的字段映射表，确定每个答案写入哪个章节
  • 建议顺序：第 2 步在第 1 步之后；第 3 步在第 1、2 步之后；第 4 步在其他三步之后
  • legal-builder-hub/CLAUDE.md 纳入 git 版本控制

硬性规则

唯一真相来源
访谈结果只填充 legal-builder-hub/CLAUDE.md 对应章节（散文形式），不另存独立文件；所有技能中心流程从此文件读取配置
确认前展示预览
每步写入前以 markdown 代码块展示填充结果，确认后才写入
安全策略为高敏感配置
第 3 步写入的安全策略变更须记录审计日志；用户可直接编辑，但安全策略变更建议通过访谈流程
部分更新互不干扰
单独触发某一步时只更新该步对应章节：身份 / 偏好 / 安全与风险 / 文书风格
临时模式
完整访谈前须立即使用其他流程时，可说「临时模式」：按默认值运行并在输出标 [临时模式]。入口列出六项默认值：整体技能管理偏好平衡型；用户角色技能使用者；安全审查级别标准审查；不允许安装未审查技能；推荐排序综合排序；注册表类型本地注册表。实践配置契约 §3.3 另列三项：技术背景「有编程经验的法律从业者」、安装前兼容性检查「强制」、自动更新「手动确认每次更新」
非技术人员模式
执业角色为非技术人员时，后续安装和安全审查操作提供详细步骤指导；配置模板另规定涉及安全审查结论时，建议升级给技术人员或安全专家确认

05执行步骤

共 4 步，按执行顺序。每步旁边（窄屏在步骤说明之后）是请律师核对的内置假设，可逐条复制。页面里的英文标记见首页「标记与术语」。

  1. 身份与角色画像访谈

    /legal-builder-hub:identity-role-profile可单独运行

    采集组织、行业、在技能中心的角色、技术背景、团队规模、是否为法律科技产品提供方、执业角色和可用集成，写入「我们是谁」「谁在使用」「可用集成」三章，使后续流程能按角色做功能路由和权限控制、按技术背景调整安装指导与报告深度、按执业角色选择工作产物标题。

    请律师核对

    • 核对 1.1Q3 与 Q8 两个角色问题的选项不一致：Q3 有「技能审核员」，Q8 没有；两者都没有「律师 / 法务」选项，而第 4 步按「法律角色（律师 / 法务）」分配工作产物标题——律师使用者应选哪一项？
    • 核对 1.2行业选项没有「法律服务」，而实体类型列有「律所」——律所应选「法律科技」还是「其他」？选「法律科技」会带上 [行业监管 flagged — 需核实主管部门规定] 标注。
    • 核对 1.3Q6 选「是」只提示关注算法备案、生成式 AI 合规（[待验证]），不追问产品形态——是否需要追问并记录，供安全审查流程使用？

    做法

    1. 读取 legal-builder-hub/CLAUDE.md，检查「我们是谁」是否已有非占位符内容；读取实践配置契约 §2.1 用户画像字段映射；本步产出是更新后的配置章节，不生成独立文件。
    2. Q1 组织 / 律所名称与实体类型（有限责任公司 / 股份有限公司 / 国有企业 / 律所 / 个人开发者 / 开源社区 / 其他）。
    3. Q2 所属行业（互联网/科技 / 金融 / 医疗健康 / 教育 / 法律科技 / 其他），并说明法律科技产品须额外关注行业监管。
    4. Q3 在技能中心的角色：技能开发者（开发和发布法律技能）/ 技能使用者（使用已发布的技能）/ 平台管理员（管理注册表和安全策略）/ 技能审核员（审查技能安全并出具报告）/ 多种角色兼有；此项影响功能路由和权限控制。
    5. Q4 技术背景（专业开发者 / 有编程经验的法律从业者 / 纯法律从业者 / IT 运维人员），影响安装指导详细程度和报告深度；Q5 团队规模（1-2人 / 3-5人 / 5-20人 / 20人以上）。
    6. Q6 是否为法律科技产品提供方（是 / 否），选「是」时提示须额外关注算法备案、生成式 AI 合规等；Q7 最大痛点（多选：找不到合适的技能 / 安装的技能不兼容 / 安全审查标准不清晰 / 技能更新管理困难 / 其他）。
    7. Q8 执业角色：技能开发者 / 技能使用者 / 平台管理员 / 非技术人员但有技术支持 / 非技术人员且无技术支持；若为非技术人员，告知安装和安全审查操作将提供详细步骤指导。Q9 如需技术支持联系谁。
    8. Q10 可用集成逐项标「已连接 / 未连接 / 不适用」：技能注册表服务、代码托管平台（GitHub/GitLab）、CI/CD 流水线、安全扫描工具、文档存储位置。
    9. 按映射表（Q1–Q7 → 我们是谁；Q8–Q9 → 谁在使用；Q10 → 可用集成）以 markdown 代码块展示填充预览，确认后写入 CLAUDE.md。

    内置规则

    • 「用户角色」（Q3）供所有流程做权限判断与功能路由；「执业角色」（Q8）供所有流程选择工作产物标题（契约 §2.1）
    • 「技术背景」（Q4）决定安装流程的指导详细程度和安全审查流程的报告深度；「团队规模」（Q5）供安装流程推荐部署方案
    • 「所属行业」（Q2）供技能发现做行业推荐、供安全审查确定行业合规要求；配置模板要求法律科技产品标 [行业监管 flagged — 需核实主管部门规定]
    • 选「是」法律科技产品提供方时，配置模板提示须额外关注算法备案义务、生成式 AI 服务合规、深度合成服务备案等 [待验证]
    • 集成未连接时核心功能仍可工作，只是需要手动指定技能路径、手动执行安全检查等（配置模板说明）
    • 本步只更新「我们是谁」「谁在使用」「可用集成」三章

    产出

    「我们是谁」（组织 / 律所名称与实体类型、所属行业、用户角色、技术背景、是否为法律科技产品提供方、团队规模、最大痛点）、「谁在使用」（角色、技术支持联系人）、「可用集成」（5 项状态）三章的 markdown 预览，确认后写入 legal-builder-hub/CLAUDE.md

  2. 偏好与范围访谈

    /legal-builder-hub:preference-scope可单独运行

    采集整体技能管理偏好、技能发现偏好、安装偏好和注册表配置，写入「技能偏好」（含技能发现偏好、安装与部署偏好）和「技能注册表」两章，驱动技能推荐、安装行为和注册表操作。

    请律师核对

    • 核对 2.1进取型为「快速试用社区技能，关键场景仍要求审查」，SKILL.md 未界定何为「关键场景」——是否应写明（如涉及客户文件、案件数据或个人信息的技能）？
    • 核对 2.2Q4 提供「下载量优先」，但推荐与排序步骤的四个排序维度里没有下载量——选这一项实际按什么排？
    • 核对 2.3Q11 可选「自动审核（通过安全审查即可发布）」——组织内部注册表是否接受无人工审核即发布？

    做法

    1. 读取 CLAUDE.md 检查偏好章节是否已有配置；读取实践配置契约字段映射（§2.2 技能偏好 / §2.4 安装偏好 / §2.8 注册表配置）；建议在第 1 步之后运行。
    2. Q1 整体技能管理偏好三选一：保守型（仅安装经过完整安全审查的技能，最高安全级别）/ 平衡型（安全审查与安装效率兼顾）/ 进取型（快速试用社区技能，关键场景仍要求审查）。
    3. Q2 关注的法律领域（多选）：商事合同 / 诉讼仲裁 / 劳动人事 / 数据合规 / 知识产权 / 监管合规 / AI 治理 / 建设工程 / 婚姻家事 / 刑事合规 / 法考培训 / 法律援助 / 全部领域。
    4. Q3 关注的能力类型（多选）：文书审查 / 文书起草 / 法规检索 / 案例分析 / 合规检查 / 期限管理 / 风险评估 / 培训训练 / 全部类型。
    5. Q4 推荐排序偏好：安全评级优先 / 社区评分优先 / 最近更新优先 / 下载量优先 / 综合排序；Q5 是否接受未审查技能出现在搜索结果中：是（标注未审查状态）/ 否（仅展示已审查技能）。
    6. Q6 默认安装位置：用户目录 .skills/ / 项目目录 .skills/ / 自定义路径；Q7 自动更新策略：自动更新（仅补丁版本）/ 自动更新（所有版本）/ 手动确认每次更新；Q8 安装前兼容性检查：强制 / 推荐 / 关闭。
    7. Q9 注册表类型：本地注册表 / 组织内部注册表 / 公共社区注册表；Q10 注册表地址（本地注册表无需填写）；Q11 发布审核流程：自动审核 / 人工审核 / 社区审核。
    8. 按映射表展示填充预览，确认后写入「技能偏好」与「技能注册表」两章。

    内置规则

    • Q1 整体偏好驱动所有流程的安全口径；在技能发现中，保守型默认只筛「已审查通过」的技能，进取型默认包含未审查技能
    • 去向：Q2 关注领域、Q4 排序偏好 → 推荐与排序；Q3 能力类型 → 分类·标签·筛选；Q5 未审查技能 → 搜索与浏览的结果过滤
    • 去向：Q6 安装位置 → 安装执行；Q7 更新策略 → 更新与卸载；Q8 兼容性检查 → 兼容性检查；Q9 注册表类型 → 技能注册表流程；Q10 地址 → 注册表查询与发布；Q11 发布审核 → 版本发布管理
    • 配置模板对三种发布审核方式的说明：自动审核（通过安全审查即可发布）/ 人工审核（须审核员批准）/ 社区审核（社区投票）
    • 法律领域 12 项、能力类型 8 项与技能发现流程「分类·标签·筛选」步骤的分类体系一致
    • 本步只更新偏好章节与注册表章节

    产出

    「技能偏好」（整体技能管理偏好；技能发现偏好四项；安装与部署偏好三项）与「技能注册表」（类型、地址、发布审核流程）的预览，确认后写入

  3. 安全策略与升级访谈

    /legal-builder-hub:security-escalation可单独运行

    采集安装前安全审查级别、是否允许安装未审查技能、敏感权限零容忍列表、数据隐私要求、风险等级定义和自动升级规则，写入「安全审查偏好」「风险校准」「升级矩阵」，驱动安全审查深度、风险标注和升级路由。

    请律师核对

    • 核对 3.1Q2 可选「是（标注风险后允许）」或「仅开发环境允许」，而安装流程把「未经安全审查的技能不得安装」定为不可绕过的硬性规则——两者冲突时以哪一个为准？
    • 核对 3.2「快速检查」只查权限范围、不做隐私评估，而 README 核心护栏要求「技能涉及敏感数据访问 → 强制数据隐私评估」——配置为快速检查时，访问案件文件的技能是否仍须做隐私评估？
    • 核对 3.3Q7 的升级联系人写入「角色权限表」，但该表只有「角色 / 可独立处理事项 / 需升级条件」三列，没有联系人栏——联系人写在哪里，SKILL.md 未规定。
    • 核对 3.4命中零容忍列表的权限（如「案件文件访问」）是否一律按红级处理，SKILL.md 未规定；零容忍列表与红级典型情形只有「读取全部文件系统」一项明确重合。

    做法

    1. 读取 CLAUDE.md 检查安全和风险章节是否已有配置；读取契约字段映射（§2.3 安全审查偏好 / §2.5 风险校准 / §2.6 升级矩阵）；建议在第 1、2 步之后运行。
    2. Q1 安装前安全审查级别三选一：完整审查（静态分析 + 权限审查 + 隐私评估，适用高风险技能）/ 标准审查（权限审查 + 隐私评估，适用一般技能）/ 快速检查（仅权限范围，适用低风险技能）。
    3. Q2 是否允许安装未经安全审查的技能：否（强制审查）/ 是（标注风险后允许）/ 仅开发环境允许。
    4. Q3 敏感权限零容忍列表（多选）：全部文件系统访问 / 命令执行 / 网络数据外传 / 用户对话数据访问 / 案件文件访问 / 个人信息访问 / 其他（请说明）。
