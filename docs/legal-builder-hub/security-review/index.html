01概要

在安装社区技能之前，对其做静态代码扫描、权限范围审查和数据隐私评估，汇总出具安全审查报告并给出「通过 / 有条件通过 / 未通过」的认证结论，作为能否安装的依据；核心原则是「安全审查是安装的前置条件，不可跳过」。流程先读取 legal-builder-hub/CLAUDE.md 中的审查级别、敏感权限零容忍列表、数据隐私要求、是否允许安装未审查技能、报告风格和用户角色，未配置时进入临时模式（标准审查；零容忍「全部文件系统访问 + 命令执行 + 数据外传」）。四个步骤依次为静态分析与代码扫描、权限范围审查、数据隐私评估、审查报告与认证，按审查级别取舍：完整审查 1+2+3+4，标准审查 2+3+4，快速检查 2+4（简化版）。发现按红级（关键）、橙级（高）、黄级（中等）、绿级（低/信息）四档标注；总流程把结论与安装决策对应为绿级通过（允许安装）、黄级有条件通过（修复并复核后安装）、橙级未通过（高风险，修复后重审）、红级未通过（严重风险，标记为不可信技能）。法律依据以《个人信息保护法》第13、28-29、38-39、55-56条，《数据安全法》第21条，《网络安全法》第21条为主，取自本插件引用库 skill-hub-citations.md。

02适用与边界

适用场景

  • 拟从社区或注册表安装一个法律技能（如 contract-review@1.2.0 或本地路径），安装前需要独立的安全审查
  • 已安装的技能发布了新版本：技能更新后原审查报告自动失效，须重新审查
  • 技能处理敏感数据、需要网络访问或文件系统访问——审查级别表把这类技能列为高风险，须完整审查
  • 技能准备发布到注册表：发布前检查要求安全审查已通过并记录审查报告编号
  • 只需要其中一项：代码扫描、权限核对、隐私合规评估，或根据已有审查结果出具报告与认证结论

不做什么

  • 不修改被审查技能：静态分析、权限审查、隐私评估三步都只出报告，不改源代码或技能代码
  • 不运行被审查代码：静态分析在不运行代码的前提下发现隐患
  • 不对混淆、压缩或加密的代码下确定结论：标注无法分析的部分，建议提供源代码版本
  • 快速检查模式不做静态分析和隐私评估，只出权限审查结论和简化版报告
  • 单独出具报告与认证结论时，至少要有一项前序审查结果，不凭空出具认证
  • 不负责安装、替换或查历史：审查通过后安装转 /legal-builder-hub:installation，替换问题技能转 /legal-builder-hub:skill-discovery，查看安全审查历史转 /legal-builder-hub:skill-registry

03输入与产出

需要律师提供

  • 待审查技能的名称与版本或本地路径（如 contract-review@1.2.0）必需
  • 技能的 SKILL.md（功能声明）和元数据中的权限清单必需
    权限审查逐项对照功能声明；未声明权限清单的直接标为橙级
  • 技能源代码与配置文件（代码路径或 Git 仓库地址）可选
    完整审查的静态分析步骤需要；标准审查和快速检查不执行该步骤
  • 隐私政策、数据处理声明可选
    如有则提供；没有隐私政策的标为橙级，并要求开发者提供隐私声明
  • legal-builder-hub/CLAUDE.md 实践配置（审查级别、敏感权限零容忍列表、数据隐私要求、是否允许安装未审查技能、报告风格、用户角色/技术背景）可选
    缺失或为 PLACEHOLDER 时进入临时模式，并建议运行 /legal-builder-hub:cold-start-interview
  • 前序审查结果（静态分析报告、权限审查报告、隐私评估报告）可选
    单独触发审查报告与认证时至少须有一项

产出

  • 静态分析扫描报告给审查员 / 技能开发者（修复用）
    扫描目标与版本、扫描日期、规则库版本、扫描文件数与代码行数；扫描摘要（红/橙/黄/绿级各几项）；发现清单（序号、风险等级、类别、文件:行号、描述、修复建议）；依赖项漏洞表（依赖项、当前版本、CVE 编号、风险等级、修复版本）
  • 权限审查报告给审查员 / 技能开发者
    权限清单（权限、请求原因、必要性：必要/不必要/超出、风险级别）；零容忍检查（是否触碰，列出触碰的权限）；越权分析（功能不需要的权限、权限范围过宽、未声明的权限）；结论三选一（权限合理 / 存在不必要权限 / 触碰零容忍或严重越权）与修复建议
  • 数据隐私评估报告给审查员 / 技能开发者
    数据流图与数据流清单（数据类型、来源、目的地、处理目的、是否个人信息）；评估摘要（数据收集、处理、存储、外传、用户权利五个维度，各给合规/部分合规/不合规（外传另有「无外传」）及风险等级）；发现清单（维度、发现、法律依据、风险等级、修复建议）；综合结论三选一（隐私合规 / 存在合规缺陷 / 严重隐私违规）与修复建议
  • 安全审查报告（含认证结论）给内部：安装决策与存档
    开头为审查者注（审查日期、技能及版本、审查范围、技能更新后须重新审查）；审查编号、技能名称与版本、审查日期、审查级别、审查员；正文七部分：一、审查摘要；二、发现汇总（含修复期限）；三、静态分析摘要；四、权限审查摘要（请求权限数、不必要权限数、是否触碰零容忍）；五、隐私评估摘要；六、认证结论（结论、安装建议、有条件通过的条件清单、有效期、复核要求）；七、法律依据；须保留至少 2 年备查

04开始前

前置条件

  • 读取 legal-builder-hub/CLAUDE.md 六项配置：安全审查级别（完整/标准/快速，决定审查深度和范围）、敏感权限零容忍列表（权限审查的硬性拒绝条件）、数据隐私要求（隐私评估的关注重点）、是否允许安装未审查技能（审查结论对安装的影响）、安全审查报告风格（报告格式）、用户角色/技术背景（报告详细程度和术语）
  • 配置缺失或为 PLACEHOLDER 时进入临时模式 [临时模式]：审查级别按标准审查（权限+隐私），零容忍权限按「全部文件系统访问 + 命令执行 + 数据外传」，并建议运行 /legal-builder-hub:cold-start-interview 完善配置
  • 确认审查独立：审查须独立于技能开发者进行，审查员不得审查自己开发的技能
  • 按审查级别确定执行哪些步骤，并备齐对应材料：源代码（完整审查）、SKILL.md 功能声明与权限清单、隐私政策与数据处理声明（如有）
  • 法条与标准引用按 legal-builder-hub/skills/_shared/legal-basis-conventions.md 的规范，条文取自 legal-builder-hub/skills/_shared/skill-hub-citations.md

硬性规则

安全审查是安装的前置条件
核心原则：安全审查是安装的前置条件，不可跳过；只有安全可靠的技能才能安装使用
审查独立性
安全审查须独立于技能开发者进行；审查员不得审查自己开发的技能（利益冲突回避）；审查过程和结论不受安装需求紧迫性影响
审查级别与步骤
完整审查 = 步骤 1+2+3+4，适用于高风险技能（处理敏感数据/网络访问/文件系统访问）；标准审查 = 步骤 2+3+4，适用于一般技能（文本处理/计算类）；快速检查 = 步骤 2+4（简化版），适用于低风险技能（纯提示词/模板类）
审查结论与安装决策
绿级通过 → 允许安装；黄级有条件通过 → 修复指定问题后允许安装（须复核）；橙级未通过（高风险）→ 不允许安装，须修复后重新审查；红级未通过（严重风险）→ 不允许安装，标记为不可信技能
审查报告保留与失效
安全审查报告须保留至少 2 年；报告内容包括审查日期、技能版本、审查范围、发现清单、修复建议、审查结论；技能更新后须重新审查，原审查报告自动失效
只出报告、不改代码
静态分析、权限审查、隐私评估三步的产出均为报告，不修改被审查技能的源代码或技能代码

05执行步骤

共 4 步，按执行顺序。每步旁边（窄屏在步骤说明之后）是请律师核对的内置假设，可逐条复制。页面里的英文标记见首页「标记与术语」。

  1. 静态分析与代码扫描

    /legal-builder-hub:static-analysis-scan可单独运行

    不运行代码，对技能源代码和配置文件做静态安全分析，找出恶意代码、硬编码密钥与凭证、不安全函数调用、已知漏洞依赖项和数据泄露隐患。

    请律师核对

    • 核对 1.1代码注入、命令注入、SQL 注入和日志输出敏感信息定为橙级；按审查报告与认证步骤的矩阵，静态分析出现任一橙级发现即为未通过、不允许安装，这一后果是否符合预期？
    • 核对 1.2允许用户把发现标记为误报，SKILL.md 未规定谁有权标记、是否须审查员确认，与审查独立性要求如何衔接？
    • 核对 1.3依赖项许可证与主项目不兼容只定为黄级（中等），不会单独导致未通过，这一定级是否合适？
    • 核对 1.4《网络安全法》（2017年）第21条在本步骤被概括为「网络安全漏洞管理」，总流程和引用库概括为「网络安全等级保护」，请核对条文并统一概括
    • 核对 1.5扫描超时只扫核心文件并标注未扫描部分，SKILL.md 未规定未扫描部分对认证结论的影响

    做法

    1. 获取技能源代码（代码路径或 Git 仓库地址），读取实践配置中的安全审查级别和敏感权限零容忍列表
    2. 加载扫描规则：OWASP Top 10（Web 应用安全风险）、平台安全规则（技能清单特有的安全规则）、密钥扫描、依赖漏洞（已知 CVE）默认启用；用户自定义规则默认不启用
    3. 恶意代码模式检测：后门/木马（远程代码执行、反向连接、隐蔽通信通道）、数据窃取（未经授权的数据收集和发送、隐蔽数据编码）、系统破坏（文件系统破坏、注册表修改、系统进程操控）、权限提升（未授权的权限请求、安全绕过尝试）
    4. 硬编码密钥与凭证扫描：硬编码的 API 密钥/Token/Secret、数据库连接串与用户名/密码、加密密钥与私钥文件、云服务凭证与 OAuth 客户端密钥
    5. 不安全函数调用识别：代码注入（eval()、动态代码执行、模板注入）、命令注入（不安全的系统命令执行、shell 调用）、SQL 注入（未参数化的查询）、路径遍历（不安全的文件路径拼接）、不安全的反序列化
    6. 依赖项检查：有 CVE 记录的严重漏洞、版本过旧可能有未修复漏洞的过时依赖、已不再维护的废弃依赖、许可证与主项目不兼容
    7. 数据泄露风险检查：日志中输出敏感信息、错误消息含敏感信息、代码注释含敏感信息、临时文件未及时清理
    8. 处理无法完整扫描的情形：混淆/压缩代码标注无法分析的代码段并建议提供源代码版本；扫描超时优先扫描核心文件并标注未扫描部分；加密文件标注无法分析；对发现标注置信度，允许用户标记为误报
    9. 按模板输出扫描报告：扫描摘要按四档风险计数，发现清单定位到「文件:行号」并附修复建议，依赖项漏洞单列 CVE 编号与修复版本

    内置规则

    • 风险等级四档：红级（关键）/ 橙级（高）/ 黄级（中等）/ 绿级（低/信息）
    • 红级：恶意代码四类（后门/木马、数据窃取、系统破坏、权限提升）；硬编码的 API 密钥、数据库凭证、加密密钥
    • 橙级：硬编码的云服务凭证与 OAuth 客户端密钥；代码注入、命令注入、SQL 注入；日志输出敏感信息
    • 黄级：路径遍历、不安全的反序列化；过时依赖、废弃依赖、依赖许可证与主项目不兼容；错误信息或注释中含敏感信息、临时文件未清理
    • 依赖项有 CVE 记录的严重漏洞定为红级或橙级
    • 规则库更新：每年 OWASP 发布更新时同步更新 OWASP Top 10 规则；定期同步国家信息安全漏洞库（CNNVD）和国际 CVE 数据库；平台规则随平台技术规范版本迭代更新；用户自定义规则须定期审查有效性
    • 只出扫描报告，不修改源代码

    法律依据

    • 《网络安全法》（2017年）第21条 — 本步骤概括为「网络安全漏洞管理」，用于漏洞检测
    • 《数据安全法》（2021年）第21条 — 本步骤概括为「数据安全保护义务」，用于数据泄露风险
    • GB/T 22239 [待验证] — 等保安全要求，用于安全技术检查

    产出

    《静态分析扫描报告》：扫描目标与版本、扫描日期、规则库版本、扫描文件数与代码行数；扫描摘要（四档计数）；发现清单（风险等级、类别、文件:行号、描述、修复建议）；依赖项漏洞表（依赖项、当前版本、漏洞编号、风险等级、修复版本）

  2. 权限范围审查

    /legal-builder-hub:permission-scope-review可单独运行

    对照技能声明的功能，逐项判断其请求的权限是否必要（最小权限原则），检查是否触碰用户配置的敏感权限零容忍列表，输出权限审查报告。

    请律师核对

    • 核对 2.1读取用户提供的法律文件（file:read-user）定为橙级，访问案件文件（data:case-files）定为红级，两者在律所场景下的界线如何划分，SKILL.md 未说明
    • 核对 2.2临时模式把「全部文件系统访问」列入零容忍；若按字面适用，需要读取合同文件的审查类技能在未配置时一律不可安装，是否合适？
    • 核对 2.3「严重越权」没有定义，只给了跨境发送和执行系统命令两个超出需要的示例；它与「存在不必要权限（可裁剪）」的分界决定认证结论是未通过还是有条件通过
    • 核对 2.4敏感权限须用户逐一审批，SKILL.md 未规定审批由谁作出、记录如何保存

    做法

    1. 从 SKILL.md 提取技能的功能声明，从技能元数据提取请求的权限清单，读取实践配置中的敏感权限零容忍列表和安全审查级别
    2. 步骤一 权限清单提取：逐项列出权限标识、技能声明的请求原因和权限级别
    3. 按六级权限分类确定审查要求：基础权限（读取技能自身文件、执行基本计算）默认允许；文件权限（读写用户文件系统）须说明具体路径和原因；网络权限须说明目标地址和目的；系统权限（执行系统命令、访问系统资源）须充分理由、默认拒绝；数据权限（对话/文件/案件）须说明数据类型和处理目的；敏感权限（身份/财务/法律文件）须单独声明、用户逐一审批
    4. 对照常见权限清单定风险：file:read（读取技能配置文件）为基础，file:write（生成输出文件）为中等；file:read-user（读取用户提供的法律文件）、network:outbound（调用外部 API）、data:conversation（读取用户与 AI 的对话）为橙级；file:write-system、network:outbound-legal（将案件数据发送至外部服务）、system:execute、data:case-files、data:personal-info 为红级
    5. 步骤二 最小权限检查：把每项权限对应到声明的功能，判断必要或超出需要并写明理由；原文示例中，读取合同文件、调用法规数据库 API 为必要，功能描述中无跨境需求却请求向境外服务器发送分析结果、未说明原因却请求执行系统命令，均判为超出需要
    6. 步骤三 零容忍检查：逐项对照实践配置中的零容忍列表，技能请求了列表中的权限即判为红级「触碰零容忍 — 不可安装」
    7. 步骤四 综合评估：按红级（零容忍触碰/严重越权）、橙级（不必要的高风险权限）、黄级（权限声明不完整）、绿级（权限范围合理）计数
    8. 处理边界情形：未声明权限清单标橙级，建议开发者补充权限声明；权限描述模糊标黄级，要求明确使用场景；运行时动态请求权限标橙级，须在声明中列出所有可能的权限请求；权限随配置变化的，标注各配置下的权限范围
    9. 出具权限审查报告：权限清单、零容忍检查、越权分析（功能不需要的权限、权限范围过宽、未声明的权限）、三选一结论和修复建议

    内置规则

    • 系统权限默认拒绝；敏感权限（身份/财务/法律文件）须单独声明并由用户逐一审批
    • 红级权限五项：写入系统文件、向外部发送法律数据、执行系统命令、访问案件文件、访问个人信息
    • 橙级权限三项：读取用户文件、网络出站、访问对话内容
    • 触碰零容忍列表 → 红级，结论为不可安装
    • 结论三选一：权限合理 / 存在不必要权限 / 触碰零容忍或严重越权
    • 只出权限审查报告，不修改技能代码

    法律依据

    • 《个人信息保护法》（2021年）第13条 — 数据处理须有合法性基础，用于数据访问权限审查
    • 《个人信息保护法》（2021年）第28-29条 — 敏感个人信息须单独同意，用于敏感数据权限审查
    • GB/T 35273 [待验证] — 个人信息最小必要原则，用于权限最小化审查

    产出

    《权限审查报告》：技能与审查日期；权限清单（请求原因、必要性、风险级别）；零容忍检查（是否触碰及触碰项）；越权分析；结论（权限合理 / 存在不必要权限 / 触碰零容忍或严重越权）与修复建议

  3. 数据隐私评估

    /legal-builder-hub:data-privacy-assessment可单独运行

    评估技能运行中的数据处理行为是否符合《个人信息保护法》《数据安全法》：收集范围、处理目的和方式、存储与保留、外传行为、用户权利保障。

    请律师核对

    • 核对 3.1标准审查不做静态分析，而本步骤判断数据外传、推断数据流向要用静态分析的线索；在标准审查下，外传结论实际只能依据开发者的声明
    • 核对 3.2SKILL.md 未规定技能开发者、律所、平台中谁是个人信息处理者，合法性基础和 PIA 义务的归属随之不确定
    • 核对 3.3法律依据表列了 PIPL 第55-56条（PIA 义务），但五个评估维度中没有「是否已开展 PIA」的检查项
    • 核对 3.4维度结论（合规/部分合规/不合规）如何对应认证矩阵的「存在合规缺陷（可修复）」与「严重隐私违规」，SKILL.md 未给出划分标准；评估只按个人信息与数据安全框架展开，未涉及案件材料的保密要求

    做法

    1. 收集技能文档（SKILL.md、隐私政策和数据处理声明，如有），调取静态分析步骤的数据流线索和权限审查步骤的权限范围，读取实践配置中的数据隐私要求和零容忍列表
    2. 画数据流图（用户输入 → 数据收集 → 数据处理 → 输出结果，旁支为数据存储和数据外传，外传再标接收方及是否跨境），并列数据流清单：数据类型、来源、目的地、处理目的、是否个人信息
    3. 数据收集评估：须明确声明收集的数据类型；目的须具体、明确、合理；仅收集实现功能所必需的数据；合法性基础须为 PIPL 第13条七类基础之一（已核实）
    4. 数据处理评估：处理方式须与声明目的相符，不得超出声明的处理范围；用数据做自动化决策的，按 PIPL 第24条审查透明度和公平性（已核实）；处理敏感个人信息的，按 PIPL 第28-29条审查单独同意（已核实）
    5. 数据存储评估：须声明存储位置（本地/云端/第三方）和保留期限，到期须删除；检查加密、访问控制、审计日志；CIIO 和达量处理者须境内存储（PIPL 第40条，已核实）
    6. 数据外传评估：须明确声明外传行为和目标、接收方身份，外传目的须具体、合理；涉及跨境传输的，按 PIPL 第38-39条审查合规路径和单独同意（已核实）
    7. 用户权利评估：知情权（PIPL 第44条）、查阅/复制权（第45条）、更正权（第46条）、删除权（第47条）、撤回同意（第14条），原文均标已核实
    8. 处理边界情形：无隐私政策标橙级，须要求开发者提供隐私声明；数据流向不明确时结合静态分析结果推断并标注不确定项；使用第三方 SDK 的须评估 SDK 的数据处理行为；加密传输仍须评估接收方合规性
    9. 出具数据隐私评估报告：五个维度逐项给出合规/部分合规/不合规（外传维度可为「无外传」）和风险等级，发现清单逐条附法律依据与修复建议，综合结论三选一

    内置规则

    • 合法性基础须落在 PIPL 第13条七类之一；同意可撤回（第14条）
    • 最小必要：只收集实现功能所必需的数据
    • 保留期限须声明，到期须删除
    • 跨境传输须走合规路径并取得单独同意（PIPL 第38-39条）
    • 无隐私政策 → 橙级
    • 加密传输不免除对接收方合规性的评估；第三方 SDK 的数据处理一并评估
    • 综合结论三选一：隐私合规 / 存在合规缺陷 / 严重隐私违规

    法律依据

    • 《个人信息保护法》（2021年）第13-14条 — 合法性基础与同意规则，用于数据收集合法性与撤回同意
    • 《个人信息保护法》（2021年）第24条 — 自动化决策须保证透明度和公平性（已核实）
    • 《个人信息保护法》（2021年）第28-29条 — 敏感个人信息保护，须单独同意
    • 《个人信息保护法》（2021年）第38-39条 — 跨境提供合规路径与单独同意
    • 《个人信息保护法》（2021年）第40条 — CIIO 和达量处理者须境内存储（已核实）
    • 《个人信息保护法》（2021年）第44-47条 — 知情、查阅/复制、更正、删除等个人权利
    • 《个人信息保护法》（2021年）第55-56条 — PIA 义务，用于影响评估
    • 《数据安全法》（2021年）第21条 — 数据分类分级，用于数据分级评估

    产出

    《数据隐私评估报告》：数据流图与数据流清单；五个维度的评估摘要；发现清单（维度、发现、法律依据、风险等级、修复建议）；综合结论（隐私合规 / 存在合规缺陷 / 严重隐私违规）与修复建议

  4. 审查报告与认证

    /legal-builder-hub:review-report-certification可单独运行

    汇总前三步的审查结果，出具完整的安全审查报告，给出「通过 / 有条件通过 / 未通过」的认证结论，作为安装决策的依据。

    请律师核对

    • 核对 4.1本步骤的综合结论只有三档，总流程却是四档（另有橙级未通过（高风险）、红级未通过（严重风险）并「标记为不可信技能」）；本步骤未规定何时标记不可信技能
    • 核对 4.2综合结论「通过」要求三个维度均为通过；标准审查没有静态分析、快速检查只有权限审查，SKILL.md 未规定未审查的维度如何计入综合结论
    • 核对 4.3报告模板只写「审查员：[角色/人员]」，未要求由人签发；模型出具的认证结论是否须经人工审查员确认后才能作为安装依据？
    • 核对 4.4审查者注固定写「审查范围包括：静态代码分析、权限范围评估、数据隐私影响评估」，标准审查和快速检查并未执行全部步骤，措辞是否应按实际级别调整？
    • 核对 4.5报告保留期「至少 2 年」，SKILL.md 未给出依据

    做法

    1. 确认至少有一项前序审查结果（静态分析报告、权限审查报告、隐私评估报告），读取实践配置中的安全审查报告风格、风险等级定义和用户角色
    2. 按认证结论矩阵逐维度定性：静态分析——无红级/橙级发现为通过，仅有黄级发现且有修复方案为有条件通过，存在红级/橙级发现为未通过；权限审查——范围合理、无越权为通过，存在可裁剪的不必要权限为有条件通过，触碰零容忍或严重越权为未通过；隐私评估——合规为通过，存在可修复的合规缺陷为有条件通过，严重隐私违规为未通过
    3. 合成综合结论：三个维度均为通过 → 绿级通过，允许安装；没有未通过维度、但有附明确修复方案的有条件通过项 → 黄级有条件通过，修复指定问题并复核后允许安装；任一维度未通过 → 红级未通过，不允许安装，须修复后重新审查
    4. 按模板写报告：开头为审查者注，列审查编号、技能名称与版本、审查日期、审查级别、审查员；正文七部分为审查摘要、发现汇总（含修复期限）、静态分析摘要、权限审查摘要、隐私评估摘要、认证结论、法律依据，各摘要引用对应步骤的报告编号
    5. 认证结论部分写明安装建议（允许安装 / 修复后允许安装 / 不允许安装）、有条件通过须修复的条件清单、有效期（仅在技能代码未变更时有效）和复核要求（修复后须由审查员复核确认）
    6. 处理边界情形：前序审查不完整 → 只基于已有结果出报告并标注未审查维度；快速检查模式 → 只出权限审查结论和简化版报告；结论有争议 → 标注争议项，建议由更高级别审查员复核；审查后发现新问题 → 出具补充审查报告，原报告标注「补充」
    7. 归档管理：至少保留 2 年，存放于实践配置的工作产物存放位置，与技能版本号绑定，技能代码变更（任何版本更新）即失效，报告出具、变更、撤销均记录审计追踪

    内置规则

    • 综合结论三档：绿级通过（三个维度均通过）/ 黄级有条件通过（无未通过、有可修复项）/ 红级未通过（任一维度未通过）
    • 静态分析出现任何红级或橙级发现，该维度即为未通过
    • 有条件通过须有明确修复方案，修复后须由审查员复核确认
    • 报告只在技能代码未变更时有效，任何版本更新即失效
    • 报告保留至少 2 年；出具、变更、撤销均须记录

    法律依据

    • 《网络安全法》（2017年）第21条 — 本步骤概括为「安全审查义务」，用于出具安全审查报告
    • 《数据安全法》（2021年）第21条 — 本步骤概括为「数据安全评估」，用于数据安全评估结论
    • 平台技术规范 — 安全审查标准的适用
    • 《个人信息保护法》（2021年）第13-14条、第28-29条、第38-39条、第55-56条 — 报告模板第七部分按维度列明：数据收集合法性、敏感个人信息、跨境数据、PIA 义务

    产出

    《安全审查报告》（含认证结论、安装建议、有条件通过的条件清单、有效期与复核要求），保留至少 2 年备查；有新问题时另出补充审查报告

08交付前检查

  • 报告载明审查日期、技能版本、审查范围、发现清单、修复建议、审查结论（总流程规定的必备内容）
  • 静态分析的每项发现定位到「文件:行号」并附修复建议；依赖项漏洞列明 CVE 编号与修复版本；扫描规则库版本已写明
  • 无法分析（混淆、压缩、加密）或因超时未扫描的部分已标注；可能误报的发现已标注置信度
  • 每项权限写明请求原因和必要性分析；零容忍列表已逐项对照；越权分析覆盖不需要的权限、范围过宽和未声明的权限
  • 隐私评估五个维度都有结论和风险等级，发现逐条附法律依据；数据流向不明确的不确定项已标注
  • 综合结论与认证矩阵一致；有条件通过列明须修复的条件和修复期限，并写明复核要求与有效期
  • 前序审查不完整时，报告已标注未审查的维度
  • 报告与技能版本号绑定，按实践配置的工作产物存放位置保存

09何时暂停或升级

  • 审查员是被审查技能的开发者 → 回避，不得审查自己开发的技能；审查结论不受安装需求紧迫性影响
  • 审查结论有争议 → 标注争议项，建议由更高级别审查员复核
  • 触碰敏感权限零容忍列表 → 红级，结论为不可安装
  • 综合结论为未通过 → 不允许安装，须修复后重新审查；总流程把严重风险的技能标记为不可信技能
  • 有条件通过 → 修复指定问题后须由审查员复核确认，方可安装
  • 审查后发现新问题 → 出具补充审查报告，原报告标注「补充」
  • 技能更新（任何版本）→ 原审查报告失效，须重新审查
  • 代码混淆/压缩或加密无法分析 → 标注并建议开发者提供源代码版本
  • 无隐私政策 → 要求开发者提供隐私声明；未声明权限清单 → 建议开发者补充；权限描述模糊 → 要求开发者明确使用场景
  • 配置缺失或为 PLACEHOLDER → 临时模式，建议运行 /legal-builder-hub:cold-start-interview

  2. 快速检查的范围三处写法不一：总流程说明写「快速检查模式可跳过步骤 1，仅执行步骤 2-4」，审查级别表写「步骤 2+4（简化版）」（2+3+4 是标准审查），实践配置文件模板写「快速检查（仅权限范围）」，须统一。
  3. 结论分级前后不一：总流程为四档（橙级未通过（高风险）须修复后重审，红级未通过（严重风险）标记为不可信技能），审查报告与认证步骤只有三档，且未规定何时标记「不可信技能」。是否保留四档？相关批注：核对 4.1
  4. 综合结论「通过」要求三个维度均为通过，但标准审查没有静态分析、快速检查只有权限审查；SKILL.md 未规定未审查的维度如何计入综合结论，也未规定快速检查能否得出「通过」并据此安装。相关批注：核对 4.2
  5. 临时模式的零容忍列表含「全部文件系统访问」，而读取用户提供的法律文件（file:read-user）正是合同审查类技能的典型权限；若按字面执行，这类技能在未配置时一律不可安装。这一默认是否合适？相关批注：核对 2.2
  6. 权限定级：读取用户提供的法律文件、调用外部 API、读取对话内容为橙级；访问案件文件、访问个人信息、向外部发送法律数据、执行系统命令、写入系统文件为红级。读取用户法律文件与访问案件文件的界线如何划，这一分档是否符合贵所对案件材料的保密要求？
  7. 三个维度的尺度不一：静态分析只要出现一项橙级发现（如一处未参数化的 SQL 查询、一处日志输出敏感信息）即判未通过、不允许安装；权限和隐私维度则以「可裁剪」「可修复」区分有条件通过。是否同意？
  8. 安全审查报告保留期为「至少 2 年」，SKILL.md 未给出依据；本插件引用库对《个人信息保护法》第56条的摘要是 PIA 报告和处理情况记录至少保存三年。若把数据隐私评估当作 PIA 使用，2 年是否不足？相关批注：核对 4.5
  9. 审查独立性要求审查员不得审查自己开发的技能，但报告模板只写「审查员：[角色/人员]」；SKILL.md 未规定模型出具的认证结论是否须经人工审查员确认或签发，也未规定谁有权把扫描发现标记为误报。相关批注：核对 4.3、核对 1.2
  10. 四个审查维度只覆盖代码、权限和数据处理；SKILL.md 未规定审查被安装技能的法律内容（法条是否现行、引用是否准确、判断是否可靠），律所安装法律技能时是否应增设这一维度？
  11. 《网络安全法》（2017年）第21条在三处被概括为三种规则：总流程为「网络安全等级保护」，静态分析步骤为「网络安全漏洞管理」，报告与认证步骤为「安全审查义务」。请核对条文并统一概括。相关批注：核对 1.4
  12. 数据隐私评估以《个人信息保护法》框架评估技能，但 SKILL.md 未规定技能开发者、律所、平台中谁是个人信息处理者，合法性基础和 PIA 义务归谁随之不定；评估也未涉及案件材料的保密要求。相关批注：核对 3.2
