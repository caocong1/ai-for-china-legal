01概要

通过四段结构化访谈，把数据处理者画像、合规立场、风险等级与升级规则、文书风格与行业监管偏好写入 data-compliance/CLAUDE.md，完成数据合规实践档案的初始化；之后 PIA、出境评估、数据安全与网络安全合规检查四条流程都从这份文件读取个性化设置。访谈按「身份与团队 → 合规立场 → 风险与升级 → 文书风格与行业监管」顺序进行，每步先读取现有配置检查目标章节是否已填写、再按实践配置契约的字段映射表逐题提问（共 42 问），写入前以代码块展示预览并经确认。对用户口述的条款号、出境门槛数量、报告时限等法律事实做合理性检查：网信办办法阈值一律保留 [待验证 — 数值随办法修订变动] 标注，存疑值标 [前提 flagged — 需验证] 并给两个写入选项，不得静默写入。四步各可单独触发，用于只更新某一章节；律师/DPO 也可直接编辑配置文件，无需重跑访谈，配置文件纳入 git 版本控制可回滚。

02适用与边界

适用场景

  • 首次使用数据合规插件，data-compliance/CLAUDE.md 仍是带 [PLACEHOLDER] 的模板
  • 组织或团队发生重大变化后（进入新行业、CIIO 状态变化、合规团队或 DPO 变动、监管重点调整）需要全面更新配置
  • 其他数据合规流程检测到配置缺失或含占位符，提示「运行冷启动访谈或说临时模式」时
  • 只需更新某一部分：行业主管部门新出规定只重跑第 4 步；角色或升级联系人变化只重跑第 3 步；新跨境政策或分类分级策略只重跑第 2 步

不做什么

  • 不做任何具体事项的合规分析、PIA、出境路径判定或文书起草，只收集并写入配置
  • 不另存独立 YAML 或 JSON 配置文件；data-compliance/CLAUDE.md 是唯一真相来源
  • 不代替律师/DPO 核实口述的法条条号与网信办办法阈值，只做合理性检查并加待验证标注
  • 「事项工作区」与「审查过的种子文档」两章不由访谈填充，由律师/DPO 直接编辑
  • 小改动（更新 DPO 或负责人联系人、调整升级矩阵角色与权限、修正处理规模估算、按新版办法更新路径偏好）不需要重跑访谈，直接编辑配置文件即可

  • data-compliance/CLAUDE.md 现有内容（模板或已部分填写）必需

    决定每个答案写入哪个章节的哪个字段；第 1 步用 §2.1，第 2 步 §2.2–2.5，第 3 步 §2.6–2.7，第 4 步 §2.8–2.9
  • 律师/DPO 对 42 个访谈问题的回答必需
    身份与团队 13 问、合规立场 14 问、风险与升级 6 问、文书风格与行业监管 9 问；多数问题给出可选项并有追问
  • 参数：只更新哪个部分（身份 / 合规立场 / 风险升级 / 文书风格）可选
    留空运行完整四步访谈
  • 内部合规报告模板、行业主管部门近期发布的特别规定可选
    第 4 步追问时提供，用于定制报告格式与行业监管识别表

产出

  • 更新后的 data-compliance/CLAUDE.md给律师内部
    替换 [PLACEHOLDER] 后的章节：我们是谁（11 个字段）/ 谁在使用 / 可用集成 / 合规立场（整体偏好 + 敏感数据政策 + 跨境政策 + 数据安全立场）/ 风险校准（四级表组织定义版）/ 升级矩阵（角色权限表 + 自动升级触发条件 + 监管报告触发）/ 文书风格 / 输出（工作产物标题律师版与非律师版）/ 共享护栏（行业监管识别表、时效性检查频率）
  • 每步写入前的填充预览给律师内部
    markdown 代码块，按配置模板的字段格式展示答案；存疑值带 [前提 flagged — 需验证]，网信办阈值带 [待验证 — 数值随办法修订变动]，路径门槛带 [时效性 flagged]，高监管行业带 [行业监管 flagged — 需核实主管部门规定]

04开始前

前置条件

  • 每步开始先读取 data-compliance/CLAUDE.md，检查目标章节是否已有非 [PLACEHOLDER] 内容；已有则提示「这些字段已有配置，是否覆盖更新？」
  • 每步读取 data-compliance/skills/_shared/practice-profile-schema.md 的字段映射表，确定答案写入位置
  • 第 2 步建议在第 1 步之后运行（需要行业背景判断数据安全立场的行业特殊性）；第 3 步建议在第 1、2 步之后运行（需要团队结构与合规立场设计升级矩阵）；第 4 步建议在第 1 步之后运行（行业已知才能定制行业监管识别）
  • data-compliance/CLAUDE.md 已纳入 git 版本控制，可用 git log 查看配置变更历史、git diff 查看变更内容、git checkout 回滚历史版本

硬性规则

唯一真相来源
访谈结果只填充 data-compliance/CLAUDE.md 对应章节的 [PLACEHOLDER]，不另存 YAML 或 JSON；散文形式便于律师/DPO 直接阅读和编辑，写入后下次调用其他流程即时生效
确认前展示预览
每步写入前以 markdown 代码块展示填充结果，确认后才执行写入
网信办阈值不得硬写
用户口述的出境数量门槛、标准合同适用门槛、备案时限、评估有效期、认证有效期等，一律写为参考值并标 [待验证 — 数值随办法修订变动，须核实最新版]，不得直接写为确认值
存疑值两选项确认
对触发合理性检查的字段，显示检测到的问题后提供两个选项：(a) 按口述写入并保留 [前提 flagged — 需验证]；(b) 按建议值修改后写入并保留 [待验证]；不得静默写入未经确认的存疑值
保留时效性标注
跨境政策中的路径门槛写入时一律保留 [时效性 flagged]；监管报告触发中的时限、频率一律保留 [待验证]
章节间一致
升级矩阵中的角色名称须与「谁在使用」记录的角色一致；行业监管识别表中的行业须与「我们是谁 → 所属行业」一致
非律师模式
执业角色为非律师时，所有输出作为研究和初步分析供律师审查而非法律结论；在对处理活动作合规结论、决定出境路径或建议监管申报前暂停并建议升级给律师确认
临时模式
未完成访谈即需使用其他流程时，可说「临时模式」：按默认值运行并在输出标注 [临时模式 — 配置你的数据合规档案以获得定制输出]。默认值：整体合规偏好平衡型；执业角色数据合规律师；数据处理者角色为个人信息处理者（非 CIIO）；处理规模不明（逐案判断出境门槛）；敏感数据按严格门槛标记常见风险类别；跨境逐案判定不预设首选路径；数据安全按保守标准识别（不确定即标重要数据风险）
部分更新互不干扰
单独触发某一步时只更新该步对应章节，不影响其他章节

05执行步骤

共 4 步，按执行顺序。每步旁边（窄屏在步骤说明之后）是请律师核对的内置假设，可逐条复制。页面里的英文标记见首页「标记与术语」。

  1. 身份与团队访谈

    /data-compliance:identity-team可单独运行

    采集数据处理者画像、执业角色与可用集成工具，写入「我们是谁」「谁在使用」「可用集成」三章，使后续流程能正确识别处理者角色（处理者 / 受托处理者 / CIIO）、按行业触发行业监管识别、按处理规模判断出境路径门槛、按执业角色选择工作产物标题、按团队规模调整整改建议的可行性。

    请律师核对

    • 核对 1.1处理规模四档（1万 / 10万 / 100万 条）只是估算量级，与现行出境门槛的对应留给后续流程判断并标 [时效性 flagged]；是否希望在此步直接提示经核实的现行门槛？
    • 核对 1.2CIIO「不确定」时的追问只问系统宕机的影响面，是否足以作初步判断？是否应加问「是否收到过关基认定通知」？
    • 核对 1.3执业角色五个选项（数据合规律师 / 企业 DPO / 企业法务 / 非律师有律师可咨询 / 非律师无律师可咨询）是否覆盖贵方实际（README 还提到「合规官」，但问题选项中没有）？
    • 核对 1.4敏感个人信息类型清单照 PIPL 第28条列举，是否需要补充贵方行业特有的敏感类别？

    做法

    1. 读取 data-compliance/CLAUDE.md，检查三个目标章节是否已有非 [PLACEHOLDER] 内容；读取实践配置契约 §2.1 数据处理者画像字段映射表。
    2. Q1 组织/律所名称与实体类型（有限责任公司 / 股份有限公司 / 国有企业 / 律所 / 其他）；Q2 所属行业（互联网/科技、金融（银行/保险/证券）、医疗健康、教育、交通、制造、能源、电信、其他），并追问是否有跨行业业务（如同时经营金融和科技）。
    3. Q3 数据处理者角色三选一：个人信息处理者（自主决定处理目的和方式）/ 受托处理者（接受委托处理，不自主决定目的，须签订数据处理协议、按委托方指示处理）/ 两者兼有（对外为处理者，对委托方为受托处理者）。
    4. Q4 是否为关键信息基础设施运营者（是 / 否 / 不确定）；不确定时追问「业务系统若宕机，是否会严重影响金融运行 / 公共服务 / 能源供应 / 电信通信」，如是则建议向行业主管部门确认关基认定，标 [行业监管 flagged — 关基认定须行业主管部门确认]；同时说明 CIIO 的额外义务：数据本地化（CSL 第37条 [待验证]）、出境须安全评估（DSL 第31条，已核实）、关基保护条例义务。
    5. Q5 处理个人信息的大致规模按四档估算（1万条以下 / 1万-10万条 / 10万-100万条 / 100万条以上），说明其影响出境路径门槛判断且门槛由网信办办法规定，标 [时效性 flagged — 须核实最新版办法]。
    6. Q6 是否处理敏感个人信息及类型（可多选：生物识别（人脸/指纹/声纹等）、医疗健康、金融账户、行踪轨迹、宗教信仰/特定身份、不满十四周岁未成年人个人信息、其他）；Q7 是否有数据出境场景（是并描述场景 / 否 / 不确定——有境外系统或境外合作方）。
    7. Q8 合规团队规模（1-2人仅兼职 / 3-5人小型专职团队 / 5人以上中大型团队 / 仅外部顾问无内部团队）；Q9 个人信息保护负责人（已设置：姓名+职位 / 尚未设置 / 正在评估是否须设置，PIPL 第52条 [待验证]）；Q10 最大数据合规痛点（多选：出境路径不确定 / PIA 未系统开展 / 数据分类分级未完成 / 等保定级未落实 / 供应商或受托处理者管理 / 隐私政策不完善 / 其他）。
    8. Q11 执业角色五选一：数据合规律师 / 企业 DPO / 企业法务 / 非律师但有律师可咨询 / 非律师且无律师可咨询；选非律师时告知：所有输出将作为研究和初步分析供律师审查，在合规结论、出境路径决定或监管申报建议前会暂停并建议升级给律师。Q12 如需升级联系哪位律师或法务总监。
    9. Q13 可用集成逐项标「已连接 / 未连接 / 不适用」：数据资产或数据地图工具、合规管理平台（如 OneTrust 类）、隐私政策/同意管理平台（CMP）、企业微信/钉钉、文档存储位置（企业内网/共享目录）。
    10. 对口述内容做四项合理性检查（见规则），然后按写入格式示例以 markdown 代码块展示「我们是谁」等章节的填充预览：金融/医疗/能源/交通等行业在所属行业后加 [行业监管 flagged — 需核实主管部门规定]，CIIO 不确定写「建议向行业主管部门确认」，处理规模后注「具体门槛须核实最新版办法 [时效性 flagged]」；确认后写入，不另存 YAML。

    内置规则

    • 合理性检查一：声称不是 CIIO 但属于金融 / 电信 / 能源等高风险行业 → 提示关基认定风险，建议向行业主管部门确认，标 [行业监管 flagged]
    • 合理性检查二：声称处理个人信息规模很小但描述的业务体量较大 → 询问是否包含用户注册数据、交易记录等，帮助合理估算规模
    • 合理性检查三：声称无数据出境但有境外合作方或境外系统 → 询问境外系统是否处理境内用户数据（API 调用 / 数据同步等），识别隐性出境场景
    • 合理性检查四：口述 PIPL 设置 DPO 的数量阈值（如「处理超过X万条须设置DPO」）→ 标 [待验证 — 须核实 PIPL 第52条 具体规定] [前提 flagged — 需验证]
    • 行业与监管主体预设对应：互联网 → 网信办/工信部；金融 → 人行/金融监管总局；医疗 → 卫健委；教育 → 教育部
    • 受托处理者的义务框架不同：须签订数据处理协议，按委托方指示处理
    • 用户提供的值涉及网信办办法阈值时，写入保留 [待验证]
    • 本步只更新「我们是谁」「谁在使用」「可用集成」三章，不影响合规立场、风险校准等其他章节

    法律依据

    • 《个人信息保护法》第52条 [待验证] — 处理达到网信部门规定数量的处理者须指定个人信息保护负责人
    • 《网络安全法》第37条 [待验证] — CIIO 数据本地化
    • 《数据安全法》第31条（已核实）— CIIO 与重要数据处理者向境外提供数据须安全评估
    • 《关键信息基础设施安全保护条例》[待验证] — 关基运营者义务

    产出

    「我们是谁」（组织名称与实体类型、所属行业、数据处理者角色、CIIO 状态、处理规模、敏感个人信息及类型、出境场景、合规团队规模、个人信息保护负责人、最大痛点）、「谁在使用」（角色、律师联系人）、「可用集成」（5 项工具状态）三章的 markdown 预览，确认后写入 data-compliance/CLAUDE.md

  2. 合规立场访谈

    /data-compliance:compliance-stance可单独运行

    采集三维合规立场——整体合规偏好、敏感数据政策、跨境政策、数据安全立场——写入「合规立场」章。这是个性化的核心配置：决定所有流程的风险评估口径与建议语气，定制 PIA 的情形判定与同意机制审查、出境路径推荐、数据分类分级与等保定级审查口径。

    请律师核对

    • 核对 2.1保守 / 平衡 / 进取三档的定义，以及「保守型适合金融医疗等高监管行业、平衡型适合大多数互联网科技企业、进取型须有经验丰富法律团队」的默认对应是否符合贵方判断？
    • 核对 2.2「重要数据可以走标准合同出境」被直接列为须纠正的错误前提（依 DSL 第31条），是否同意这一立场？
    • 核对 2.3重要数据识别选项「行业目录未公布则按保守标准识别：影响行业运营或公共利益的数据推定为重要数据」的措辞是否恰当？
    • 核对 2.4出境路径选项对标准合同（相对成本低、适合中小规模）与保护认证（集团内跨境数据流转）的描述是否符合当前实践？访谈不提供任何现行门槛数值，是否需要律师预填？

    做法

    1. 读取 data-compliance/CLAUDE.md 检查「合规立场」是否已填写；读取实践配置契约 §2.2–2.5 字段映射表；建议在第 1 步之后运行以了解行业背景。
    2. Q1 整体合规偏好三选一：保守型（遇不确定即标待验证、选最严格合规路径、建议升级；适合金融/医疗等高监管关注度行业或有过往监管处罚记录者）/ 平衡型（在合规要求与业务运营成本间平衡；适合大多数互联网/科技企业）/ 进取型（在合规边界内寻求灵活方案，不越线但允许更多创新和效率优先；须有经验丰富的数据合规法律团队支持）。
    3. Q2 处理敏感个人信息的内部门槛，追问：是否须法务/DPO 预先审批方可启动新处理活动、是否须单独开展 PIA、外部技术供应商处理敏感数据时是否有特别管控。Q3 单独同意获取方式（弹窗单独勾选与注册同意分离 / 书面确认（线下）/ 分层告知（先通用告知再单独告知敏感项）/ 其他），并说明 PIPL 第28-29条（已核实）要求敏感个人信息须单独同意、不可与一般同意合并。
    4. Q4 是否处理不满十四周岁未成年人个人信息；是则追问如何取得监护人同意、是否有专门处理规则（PIPL 第29条，已核实）。Q5 敏感数据最小化立场（能匿名化/去标识化的优先采用 / 不收集非业务必需的敏感类 / 已有流程评估每类敏感信息必要性 / 暂无明确立场 [待建立]）。Q6 生物识别使用限制（仅用于身份认证不用于营销分析 / 不使用生物识别 / 允许在明确场景下使用并描述场景）。
    5. Q7 是否允许数据出境（是 / 否——默认境内存储、出境须审批 / 视情况逐案判断）。Q8 首选出境路径按优先级排序，依 PIPL 第38条（已核实）三路径：标准合同（相对成本低，适合中小规模 [适用门槛须验证]）/ 安全评估申报（大规模或重要数据强制）/ 保护认证（集团内跨境数据流转 [待验证适用条件]）/ 逐案确定不预设偏好。
    6. Q9 数据本地化立场（默认境内存储出境须审批 / CIIO 须本地化（CSL 第37条 [待验证]）非 CIIO 视规模决定 / 逐案判断）。Q10 境外接收方偏好或禁止名单，追问是否有特定国家/地区须升级处理、是否有接收方白名单。Q11 重要数据出境立场，依 DSL 第31条（已核实）：重要数据须先经数据分类分级识别，确认后须经安全评估申报 / 不确定数据类别时按保守推定为重要数据 / 已识别重要数据范围并描述。
    7. Q12 数据分类分级策略，依 DSL 第21条（已核实）三级分类（国家核心数据 / 重要数据 / 一般数据）：已参照行业主管部门目录完成并说明状态 / 已自建体系但不确定是否符合行业目录 / 尚未完成 [待建立]。Q13 重要数据识别立场：对照已公布的行业主管部门目录识别 [行业监管 flagged] / 行业目录尚未公布则按保守标准识别（影响行业运营或公共利益的数据推定为重要数据）/ 重要数据须单独台账管理。Q14 等级保护定级倾向：按业务系统实际性质定级不盲目降级以节省成本 / 倾向从严定级（宁高勿低）/ 已完成定级并列出系统名称+级别 / 尚未开展 [待启动]。
    8. 对口述的门槛数值与条文号做四项合理性检查（见规则）：发现存疑值先提示，经确认后写入并保留 [前提 flagged]；跨境政策中的路径门槛一律保留 [时效性 flagged]。
    9. 以 markdown 代码块展示「合规立场」章填充预览，确认后写入，不另存 YAML。

  3. 风险与升级访谈

    /data-compliance:risk-escalation可单独运行

    定义风险等级、角色权限与升级条件、自动升级触发条件和监管报告触发规则，写入「风险校准」「升级矩阵」两章，使所有流程在输出中统一使用组织定义的四级风险标注、给出精确的升级路由（升级给哪个角色）、在触发条件下自动提示而非依赖用户判断、在须监管报告的事件发生时给出正确的报告流程提示。

    请律师核对

    • 核对 3.1四级风险的典型情形归类（「PIA 未开展」归高而非关键、「记录保存不足」归中等）是否符合贵方口径？配置模板的「关键」级还附 PIPL 第66条处罚幅度 [待验证具体条款]，访谈表中省略了，是否需要同步？
    • 核对 3.2自动升级触发「大规模敏感个人信息处理」的数量门槛留空 [X]（配置模板举例 100 万条），贵方以多少条为界？
    • 核对 3.3「境外执法机构要求提供数据」出现在访谈预设触发表中，但配置模板的预设列表只有 6 项、没有这一项，是否保留？
    • 核对 3.4监管报告五场景的时限与频率全部标 [待验证]，访谈不给任何参考值，是否希望律师预先填入经核实的时限？

    做法

    1. 读取 data-compliance/CLAUDE.md 检查「风险校准」「升级矩阵」是否已填写；读取实践配置契约 §2.6–2.7；建议在第 1、2 步之后运行。
    2. Q1 风险等级框架：展示配置文件预设的四级表（关键 / 高 / 中等 / 低，原文以红、橙、黄、绿圆点标记）供直接确认沿用或调整；追问是否需调整门槛定义，例如合规偏好为保守型时是否把部分「高」提升为「关键」。
    3. Q2 组织对数据合规违规的容忍底线：追问是否有零容忍场景（如不可接受任何未经授权的数据出境）、是否有特殊监管关注事项（如近期收到过监管问询，对某类风险更敏感）；结果作为「风险校准」典型触发情形的补充或调整。
    4. Q3 角色层级，通常按三层描述并各列可独立处理事项与需升级条件：1 基础层（如数据合规助理/初级法务：一般 PIA 初审、数据映射整理；发现重要数据或敏感数据大规模处理时升级）；2 主责层（如 DPO/数据合规律师/法务经理：PIA 审批、标准合同准备、等保定级初步意见；涉及重要数据出境、监管问询、数据泄露时升级）；3 决策层（如法务总监/外部律师/合伙人：安全评估申报决策、重大 PIA 审查、监管沟通；重大数据泄露、监管检查、上市前审查时升级）。
    5. Q4 七类数据合规事项的决策权限分配，各填「谁可独立决策 / 谁须升级审批」：一般 PIA 开展与审查；安全评估申报（向网信办，通常须高层决策）；标准合同签订与备案；等保定级与备案；数据泄露事件处置；监管沟通（回复问询/检查，通常须法务总监参与）；向监管部门主动报告。
    6. Q5 逐项确认七项预设自动升级触发（是否适用、升级至哪个角色）：重要数据出境（DSL 第31条，已核实）；大规模敏感个人信息处理（超过[X]条，[待验证门槛]）；收到网信办/公安/工信部等监管问询或检查通知；数据泄露或安全事件发生或疑似发生；上市/融资前数据合规审查（网络安全审查门槛 [待验证]）；关基认定通知或怀疑业务符合关基标准；境外执法机构要求提供数据。追问是否补充其他场景（特定合作方、特定数据类型、行业特殊事件）。
    7. Q6 五类监管报告触发场景，各填报告义务、内部启动流程与验证状态：数据安全事件如泄露或系统被入侵——须向主管部门报告（时限 [待验证]）；个人信息泄露涉及大量个人——须通知受影响个人（PIPL 第57条 [待验证]）；重要数据处理者定期风险评估报告——须定期向主管部门报送（频率 [待验证]）；数据出境前安全评估申报——须在出境前向网信办申报 [待验证]；关基运营者事件报告（若 CIIO）——须向保护工作部门和公安机关报告 [待验证]。
    8. 对口述的时限、门槛做四项合理性检查（见规则）；核对升级矩阵角色名称与「谁在使用」一致；以 markdown 代码块展示预览，确认后写入，不另存 YAML。

    内置规则

    • 预设「关键」级：明显违反强制性规定，极大可能被监管处罚或面临暂停业务；典型情形：未经合规路径向境外提供个人信息、大规模敏感个人信息无同意处理、重要数据未申报出境、监管检查中发现重大合规缺口
    • 预设「高」级：有较大法律风险，可能受到监管关注或行政处罚；典型情形：告知事项不完整、同意机制存在瑕疵、PIA 未开展、敏感个人信息未单独同意
    • 预设「中等」级：存在合规改进空间，风险有限但建议整改；典型情形：记录保存不足、权利响应机制不完善、数据分类分级尚未完成
    • 预设「低」级：基本合规或风险可接受，记录备档备用；典型情形：形式要件完整但细节需优化、已有内控措施但文档化不足
    • 合理性检查：口述「数据泄露后48小时内须向监管报告」→ 标 [待验证 — 具体报告时限须核实相关条款，不同事件类型和规模可能有不同期限] [前提 flagged — 需验证]
    • 合理性检查：口述「处理超过X万条记录须向网信办申报」→ 标 [待验证 — 数值随出境办法修订变动，须核实最新版] [前提 flagged — 需验证]
    • 合理性检查：口述「轻微泄露不需要报告」→ 提示报告义务与事件严重程度相关，轻微事件的处理须核实具体规定 [待验证]
    • 合理性检查：口述「内部自查等同于监管申报」→ 重要数据处理者的风险评估报送是向监管部门报送，非内部自查可替代 [前提 flagged — 需验证]
    • 监管报告触发中的时限、频率写入时一律保留 [待验证]
    • 常见重跑场景：新增团队成员或调整角色；监管重点调整（近期执法行动影响风险口径）；DPO 或法务总监换人

    法律依据

    • 《数据安全法》第31条（已核实）— 重要数据出境须安全评估，作为自动升级触发
    • 《个人信息保护法》第57条 [待验证] — 个人信息泄露须通知受影响个人
    • 网络安全审查办法（网信办等）— 上市/融资前网络安全审查，门槛 [待验证]

    6. Q6 行业监管识别：按配置模板预设的七行业关注点逐行确认贵方是否有额外要求或限制——金融（金融数据分类分级、个人金融信息保护）；医疗健康（健康数据、基因数据特别保护）；汽车（汽车数据安全管理规定 [待验证]）；教育（未成年人个人信息、教育数据特别保护）；互联网/平台（算法推荐、用户画像）；电信（电信数据安全专项规定）；能源/交通（关基认定风险、重要数据识别）；追问行业主管部门近期是否发布希望特别关注的规定。
    7. Q7 跨境路径决策的内部审批与文档要求：启动安全评估申报前须经过哪些内部审批层级；标准合同签订前由哪个部门/角色审批；是否有境外接收方合同审查前置要求；作为「行业监管识别」的跨境决策流程补充写入。
    8. Q8 时效性检查频率：保留默认（6 个月复核一次）/ 更严格（3 个月）/ 降低频率（12 个月，适合低频监管变化场景）；更新「共享护栏 → 时效性触发」。
    9. Q9 工作产物标题：确认或调整预设的两套——律师角色「律师工作产物 — 受律师-当事人特权保护 / 保密」；非律师角色（DPO/法务）「研究笔记 — 非法律建议，供律师审查」；追问是否需中英文双语标题。
    10. 对口述内容做四项合理性检查（见规则）；核对行业监管识别表的行业与「我们是谁 → 所属行业」一致；以 markdown 代码块展示预览，确认后写入，不另存 YAML。
