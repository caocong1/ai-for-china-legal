01概要

面向需要建立或检查《数据安全法》合规体系的企业及其律师/DPO，按四个步骤完成全面审查：先依 DSL 第21条把数据资产划为国家核心数据/重要数据/一般数据并形成分级清单；再对照行业主管部门目录（或按保守标准推定）确认重要数据范围，核对重要数据处理者的负责人、管理机构、定期风险评估报送等强制义务及出境限制；然后建立或审查覆盖收集到删除八个生命周期阶段的数据安全管理制度、组织保障、培训与技术措施；最后建立定期风险评估与报送、日常监测、四级事件分级与六阶段应急报告、数据交易合规和境外执法调取应对框架。流程开始前读取 data-compliance/CLAUDE.md 的所属行业、CIIO 身份、分类分级策略、重要数据识别立场、数据安全立场、等保倾向、团队规模与文书风格；配置为占位符时进入临时模式，不确定等级的数据按上一级（重要数据）推定。DSL 中只有第21条、第31条标「已核实锚点」，管理制度、风险评估报送、事件报告、数据交易、境外调取的条文一律写为「条号待验证」，具体频率、时限也全部标 [待验证]，由律师核实后填入。

02适用与边界

适用场景

  • 新业务上线前的数据安全合规审查
  • 年度数据安全合规自查
  • 监管检查准备，需要对照 DSL 义务逐项核对制度与记录
  • 尚未完成数据分类分级，需要建立三级分级制度与数据分级清单
  • 需要判断企业是否为重要数据处理者，以及负责人、管理机构、风险评估报送等义务是否已落实
  • 需要建立或审查覆盖全生命周期的数据安全管理制度、培训计划与技术措施
  • 发生或疑似发生数据安全事件，需要分级、应急处置与向主管部门报告
  • 拟参与数据交易，或收到境外司法/执法机构的数据调取请求

不做什么

  • 不处理 CIIO 的等级保护定级与关基保护条例叠加义务（定级不低于三级、专门安全管理机构等）——交由网络安全法合规检查流程（network-security-compliance）处理，本流程不重叠
  • 不操办重要数据出境的安全评估申报本身——识别出重要数据出境需求后转数据出境评估流程的申报步骤（/data-compliance:security-assessment-filing）
  • 不处理国家核心数据：其管理超出普通企业处理范围，发现时须立即升级
  • 不替代行业主管部门的重要数据目录：目录须由用户向主管部门获取或查阅，本流程只做对照与保守推定
  • 不提供 DSL 配套条文的具体条号、评估报送频率、事件报告时限、日志留存期限等数值——一律标 [待验证]
  • 向主管部门报送的风险评估报告、安全事件报告不受律师-当事人特权保护，不加特权标头

03输入与产出

需要律师提供

  • 合规检查场景描述必需
    如：新业务数据安全合规审查 / 年度自查 / 监管检查准备 / 疑似安全事件处置 / 数据交易审查 / 境外执法调取应对
  • data-compliance/CLAUDE.md 实践配置（所属行业、是否为 CIIO、数据分类分级策略、重要数据识别立场、数据安全立场、等级保护定级倾向、合规团队规模、文书风格/工作产物标题）必需
    关键字段为占位符时进入临时模式；行业为占位符时仅使用 DSL 三级通用框架并提示补充行业信息
  • 数据资产清单 / 数据地图 / 处理活动记录（ROPA）必需
    数据资产梳理不完整时分级步骤暂停并提供梳理问题清单；已连接数据地图工具时可直接导出
  • 行业主管部门重要数据目录（如已公布）可选
    未公布或无法获取时按保守标准推定并标 [行业监管 flagged — 目录待公布]
  • 现有制度文件（数据安全管理制度、ISO 27001 等体系文件、权限台账、培训记录）可选
    制度审查步骤需要；已有 ISO 27001 体系时评估与 DSL/PIPL 的差距
  • 重要数据出境需求说明可选
    有出境需求时触发重要数据出境对照表并转申报步骤
  • 安全事件信息（发现时间、数据类型与数量、受影响个人数、事件来源）可选
    事件处置场景；等级无法立即确定时先按较高等级处理
  • 数据交易合同、数据来源证明、中介机构审核记录可选
    数据交易审查场景；对方无法证明来源合法时终止交易

产出

  • 数据分类分级报告给律师内部 / 客户
    七部分：一、适用法律依据；二、数据资产梳理摘要；三、数据分级清单摘要与 [红] 重要数据汇总（含判定依据：按目录/按保守推定）；四、行业目录衔接情况；五、PIPL 与 DSL 交叉数据；六、待验证与待核实事项；七、下一步建议。另产出九列数据分级清单（数据目录）
  • 重要数据识别与处理评估报告给律师内部 / 客户
    四部分：一、重要数据识别结论表与识别方法；二、重要数据处理者义务落实表（负责人、管理机构、风险评估计划、报送计划，含责任人与计划日期）；三、重要数据出境评估（需求、范围、路径①、评估状态）；四、待验证事项表。另产出八项重要数据专项台账
  • 数据安全管理制度审查报告给律师内部 / 客户
    五部分：一、八阶段制度完整性审查表；二、组织保障审查（数据安全负责人、管理机构、个人信息保护负责人）；三、技术措施审查表（加密、MFA、审计日志、备份，各标风险级别）；四、整改建议表（问题、风险级别、措施、完成日期）；五、待验证事项表
  • 数据安全风险评估报告给律师内部 / 客户；报送主管部门的版本须用正式报告格式、不受特权保护
    五部分：一、重要数据处理情况；二、七维度风险评估结论表（等级 [红]/[橙]/[黄]/[绿]、主要发现、整改建议）；三、综合风险结论与主要风险项；四、整改计划表；五、待验证事项表。事件场景另产出初报/进展报告/终报与受影响个人通知稿

04开始前

前置条件

  • 读取 data-compliance/CLAUDE.md 八项配置：所属行业（行业目录识别 [行业监管 flagged]）、是否为 CIIO（义务强度、关基叠加、出境强制评估）、数据分类分级策略（已完成或从头建立）、重要数据识别立场（保守推定 vs 对照目录）、数据安全立场（保守/平衡/进取影响风险评估口径）、等级保护定级倾向（与等保衔接，交网络安全法合规检查流程）、合规团队规模（制度落地可行性）、文书风格/工作产物标题（报告格式）
  • 关键配置为占位符时进入临时模式 [临时模式]：遇不确定等级的数据按上一级（重要数据）推定；对可能影响行业运营或公共利益的数据推定为重要数据并标 [行业监管 flagged — 按保守推定]；标注所有临时模式判断并建议运行 /data-compliance:cold-start-interview 后重新运行
  • 读取 CIIO 字段：CIIO → 除三级分类分级外须满足 CSL 关基条例更高要求，交由网络安全法合规检查流程；不确定 → 按 CIIO 处理并建议向行业主管部门确认
  • 读取行业字段识别金融、医疗健康、工业/制造、汽车、电信、能源/交通的行业特殊要求
  • 核实时效性：DSL 第21条、第31条已核实可引用；DSL 管理制度、事件报告、数据交易的具体条款 [待验证]；各行业重要数据目录持续更新须每季度复核；《网络数据安全管理条例》施行状态 [待验证]
  • 建议按顺序执行：分级结果是重要数据识别的输入，识别出的重要数据是管理制度与风险评估的基础；各步骤也可单独触发
  • 使用者为非律师角色时，所有输出作为供律师审查的研究，在作出合规结论或建议启动监管申报前暂停并建议升级律师（来自实践配置文件）

硬性规则

数据处理者与 CIIO 立场确认
CIIO 除 DSL 三级分类分级外，还须满足 CSL 关基保护条例的更高安全要求（定级不低于三级、专门安全管理机构等），交由网络安全法合规检查流程处理，本流程不重叠；CIIO 身份不确定 → 临时模式按 CIIO 处理，建议向行业主管部门确认关基认定情况
重要数据识别提示
重要数据识别决定后续义务强度；目录由各行业各地区主管部门制定，须核实适用目录 [行业监管 flagged — 需核实主管部门规定]；目录未公布时按保守标准推定并标 [行业监管 flagged — 目录待公布]；国家核心数据适用最严格管理，超出普通企业处理范围，发现时立即升级
行业监管识别
金融（金融数据分类分级标准区别于 DSL 通用标准，人民银行/金融监管总局）、医疗健康（健康医疗数据、基因数据，国家卫健委）、工业/制造（工业数据分类分级规范，工信部）、汽车（汽车数据安全管理 [待验证]，工信部/网信办）、电信（电信数据安全规定，工信部）、能源/交通（关基认定与重要数据出境风险高，国家发改委/交通部）
重要数据出境衔接
任何主体的重要数据出境需求 → [红] 强制路径①安全评估申报（/data-compliance:security-assessment-filing）；CIIO 重要数据出境 → 路径判定 + 申报（CSL 第37条关基本地化 [待验证] + DSL 第31条）；重要数据出境不适用标准合同（路径③）或保护认证（路径②）；重要数据与个人信息同时出境时可合并申报，但须在材料中分别说明
目的地与特权检查
向主管部门报送的风险评估报告、安全事件报告不受律师-当事人特权保护，须用正式报告格式；内部法律分析按配置的工作产物标题标注；外部数据合规报告须确认目的地在特权保护圈内
时效性提示
DSL 关于管理制度、事件报告、数据交易的具体条款 [待验证 — 须核实 DSL 配套条文号及实施细则]；各行业重要数据目录持续更新 [行业监管 flagged]，每季度复核；《网络数据安全管理条例》施行状态 [待验证]
流程顺序
步骤 1 分类分级 → 步骤 2 重要数据识别与处理 → 步骤 3 管理制度 → 步骤 4 风险评估与报告；步骤 1 的分级结果为步骤 2 的输入，步骤 2 识别的重要数据为步骤 3、4 的基础；各步骤可单独触发
来源标签与验证状态
法条引用一律标 [模型知识 — 需验证]；DSL 第21/31条与 CSL 第21条标「已核实锚点，建议复核」；其余 DSL 条文标 [条号待验证]；引用规范见 data-compliance/skills/_shared/legal-basis-conventions.md

05执行步骤

共 4 步，按执行顺序。每步旁边（窄屏在步骤说明之后）是请律师核对的内置假设，可逐条复制。页面里的英文标记见首页「标记与术语」。

  1. 数据分类分级

    /data-compliance:data-classification-grading可单独运行

    依 DSL 第21条建立三级分类分级制度：梳理数据资产，按重要程度与危害程度两个维度判定级别，衔接行业重要数据目录，梳理与 PIPL 个人信息分类的交叉关系，形成数据分级清单。

    请律师核对

    • 核对 1.1「不确定等级按上一级（重要数据）推定」「宁可误判为高级别不可低判」的从严推定立场会抬高客户义务，文件学说部分也标此点「有争议」，贵所是否同意作为默认？
    • 核对 1.2危害程度表把「损害合法权益但不涉公共利益」的数据归为「重要数据/一般数据（视规模）」，是否认可把数据规模作为升级因素？
    • 核对 1.3分级清单复核「每年不少于一次」、目录复核「每季度」两种频率为文件自设，是否符合贵所惯例？
    • 核对 1.4三级层级关系的集合符号表述（「国家核心数据 ⊂」「重要数据 ⊃ 一般数据（相互排斥）」）自相矛盾，属 SKILL.md 原文错误，建议修正
    • 核对 1.5公开数据「加工整合后须重新评估」的触发标准未量化，是否需补充口径？

    做法

    1. 读取实践配置中的所属行业、数据分类分级策略、重要数据立场；分类分级策略为占位符时进入临时模式——不确定等级的数据按上一级（重要数据）推定；行业为占位符时仅使用 DSL 三级通用框架并提示补充行业信息
    2. 步骤一：按 DSL 第21条列出三级框架表——国家核心数据（关系国家安全、国民经济命脉、重要民生、重大公共利益；最严格管理；绝大多数企业不涉及）、重要数据（遭篡改/破坏/泄露/非法获取利用后可能危害国家安全、公共利益或合法权益且达到重要影响级别；须专项制度、负责人、定期评估报送、出境须安全评估；按行业目录识别）、一般数据（其余数据；基本管理制度）
    3. 步骤二：梳理六类数据资产（用户/客户个人信息、敏感个人信息、内部业务运营数据、技术与研发数据、行业特定数据、公开/已授权数据），记录量级、产生/收集方式、存储位置、流转方式；已连接数据地图工具则导出清单作为起点，否则通过业务访谈和系统盘点手动建立
    4. 步骤三 3.1 重要程度正向判断：对每类资产回答五个问题——是否与国家安全/国防/重大基础设施直接相关（→ 可能国家核心）、是否与国民经济命脉相关（→ 可能重要）、是否与重要民生或重大公共利益相关（→ 可能重要）、是否已列入行业目录（→ 重要）、是否仅涉及企业内部运营且影响有限（→ 可能一般）
    5. 步骤三 3.2 危害程度反向判断：假设数据遭泄露/篡改/非法获取后——危害国家安全或对国民经济重大影响（极严重 → 国家核心/重要）、影响社会稳定、公共秩序或行业运转（严重 → 重要）、损害合法权益但不涉公共利益（中等 → 重要/一般视规模）、仅个别主体有限影响可常规救济（较轻 → 一般）
    6. 步骤三 3.3：优先对照六行业目录表（金融、医疗健康、工业/能源、汽车、电信、互联网/平台）；目录未公布时分析数据对经济社会运转的实际影响面，宁可误判为高级别不可低判，标 [行业监管 flagged — 目录待公布，按保守标准推定]，建议每季度复核目录发布情况
    7. 步骤四：并行标注 PIPL 分类（个人信息 / 敏感个人信息，PIPL 第28条）与 DSL 级别，识别交叉数据——大规模敏感个人信息（基因、健康、行踪轨迹）可能同时属于 DSL 重要数据
    8. 步骤五：形成九列数据分级清单（资产名称、数据类型、DSL 级别、PIPL 分类、主要处理活动、存储位置境内/境外/混合、出境情况、主要风险、保护措施要求）；安排首次全面梳理与定期复核
    9. 对照九项检查清单，按模板输出七部分《数据分类分级报告》，重要数据汇总标 [红] 并说明判定依据，建议对重要数据触发重要数据识别与处理步骤

    内置规则

    • 分级实行「不降级」原则：数据在多种情形下均涉及时取最高级别保护
    • PIPL 与 DSL 两套分级并行：同时满足两套标准时两套义务均须满足；不可以 PIPL 同意机制替代 DSL 重要数据保护义务；跨行业数据（如同时涉及金融+医疗）按最高敏感等级处理
    • 行业目录是识别重要数据的核心依据，须优先对照目录判断
    • 数据级别有争议（可能重要也可能一般）→ 按较高等级处理，建议向主管部门咨询或委托专业机构评估，并在报告中记录争议点
    • 公开可查数据（政府公开数据、上市公司财报）原则上为一般数据；但加工整合后形成新的分析能力（如大规模用户行为聚合）须重新评估
    • 研发/训练数据（如 AI 模型训练数据集）含大规模个人信息或行业特定数据时须纳入分级评估；模型输出数据的级别视其内容而定
    • 处理者同时为 CIIO → 在三级分类基础上叠加 CSL 关基保护要求（更严格等保、更严格本地化），标 [CSL关基衔接 — 需核实关基条例义务]

  2. 重要数据识别与处理

    /data-compliance:important-data-handling可单独运行

    对照行业目录（或按保守标准推定）确认重要数据范围，落实重要数据处理者的强制义务（数据安全负责人与管理机构、定期风险评估并报送），评估重要数据出境的安全评估要求，并建立重要数据专项台账。

    请律师核对

    • 核对 2.1保守推定五情形中「被竞争对手或外国机构获取后可能对产业安全造成影响」把竞争因素纳入重要数据认定，是否与商业秘密混同、范围过宽？
    • 核对 2.2步骤 2.3 要求重要数据出境前完成跨境 PIA（PIPL 第55条第(四)项），但 PIA 是个人信息义务——不含个人信息的重要数据是否也适用？文件未区分
    • 核对 2.3「负责人未设立 → 建议在 [时限] 内完成」时限留空，而管理制度步骤写了 30 天，两处口径是否统一？
    • 核对 2.4台账「访问权限每季度复核」「识别依据年度复核」为文件自设频率，是否符合贵所实践？
    • 核对 2.5「重要数据已出境但未经评估 → 必要时主动向监管部门报告」的主动报告立场是否同意？

    做法

    1. 读取实践配置中的所属行业、CIIO 身份、重要数据出境立场、重要数据识别立场；CIIO 身份或行业不确定时进入临时模式——重要数据按保守标准从严推定，CIIO 不确定按 CIIO 处理；建议已完成数据分类分级以获取初步重要数据清单
    2. 步骤一 1.1：对照七行业目录制定机关表（金融—人民银行/金融监管总局、医疗健康—国家卫健委、工业制造—工信部、汽车—工信部/网信办、电信—工信部、能源/交通—国家发改委/交通运输部、互联网/平台—网信办，目录状态均 [待验证]），填写目录对照工作表（资产名称、是否在目录中/目录未发布、目录依据、结论：重要/一般/待确认）
    3. 步骤一 1.2：目录缺失时按五条保守推定情形判断——数据规模达一定量级且类型关系行业主要功能（如能源调度、金融交易数据）→ 重要；被竞争对手或外国机构获取后可能影响产业安全 → 重要；反映国家治理或公共服务运营状况（交通运行、医疗资源分布）→ 重要；汇聚后可反推分散的敏感信息 → 重要（评估汇聚影响）；仅企业内部运营且无法汇聚产生更高影响 → 一般（需记录理由）
    4. 步骤二 2.1：核对三项 [红] 强制组织义务——数据安全负责人（是否须为高级管理人员 [待验证]）、数据安全管理机构（规模要求 [待验证]）、职责界定（含分类分级、安全评估、事件处置）；提示处理个人信息达规模时还须指定个人信息保护负责人（PIPL 第52条 [待验证]），两者可整合但须区分职责
    5. 步骤二 2.2：核对三项 [红] 强制评估义务——定期开展风险评估（频率 [待验证 — 须核实 DSL 配套规定]）、报告内容四要素（处理活动合规性、安全措施有效性、重要数据安全状态、风险识别与应对）、向主管部门报送（频率/对象/渠道 [待验证]）；详细方法交风险评估与报告步骤
    6. 步骤二 2.3：按出境主体区分——CIIO 在境内收集产生的重要数据出境参照 CSL 及关基条例向主管部门申报安全评估 [待验证]（DSL 第31条前段）；非 CIIO 按国家网信部门会同有关部门制定的办法执行安全评估 [待验证]（DSL 第31条后段）；说明重要数据出境一律路径①并须完成跨境 PIA（PIPL 第55条第(四)项+第56条）
    7. 步骤三：填写重要数据出境对照表（是否含重要数据、是否 CIIO、出境业务合法正当必要性及能否境内处理替代、数据最小化、安全评估申报状态），结论三选一：确需出境 → [红] 强制安全评估并转申报步骤；不建议出境 → 境内处理方案并记录决策理由；范围不明确 → 先缩小范围去除不确定部分再评估
    8. 步骤四：建立八项重要数据专项台账（名称及类型、来源、识别依据、存储位置、访问权限、出境情况、风险评估状态、负责人），并按各项更新频率维护（变化时更新 / 识别依据年度复核 / 访问权限每季度复核 / 风险评估状态每次评估后更新）
    9. 对照十项检查清单（含「重要数据均存储在境内（或已启动出境安全评估）」「CIIO 身份不确定时已按 CIIO 处理并标 [临时模式]」），按模板输出四部分《重要数据识别与处理评估报告》

    内置规则

    • 重要数据出境不适用标准合同（路径③）和保护认证（路径②），一律须经安全评估（路径①），触发数据出境评估流程的申报步骤
    • 重要数据须境内存储，出境须评估（台账「存储位置」项标 [红]）
    • 识别范围有争议（业务团队与合规团队分歧）→ 记录分歧，按较高等级处理，建议寻求主管部门或外部专家意见
    • 不确定是否为重要数据处理者 → 按保守推定建立重要数据处理者义务合规体系，待主管部门确认后调整
    • CIIO 认定中尚未收到通知 → 业务性质接近关基范围时主动向行业主管部门咨询，同时按 CIIO 义务建立合规框架
    • 重要数据出境有紧迫业务需求 → 安全评估不可绕过（[红]）；可探索境内处理+仅提供处理结果的方式替代出境
    • 重要数据范围超出预期影响业务 → 评估数据最小化方案（剔除重要数据后出境）与业务模式调整可行性
    • 重要数据已出境但未经安全评估 → 立即暂停该出境活动（[红]），评估历史出境影响，启动安全评估申报，必要时主动向监管部门报告
    • 处理多个行业的重要数据 → 各行业目录均须对照，最高等级要求适用于全部重要数据管理
    • 风险评估报送主管部门不明确（多头监管）→ 按行业/数据类型识别主要监管主体，同时向多个部门咨询，标 [行业监管 flagged — 多头监管需核实主报部门]
    • 数据安全负责人尚未设立 → 标 [橙]/[红] 整改项，建议在 [时限] 内完成，提供职责清单模板

    法律依据

    • 《数据安全法》（2021年）第21条 — 三级分类分级，重要数据目录由各地区各部门制定（已核实锚点，建议复核）

    • 《数据安全法》（2021年）关于重要数据处理者义务 [条号待验证] — 明确数据安全负责人和管理机构，定期风险评估并向主管部门报送报告
    • 《个人信息保护法》（2021年）第40条 — CIIO 及达量处理者个人信息本地化与出境安全评估；与跨境 PIA 无关（已核实锚点，建议复核）
    • 《个人信息保护法》（2021年）第55条第(四)项+第56条 — 向境外提供属 PIA 法定情形，报告留存三年（已核实锚点，建议复核）
    • 《个人信息保护法》（2021年）第52条 [待验证] — 处理个人信息达规定规模须指定个人信息保护负责人
    • 《网络安全法》（2017年）第37条 [待验证具体条号] — 关基运营者境内存储重要数据，确需出境须安全评估

    • 《数据出境安全评估办法》（2022年，网信办） — 重要数据处理者出境须申报的情形与材料 [具体条款与门槛待验证]
    • 各行业主管部门重要数据目录 [行业监管 flagged — 需核实主管部门最新目录]

    做法

    3. 按四层制度文件体系核对完整性：顶层「数据安全管理总则」；六项专项制度（分类分级、访问控制、共享与对外提供、重要数据管理、安全事件应急处置）；操作规程；记录表单（处理活动、权限申请、共享、事件记录）

    做法

    1. 读取实践配置中的数据安全立场、重要数据识别立场、CIIO 身份、合规团队、文书风格；数据安全立场为占位符时进入临时模式——安全事件按最高等级处置，报告时限按最严格标准执行；建议已完成分类分级与重要数据识别
    2. 步骤一 1.1：按七个维度及对应方法开展重要数据风险评估——处理合法合规性（文档审查+访谈）、分类分级准确性（清单核对）、安全措施有效性（技术测试+日志审查）、人员管理合规性（权限台账+培训记录）、数据共享与出境合规（共享/出境记录审查）、威胁与漏洞识别（漏洞扫描+威胁情报+重要系统渗透测试）、安全事件回顾（事件记录审查）
    3. 步骤一 1.2：区分三类评估——定期全面风险评估（重要数据处理者，频率 [待验证]，建议至少年度一次，出风险评估报告）、触发式评估（重大事件/出境评估前/重大业务变化，出专项报告）、日常安全检查（月度/季度，出检查记录）
    4. 步骤一 1.3：确认报送要素——报送对象（行业主管部门 [行业监管 flagged]）、周期 [待验证]、核心内容六项（重要数据范围、处理活动合规性、安全措施现状、风险识别与应对、历史事件回顾、改进计划）、渠道 [待验证]；报送前经数据安全负责人审签，并提示报送报告不受律师-当事人特权保护
    5. 步骤二：按五个监测维度核对监测方式、告警机制与负责团队——网络入侵与异常访问（SIEM/IDS、日志分析、基线阈值告警）、数据异常访问（DAM、异常查询与批量下载检测）、漏洞跟踪（定期扫描、CVE 订阅、补丁管理、高危即时告警）、重要数据异常流出（DLP、传输监测）、外部威胁情报；监测日志留存期 [待验证 — 结合等保与 DSL 配套规定]
    6. 步骤三 3.1：按四级事件分级判定——特别重大 Ⅰ级（危害国家安全/社会稳定/重大公共利益，涉国家核心数据或大规模重要数据）、重大 Ⅱ级（涉重要数据或大规模个人信息，如超过百万条个人信息泄露、重要行业数据被窃取）、较大 Ⅲ级（如数万条个人信息泄露、内部重要业务数据泄露）、一般 Ⅳ级（少量用户数据泄露）；分级标准 [待验证]
    7. 步骤三 3.2：按六阶段流程处置——[1] 立即响应（确认真实性、启动应急小组、隔离止损）→ [2] 初步评估（类型与影响范围、来源原因、定级，时限 [待验证]）→ [3] 报告决策（特别重大/重大立即启动向主管部门报告 [时限待验证]；涉个人信息泄露评估是否通知个人 [条件与时限待验证]；通知法务/合规/负责人）→ [4] 深度处置（遏制、证据保全、恢复）→ [5] 事件报告：初报/进展报告/终报 [时限待验证] → [6] 事后复盘（根因、改进、复盘报告）
    8. 步骤三 3.3–3.4：按初报/进展/终报内容表填报（基本情况、影响范围估算与更新、起因经过、已采取措施、整改计划仅终报）；确定报告对象——行业主管部门、网信部门（个人信息相关）、公安部门（涉嫌犯罪），时限均 [待验证]
    9. 步骤三 3.5：评估是否须通知受影响个人并按四项内容起草通知——泄露事件描述（何时/何种数据/可能后果）、已采取的补救措施、个人可采取的保护措施（改密码、警惕诈骗）、投诉/咨询渠道
    10. 步骤四：按卖方（证明来源合法，不得出售违法收集数据）、中介机构（要求双方说明来源、审核身份、留存审核与交易记录 [期限待验证]）、买方（核实来源，不得购买明知违法数据）三角色核对义务，走七项数据交易合规清单，评估重要数据交易限制 [行业监管 flagged]
    11. 步骤五：收到境外司法/执法机构调取请求时按五项原则处置——未经主管机关批准不得提供（[红]）、立即法律咨询（通知法务/外部律师）、向主管部门报告并听取意见 [具体要求待验证]、评估司法协助条约（MLAT）等合法途径、获批前不得单方面提供任何数据（[红]）
    12. 对照十三项检查清单，按模板输出五部分《数据安全风险评估报告》

    内置规则

    • 事件分级参考数量：Ⅱ级含「超过百万条个人信息泄露」，Ⅲ级含「数万条个人信息泄露」，Ⅳ级为少量用户数据泄露——均为参考标准，以主管部门规定为准 [待验证]
    • 事件等级无法立即确定 → 先按较高等级（[橙]/[红]）处理并加速评估，不因等级不确定而延误报告
    • 数据安全事件与个人信息泄露同时发生 → DSL 事件报告与 PIPL 泄露通知两套义务并行，分别满足各自时限
    • 跨国集团境外主体泄露境内个人信息 → 境内个人信息保护义务仍须满足，须评估是否触发 PIPL 义务及境内报告义务
    • 国家核心数据绝对禁止进入数据交易市场（[红] 硬性要求）；重要数据须确认无禁止性规定且符合安全要求方可谨慎交易
    • 交易对方无法证明数据合法来源 → 终止交易（[红] 风险不可接受）；交易后发现来源违法 → 立即停止使用、向主管部门报告（如适用）、评估损害赔偿与责任
    • 境外执法机构以紧急为由要求立即提供数据 → 紧急情形不构成绕过中国法律程序的理由（[红]），立即咨询律师并向主管部门报告，向境外机构说明须经中国合法程序
    • 向主管部门提交的报告内容与实际不符 → 极高合规风险（[红]），立即纠正，可能须主动向主管部门说明
    • 风险评估报送逾期 → 合规缺口（[橙]/[红]），评估是否须说明情况，立即补报并建立提醒机制
    • 无应急预案即发生事件 → 临机处置优先止损，同步建立临时应急小组，事后立即建立正式应急机制

  • 数据级别或重要数据范围有争议 → 按较高等级处理，记录争议，建议向主管部门咨询或委托专业机构/外部专家评估
  • CIIO 身份不确定或业务接近关基认定范围 → 按 CIIO 建立合规框架，主动向行业主管部门咨询，关基叠加要求转网络安全法合规检查流程
  • 识别到重要数据且有出境需求 → [红] 强制路径①，转 /data-compliance:security-assessment-filing（CIIO 另先走 /data-compliance:pathway-determination）
  • 重要数据已出境但未经安全评估 → 立即暂停，评估历史影响，启动申报，必要时主动向监管部门报告
  • 风险评估报送主管部门不明确（多头监管）→ 识别主要监管主体并同时向多个部门咨询，标 [行业监管 flagged — 多头监管需核实主报部门]
  • 安全事件：特别重大/重大 → 立即启动向主管部门报告 [时限待验证]；等级不明 → 先按较高等级处理；涉个人信息泄露 → 评估通知个人并报网信部门；涉嫌犯罪 → 报公安部门
  • 数据交易对方无法证明来源合法 → 终止交易；交易后发现来源违法 → 立即停止使用并报告主管部门（如适用）
  • 收到境外司法/执法机构数据调取请求 → 立即通知法务/外部律师，向主管部门报告，未经批准不得提供，紧急情形亦不例外
  • 向主管部门提交的报告与实际不符 → 立即纠正，可能须主动向主管部门说明
  • 使用者为非律师角色 → 在作出合规结论、建议启动监管申报前暂停并升级律师；监管问询/检查、数据泄露事件、关基认定通知触发实践配置文件的自动升级
