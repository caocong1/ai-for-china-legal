01概要

依《网络安全法》（2017年）第21条和第31条起，对企业或机构运营的网络与信息系统做一次全面的网络安全法合规检查，产出等保、关基、运营者义务、个人信息收集四份合规审查报告，每份报告都带关键/高/中等/低四级风险分级与整改建议。做法是先读取 data-compliance/CLAUDE.md 中的 CIIO 身份、所属行业、等级保护定级倾向、数据安全立场、合规偏好、团队规模和文书风格，再按「等保定级（基础层）→ 关基特别保护（若适用）→ 网络运营者一般义务 → 个人信息收集合规（CSL 与 PIPL 衔接）」四步顺序执行，每一步也可以单独触发。法条引用统一走 data-compliance/skills/_shared/data-protection-citations.md 引用库：CSL 第21条、第31条起以及 PIPL 第13-14、28-29、44-47条按「已核实锚点」引用，CSL 第37条、实名制与日志留存条号、等保国标编号、关基条例具体条款等一律标 [待验证]。检查中发现出境场景转出境评估流程，发现需要完整 PIA 的情形转 PIA 生成流程。

02适用与边界

适用场景

  • 互联网平台网络安全合规自查
  • 金融机构等保与关基合规审查
  • 年度网络安全合规体检
  • 系统上线前，或系统发生功能扩展、用户规模大幅变化、新增重要数据处理等重大变更后，需要评估是否重新定级
  • 客户属于金融、电信、能源/交通/水利、医疗/公共服务、大型互联网平台等高风险行业，需要评估关基认定可能性，或已收到关基认定通知
  • 需要把等保、关基、运营者义务、个人信息收集四项放在一个流程里出一套完整报告

不做什么

  • 数据出境路径判定与安全评估申报：转 /data-compliance:pathway-determination 或 /data-compliance:security-assessment-filing
  • 完整的个人信息保护影响评估（PIA）：转 /data-compliance:pia-generation
  • 《数据安全法》下的数据分类分级、重要数据管理：转 /data-compliance:data-security-compliance
  • 不替代公安机关、等保测评机构或行业保护工作部门的定级、测评与关基认定结论；关基认定须通过行业主管部门确认，不可自行认定或否认
  • 不代为向公安机关提交等保备案材料，也不代为向监管部门提交报告

03输入与产出

需要律师提供

  • 合规检查场景描述（如：互联网平台网络安全合规自查 / 金融机构等保与关基合规审查 / 年度网络安全合规体检）必需
  • data-compliance/CLAUDE.md 实践配置：是否为 CIIO、所属行业、等级保护定级倾向、数据安全立场、整体合规偏好、合规团队规模、文书风格与工作产物标题可选
    缺失或为 [PLACEHOLDER] 时进入临时模式；建议先运行 /data-compliance:cold-start-interview
  • 系统清单及每个系统的功能描述、用户规模（注册/活跃）、处理数据类型、行业归属、历史定级与备案情况、是否承载关基、境外访问与跨境数据流必需
    信息不足以判断等级时，流程会列出缺失项要求补充，不猜测
  • 关基相关材料：行业主管部门认定通知（如有）、专门安全管理机构与安全负责人设置、关键岗位人员审查、年度安全检测评估、应急演练、采购安全审查、数据存储位置与境外备份情况可选
  • 运营者义务材料：实名验证机制、各类日志留存配置与期限、安全技术措施清单、应急预案与演练记录、违法信息监测处置机制可选
  • 个人信息收集材料：隐私政策、App 系统权限清单、同意弹窗与撤回入口描述、用户查阅/更正/删除/注销入口说明可选

产出

  • 网络安全等级保护合规审查报告给律师内部或客户；向公安机关提交的备案材料须另用正式报告格式（不受律师-当事人特权保护）
    报告头（系统名称、审查日期、审查范围、审查模式：正常/临时）；等级认定表（受侵害客体、危害程度、建议等保级别 [待验证]、是否为 CIIO）；合规状态表（等保备案、等级测评、安全物理环境、安全通信网络、安全区域边界、安全计算环境、安全管理制度，每项给状态、风险等级、整改建议）；风险摘要（关键/高/中等/低各项数与主要风险）；下一步行动（优先整改项与期限、备案/测评安排、持续监控计划）；审查者注与时效性标记
  • 关键信息基础设施保护合规审查报告给律师内部或客户；关基安全评估报告向保护工作部门提交时须用正式报告格式
    报告头（组织名称、业务领域、审查日期、CIIO 认定状态：已认定/未认定/不确定、审查模式）；关基识别评估（行业归属、系统中断后果、数据敏感性、关基认定风险）；关基义务履行状态表（专门安全管理机构、安全负责人、关键岗位人员审查、定期安全检测评估、应急预案与演练、数据本地化、出境安全评估、供应链采购安全审查）；数据本地化与出境评估表（个人信息、重要数据各列存储位置、本地化合规、出境情况、出境合规状态）；衔接行动项；审查者注
  • 网络运营者安全义务合规审查报告给律师内部或客户
    报告头（运营者名称、业务类型、审查日期、审查模式）；义务履行评估表（实名制验证、日志留存不少于六个月 [待验证]、防入侵技术措施、重要数据备份与加密、访问控制与最小权限、应急预案与演练、违法信息处置机制、行业特殊义务，每项给合规状态、风险等级、主要发现、整改建议）；风险摘要；优先整改项（整改项 + 责任人 + 完成期限）；审查者注
  • 个人信息收集合规审查报告给律师内部或客户
    报告头（主体名称、产品/服务、审查日期、审查范围、主要合法性基础、是否处理敏感个人信息、审查模式）；合规框架适用（PIPL 优先 + CSL 补充及理由）；收集合规性评估表（按信息类别列合法性基础、告知完整性、最小必要合规、风险等级）；告知同意机制评估（隐私政策、同意机制、撤回机制、敏感个人信息单独同意）；用户权利保障评估（查阅、更正、删除、账户注销）；深度 PIA 触发建议；审查者注

04开始前

前置条件

  • 读取 data-compliance/CLAUDE.md：是否为 CIIO、所属行业、等级保护定级倾向、数据安全立场、整体合规偏好、合规团队规模、文书风格与工作产物标题；并引用 data-compliance/skills/_shared/ 下的引用库、引用规范、配置读取契约三个文件
  • 配置缺失或为 [PLACEHOLDER] 时进入临时模式：CIIO 状态不明则按 CIIO 处理（从严推定）；等保定级遇不确定时建议按上一级定级（宁高勿低）；合规偏好默认平衡型；所属行业不明时所有行业特殊义务均标 [行业监管 flagged — 须核实]；所有基于临时模式的判断标注 [临时模式 — 配置数据合规档案以获得定制输出]，并建议先运行 /data-compliance:cold-start-interview 后重跑
  • 触发任何步骤前先确认 CIIO 立场：是 CIIO → 步骤 2 为必选、等保定级须≥三级 [待验证]、数据本地化须落实 [待验证]、出境须安全评估（DSL 第31条）；否 CIIO → 步骤 2 可跳过仅做风险评估、等保按实际系统性质定级；不确定 → 按 CIIO 处理并建议向行业主管部门确认认定情况 [行业监管 flagged]
  • 读取所属行业，识别行业主管部门及额外关注点，后续所有输出带 [行业监管 flagged] 标记
  • 步骤顺序：步骤 1 的等保级别是步骤 2 关基叠加的前提；步骤 2 的 CIIO 识别影响步骤 3 的义务强度；步骤 4 与步骤 3 相互补充；各步骤均可脱离整个流程单独触发

硬性规则

CIIO 立场确认
读取 CLAUDE.md「是否为关键信息基础设施运营者（CIIO）」字段：是 → 关基保护步骤必选、等保须≥三级 [待验证]、数据本地化须落实 [待验证]、出境须安全评估（DSL 第31条，已核实）；否 → 关基步骤可跳过仅做风险评估；不确定 → 临时模式按 CIIO 处理，建议向行业主管部门确认 [行业监管 flagged]
关基识别提示
以下五类高风险组织须特别评估关基认定可能性（CSL 第31条）：金融（银行/证券/保险核心系统，建议主动向行业主管部门了解认定情况）；电信（基础电信运营商，工信部监管）；能源/交通/水利（国家发改委/交通部等）；医疗/公共服务（卫健委等）；大型互联网平台（须评估是否触发「信息服务」类关基）。均标 [行业监管 flagged]
行业监管识别
按 CLAUDE.md「所属行业」识别额外关注与主管部门：金融 → 金融行业网络安全监管规定、金融数据分级（人民银行/金融监管总局）；电信 → 电信网络安全要求、电话实名制（工信部）；医疗健康 → 医疗健康数据特别保护（国家卫健委）；能源/交通 → 关基认定风险高、工控系统等保 2.0 扩展要求（国家发改委/交通部）；教育 → 未成年人个人信息特别保护（教育部）；互联网/平台 → App 专项合规、算法推荐、用户画像（网信办/工信部）。均标 [行业监管 flagged]
出境合规衔接
检查中发现出境场景须衔接出境评估：CIIO 向境外提供重要数据 → /data-compliance:security-assessment-filing，强制安全评估（DSL 第31条，已核实）；CIIO 向境外提供大规模个人信息 → /data-compliance:pathway-determination + /data-compliance:security-assessment-filing，安全评估 [待验证]；非 CIIO 向境外提供个人信息 → /data-compliance:pathway-determination，三路径之一（PIPL 第38条，已核实）；数据本地化违规（境外存储境内数据）→ 优先走 /data-compliance:cii-protection，须立即整改 [待验证 — CSL第37条]
个人信息收集衔接 PIA
步骤 4 发现以下情形须触发深度评估：处理敏感个人信息（PIPL 第28条）→ /data-compliance:trigger-consent-basis；自动化决策场景（PIPL 第24条）→ /data-compliance:trigger-consent-basis；需要完整 PIA 报告 → /data-compliance:pia-generation；数据映射与最小必要深度评估 → /data-compliance:data-mapping-necessity
目的地与特权检查
向监管部门提交的报告（等保备案材料、关基安全评估报告、安全事件报告）不受律师-当事人特权保护，须使用正式报告格式；内部法律分析以律师工作产物格式标注（CLAUDE.md「工作产物标题」）；外部网络安全合规报告须确认目的地在特权保护圈内
时效性提示
CSL 第21条、第31条起已核实可引用（建议复核）；等保定级标准 GB/T 22240 与等保 2.0 基本要求 GB/T 22239 的编号与版本 [待验证]；关基条例具体条款 [待验证] [行业监管 flagged]；实名制/日志留存具体条款 [待验证]；网信办/工信部 App 相关监管规定更新频繁，须每季度复核 [时效性 flagged]
用户陈述合理性检查
用户口述系统等级（如「我们是二级」）、具体等保条文号、测评有效期/频率、日志留存期限、关基认定细节时，不直接采信：询问依据、核实有无书面定级报告与备案证明，并标 [前提 flagged — 需验证] 或 [待验证 — 须核实最新规定]

05执行步骤

共 4 步，按执行顺序。每步旁边（窄屏在步骤说明之后）是请律师核对的内置假设，可逐条复制。页面里的英文标记见首页「标记与术语」。

  1. 网络安全等级保护

    /data-compliance:mlps-grading可单独运行

    对网络运营者运营的每个系统完成等保定级判断、备案与测评状态核查、等保 2.0 安全建设差距评估，形成等保合规状态报告；等保是关基保护的基础层。

    请律师核对

    • 核对 1.1初步定级表把金融核心、大型互联网平台、政府公共服务、医疗卫生系统一律预设为「第三级起」，是否符合贵所实践？
    • 核对 1.2「大型互联网平台（超过一定用户规模）」没有给出用户规模数字，是否需要补一个门槛？
    • 核对 1.3临时模式「宁高勿低」按上一级定级的保守策略，可能增加客户合规成本，是否接受？
    • 核对 1.4第三级每年测评、第四级每半年测评、日志六个月等数字全部标 [待验证]，请律师确认后决定是否去掉标记。
    • 核对 1.5监管机构定位写「等保由公安部主管，网信办统筹协作」，并提示行业主管部门可能有叠加要求，是否同意？

    做法

    1. 读取 CLAUDE.md 中的 CIIO 身份、所属行业、等级保护定级倾向、数据安全立场；「等级保护定级倾向」为 [PLACEHOLDER] 时启用临时模式，按保守定级策略，遇不确定等级建议按上一级定级（宁高勿低），标 [临时模式 — 配置数据合规档案以获得定制输出]。
    2. 以等保五级框架为基准：按「受侵害客体（公民法人权益 / 社会秩序 / 公共利益 / 国家安全）」与「侵害发生后的危害程度（一般 / 严重 / 特别严重）」两个维度交叉确定等级 [待验证 — 具体定级标准条款]。
    3. 采集七项系统信息：系统名称与功能描述、用户规模（注册数/活跃数）、处理数据类型（个人信息/重要数据/敏感数据/一般数据）、系统行业归属、是否已完成等保定级、是否为 CIIO 或承载关基、境外访问或跨境数据流。
    4. 对照「初步定级判断表」按系统类型给出建议最低等级；用户口述等级（如「我们是二级」）时做合理性检查，询问定级依据并核实有无书面定级报告和备案证明，标 [前提 flagged — 需验证]。
    5. 核查定级备案四阶段：定级申报（填写定级报告，建议邀请测评机构辅助）→ 专家评审（第三级及以上，[待验证是否强制]）→ 向所在地公安机关备案并取得「备案证明」[待验证具体备案部门与材料清单] → 公安机关审核（第三级及以上重点审核 [待验证]）；核对备案材料：定级报告、安全技术措施说明、主要负责人签字的责任声明 [待验证]。
    6. 按等保 2.0 十个安全要求维度（安全物理环境、安全通信网络、安全区域边界、安全计算环境、安全管理中心、安全管理制度、安全管理机构、安全管理人员、安全建设管理、安全运维管理）逐项评估「符合 / 部分符合 / 不符合」；系统部署在云、支持移动端、含物联网设备或属工控系统时，加查对应的等保 2.0 扩展要求 [待验证]。
    7. 核查等级测评：第三级每年一次、第四级每半年一次 [待验证具体频率]；首次测评在定级备案后开展；须委托公安部认可的等保测评机构，不得自行测评；查看测评结论（优/良/中/差 [待验证]）、不符合项整改清单及整改验证情况。
    8. 判断系统是否涉及关键信息基础设施，是则同步触发 /data-compliance:cii-protection 叠加关基义务；系统发生功能变更、用户规模大幅增加、新增重要数据处理时，评估是否触发重新定级。
    9. 信息不足以判断等级时，列出缺失信息（业务功能/用户规模/数据类型）要求补充，不猜测；跨省多地系统的备案管辖只描述基本原则（通常向系统主要运营地公安机关备案 [待验证]）并标明须核实。
    10. 按输出模板生成报告：等级认定表、合规状态表（每项给关键/高/中等/低风险与整改建议）、风险摘要、下一步行动；审查者注写明等保定级标准与测评频率均待验证、国标须核实最新版本 [时效性 flagged]。

    内置规则

    请律师核对

    • 核对 2.1本步骤对 CIIO 个人信息出境有两种口径（本地化表：确需出境须安全评估；出境表：一般规模按三路径判断），请律师定一个统一立场。

    • 核对 2.3临时模式按 CIIO 从严推定会把九项关基义务全部列为待整改，是否接受这一保守默认？

    做法

    1. 读取 CLAUDE.md 中的 CIIO 身份、所属行业、数据本地化立场、重要数据出境立场、合规团队规模；CIIO 为 [PLACEHOLDER] 或「不确定」时启用临时模式：按 CIIO 处理、从严推定，标 [临时模式 — 按 CIIO 从严推定]，并建议向行业主管部门确认认定情况。
    2. 按 CSL 第31条列举的八类重点行业领域（公共通信和信息服务、能源、交通、水利、金融、公共服务、电子政务、其他）判断行业归属；核心标准是：网络设施或信息系统一旦遭到破坏、丧失功能或数据泄露，可能严重危害国家安全、国计民生或公共利益。
    3. 梳理关基认定四阶段 [待验证 — 条例具体条款]：行业主管部门（保护工作部门）认定 → 通知运营者 → 运营者配合认定并提供材料（不配合属违法）→ 认定结果通报国家网信部门和公安部门；确认客户是否已收到认定通知并归档。
    4. 用五项自查表评估认定风险：是否属于第31条列举行业；系统中断后果严重性（影响大量用户如数百万以上或关键公共服务）；是否已收到认定通知；是否被列为重要数据或国家核心数据处理者；是否为其他已认定关基系统的关键技术供应商。高风险信号出现时升级处理并标 [行业监管 flagged]。
    5. 逐项核查关基运营者九项特别义务 [待验证]：设置专门安全管理机构并配专职人员；设置网络安全负责人；重要岗位人员安全背景审查；每年至少一次安全检测与风险评估并邀请保护工作部门或其指定机构；制定应急预案并定期演练；重大网络安全事件及时向保护工作部门和公安机关报告；采购可能影响国家安全的网络产品和服务申报网络安全审查；在等保第三级及以上基础上加码；配合保护工作部门的检查、指导、监督。
    6. 用「关基运营者 vs 一般网络运营者」七行对比表标出义务差异与风险等级。
    7. 审查数据本地化：识别 CIIO 在境内运营中收集或产生的个人信息完整范围，和参照行业目录识别的重要数据范围 [行业监管 flagged]；确认主要存储位置在境内（含云存储）；核查境外系统备份/同步、境外第三方处理或 SaaS 服务是否构成出境 [待验证]。
    8. 审查出境安全评估：CIIO 向境外提供重要数据 → 必须安全评估（DSL 第31条，已核实），衔接 /data-compliance:security-assessment-filing；向境外提供大规模个人信息 → 须安全评估（适用门槛 [待验证]），衔接 /data-compliance:pathway-determination + security-assessment-filing；向境外提供一般规模个人信息 → 按 PIPL 第38条三路径判断，但 CIIO 不适用标准合同的具体规则 [待验证]。
    9. 用户称「标准合同路径已申报，关基出境不用评估」时予以纠正：CIIO 重要数据出境不适用标准合同替代安全评估（具体规则须验证），标 [前提 flagged — 需验证]；用户口述关基认定条件或义务清单时做合理性检查，具体条款标 [待验证]。
    10. 发现有境外数据备份但未评估出境 = 关键风险，提示触发 /data-compliance:security-assessment-filing；供应链产品采购涉及境外厂商时，提示评估网络安全审查申报要求 [待验证 — 须核实审查办法最新版]。
    11. 生成报告：关基识别评估（行业归属、系统中断后果、数据敏感性、认定风险）、关基义务履行状态（八项）、数据本地化与出境评估、衔接行动项（出境场景触发 security-assessment-filing；等保复核 mlps-grading 确认≥三级；运营者一般义务 operator-obligations）。

    内置规则

    • 关基认定须通过行业主管部门确认，不可自行认定或否认。
    • 未被认定为 CIIO 但属于 CSL 第31条列举行业：仍须评估关基认定风险，标 [行业监管 flagged]；正式被认定前按等保基础义务履行。
    • CIIO 系统同时承载一般业务数据：按最严格标准（关基保护）统一处理，分类存储可降低部分合规风险。
    • 外资企业在华关基运营：须遵守中国关基保护规定，外资身份不影响关基义务 [待验证]。

    • 义务对比表风险等级：等保≥三级 — 高；专门安全机构 — 关键；定期安全检测评估 — 关键；应急演练 — 高；采购安全审查 — 关键；数据本地化 — 关键；出境限制 — 关键。
    • 数据本地化表：CIIO 收集的个人信息须境内存储 [待验证 — CSL第37条]，确需出境须安全评估 [待验证]；CIIO 产生或处理的重要数据须境内存储 [待验证 — CSL第37条]，出境须安全评估（DSL第31条，已核实）；一般业务数据无强制本地化，走 PIPL 三路径。
    • 所有 CIIO 出境场景均须首先评估是否触发安全评估申报义务；不得以「合同所必需」「标准合同」等一般路径替代强制安全评估 [待验证]。
    • 监管格局：各行业保护工作部门（金融 → 人行/金融监管总局；能源 → 发改委/能源局；电信 → 工信部）负责认定与监管，网信办统筹协调，公安部负责网络安全检查 [行业监管 flagged]。

    9. 审查配合监督检查义务（提供数据、日志、文件，配合技术检测，提供场地设施，在法定范围内协助、不得拒绝阻挠 [待验证]）与违法信息处置义务（发现禁止发布或传输的信息立即停止传输、保存记录、向主管部门报告；建立监测处置机制 [待验证]）。
    10. 核查电信/金融/医疗行业特殊义务 [行业监管 flagged]；输出义务履行评估表（八项）、风险摘要、优先整改项（整改项 + 责任人 + 完成期限），审查者注写明第21条已核实、其他义务条号待验证 [时效性 flagged]。

    内置规则

    在网络运营者层面审查个人信息收集使用合规：合法正当必要原则、告知同意机制、最小必要原则、用户权利保障及 CSL 与 PIPL 衔接，并判断是否需转入深度 PIA。

    请律师核对

    • 核对 4.1捆绑同意在本步骤定为关键风险，但 PIA 流程的 trigger-consent-basis 和 CLAUDE.md 风险校准都定为高风险，请统一。

    • 核对 4.5员工个人信息可援引「合同所必需」[待验证] 的立场是否同意？

    做法

    1. 读取 CLAUDE.md 中的是否处理敏感个人信息、敏感数据政策、整体合规偏好、所属行业；「敏感数据政策」为 [PLACEHOLDER] 时启用临时模式：按严格门槛标记所有常见敏感类别（生物识别/医疗/金融账户/未成年人）并触发单独同意提示，标 [临时模式 — 配置数据合规档案以获得定制输出]。
    2. 先定适用框架：CSL 与 PIPL 同为全国人大常委会制定，后法 PIPL 优先、特别法优先；PIPL 适用范围更广、规则更完整，个人信息保护事项优先适用 PIPL，CSL 网络运营者规定只在 PIPL 未覆盖的边界情形补充适用；执法机关同为网信办/公安，协同执法。
    3. 合法正当必要审查四步：梳理收集的个人信息清单（框架级审查，深度映射交 /data-compliance:data-mapping-necessity）→ 判断每项信息的合法性基础（PIPL 第13条七类）→ 验证必要性（是否与提供服务直接相关、是否超出服务需要）→ 检查正当性（隐私政策真实清晰、收集行为不欺骗误导）。
    4. 告知同意审查六项：隐私政策存在性；内容完整性（处理目的、信息类型、保存期限、接收方）；同意自愿性（注册同意与服务可分离，合同所必需的不须另取同意）；同意明确性（不预先勾选、不默许）；撤回同意便捷性；App 权限申请须告知目的且不得与功能无关。按风险信号表定级。
    5. 敏感个人信息单独同意核查（PIPL 第28-29条）：生物识别（人脸/指纹/声纹）、医疗健康、金融账户、行踪轨迹、宗教信仰与特定身份须单独同意且不得与一般个人信息捆绑；不满十四周岁未成年人信息须监护人同意并制定专门处理规则。深度审查转 /data-compliance:trigger-consent-basis。
    6. 最小必要审查五维：字段必要性（非必要字段删除或改可选）；频率必要性（不得持续获取位置等超频采集）；范围必要性（导航只需当前位置不需历史轨迹）；保存期限必要性；功能外收集（申请无关权限即违反）。执行 App/产品五项最小必要清单：权限与功能逐一对应、非核心功能敏感权限可拒绝且不影响核心服务、字段逐一验证、保存期限写入隐私政策、到期自动删除或定期清理。[行业监管 flagged — 须核实网信办 App 最小必要规定]
    7. 用户权利审查（PIPL 第44-47条已核实；可携带权 [待验证条号]）：查阅入口（账户设置/隐私中心）、更正请求响应、删除请求响应（第47条法定情形）、撤回同意后停止处理、账户注销后删除或匿名化 [待验证注销时限]、响应时限 [待验证]。
    8. 填写 CSL/PIPL 衔接对照表七项：合法性基础、告知义务、同意、最小必要、用户权利、泄露补救（PIPL 第57条 [待验证]）、执法机关，每项注明 PIPL 优先或 PIPL + 行业规定。
    9. 处理典型情形：用户称「已有隐私政策无需审查」→ 逐项核对告知要点 [前提 flagged]；口述同意合规但存在捆绑 → 指出与第14条不符、建议分离设计；称「平均用时不到一秒的同意弹窗符合要求」→ 指出知情同意须有合理阅读时间；收集与服务无明显关联的信息 → 关键风险、建议删除字段或明确必要性；询问是否需要 DPO → 解释 PIPL 第52条 [待验证] 达到规定规模须指定负责人；App 权限超范围 → 关键风险、立即整改（网信办 App 专项整治执法活跃）。
    10. 输出报告并给出深度 PIA 触发建议：处理敏感个人信息（第28条）、告知同意机制重大瑕疵、自动化决策（第24条）→ /data-compliance:trigger-consent-basis；跨境提供个人信息 → /data-compliance:pathway-determination。审查者注提示 App 相关规定须每季度复核 [时效性 flagged]。

    内置规则

    • 风险信号定级：无隐私政策或难以访问 = 关键；内容笼统缺乏实质 = 高；捆绑同意（强制同意注册/营销）= 关键；预先勾选同意框 = 关键；撤回途径繁琐或需申请审批 = 高；超范围权限（如记事本申请通讯录）= 关键。
    • 同意四要件（PIPL 第14条）：自愿（不捆绑、可与服务分离）；明确（不默许、不预先勾选）；知情（告知充分）；可撤回（便捷撤回且撤回后不得遭受不合理后果）。
    • 告知内容（PIPL 第17条 [待验证]）：处理者名称与联系方式、处理目的与方式、个人信息类型与保存期限、行使权利的方式途径及其他应告知事项。
    • 仅收集匿名化数据：匿名化（而非去标识化/假名化）后不属于个人信息，须核实匿名化真正不可逆 [待验证标准]。
    • 受托处理者场景：受托方按处理者指示处理，合规义务主要在委托方，受托方须签订数据处理协议。
    • 员工个人信息（HR 场景）同样适用 PIPL，劳动合同场景可援引合同所必需作为合法性基础 [待验证]。
    • 直接营销：单独同意或退出权（opt-out）的适用规则 [待验证 — 须核实 PIPL 营销场景具体规定]。
    • 算法推荐场景涉及 PIPL 第24条自动化决策，须提供非针对个人的选项和拒绝权。
    • 用户信息存储期满触发第47条主动删除义务，须确认自动化删除机制。
    • 泄露事件触发 PIPL 泄露通知义务 [待验证 — 第57条]，原文写「升级至 risk-escalation」。

08交付前检查

  • 等保：已梳理所有需纳入等保管理的系统并初判等级；第二级及以上系统已向公安机关备案并取得备案证明 [待验证]；第三级及以上已委托认可测评机构测评 [待验证]；不符合项已形成整改计划；等保 2.0 各维度逐一检查；云/移动/物联网/工控场景已对照扩展要求 [待验证]；定级报告、备案证明、测评报告归档；涉关基已同步触发关基保护步骤；系统变更后已评估是否重新定级
  • 关基：已自查是否属于 CSL 第31条列举领域；认定通知已归档；专门安全管理机构与安全负责人已设 [待验证]；关键岗位人员审查已完成 [待验证]；年度安全检测与风险评估计划已制定执行 [待验证]；应急预案已制定并演练 [待验证]；个人信息与重要数据本地化存储已落实 [待验证 — CSL第37条]；出境场景已识别是否须安全评估（DSL 第31条）；供应链采购已评估网络安全审查申报 [待验证]；与保护工作部门和公安机关的事件报告机制已建立 [待验证]
  • 运营者义务：注册/登录实名验证且未实名用户无法获取相关服务 [待验证]；实名信息访问受限防泄露；网络访问/操作/安全日志留存≥六个月 [待验证] 且防篡改、可供监管查阅；防病毒/防入侵/漏洞管理已部署并更新；重要数据定期备份且恢复已测试；最小权限、特权账户管理、离职账户注销；内外部传输加密；应急预案文档化并定期演练 [待验证]；内部升级与监管报告时限明确 [待验证]；违法信息监测处置机制已建立 [待验证]；电信/金融/医疗行业特殊义务已核查 [行业监管 flagged]
  • 个人信息收集：每类收集均有 PIPL 第13条合法性基础；隐私政策公示且内容完整（目的/方式/类型/保存期限/接收方）；同意自愿、明确、知情、不捆绑；撤回便捷且撤回后停止处理；敏感个人信息已取得单独同意（第28-29条）；App 权限与功能逐一对应；保存期限已设置并到期删除；查阅/更正/删除机制已建立；注销后删除或匿名化；行业特殊规定已核查 [行业监管 flagged]
  • 每份报告注明审查模式（正常/临时）、审查者注、国标与条号的 [待验证] 标记及 [时效性 flagged] 提示；所有法律引用带来源标签

09何时暂停或升级

  • CIIO 状态不确定：临时模式按 CIIO 处理，并建议向行业主管部门确认关基认定情况 [行业监管 flagged]
  • 发现系统可能属于关基但未被认定：标 [行业监管 flagged]，提示触发 /data-compliance:cii-protection 评估认定风险；关基认定须由行业主管部门确认，不可自行认定或否认
  • 以下情形判为关键风险、立即建议整改：第三级系统已定级但未测评；日志完全缺失；有境外数据备份但未评估出境；境外存储境内数据（本地化违规）；收集与服务无明显关联的个人信息；App 权限超范围申请。日志缺失等重大隐患还须评估是否主动与监管部门沟通
  • 发现出境场景：转 /data-compliance:pathway-determination 或 /data-compliance:security-assessment-filing；CIIO 不得以「合同所必需」「标准合同」等一般路径替代强制安全评估 [待验证]
  • 发现敏感个人信息、自动化决策、告知同意重大瑕疵或需要完整 PIA：转 /data-compliance:trigger-consent-basis、/data-compliance:data-mapping-necessity 或 /data-compliance:pia-generation
  • 遭遇监管调查或检查：按法定要求配合、不超范围；保留相关日志和文件；升级至法务总监/外部律师
  • 个人信息泄露事件：触发 PIPL 泄露通知义务 [待验证 — 第57条]，原文写「升级至 risk-escalation」（SKILL.md 未规定具体升级路径）
  • 用户口述等级、条文号、留存期、测评频率、关基认定细节：合理性检查，标 [前提 flagged — 需验证] 或 [待验证]，不直接写入结论
  • 向监管提交的报告不受特权保护，须用正式报告格式；外部合规报告须确认目的地在特权保护圈内
