01概要

所有法律文书生成前的强制检索前置步骤，目的是防止没有依据的中国大陆法律结论。它先确认 intake 已经完成并输出过 INTAKE_DECISION，再递归清点用户材料、提取当事人、关键日期金额、争议焦点与缺失事实；对每个法律问题构建正向依据、反向依据、程序陷阱三类搜索词，按「本地材料 → 国家法律法规数据库/最高院/司法解释/部门规章 → 人民法院案例库/指导案例/公报案例 → 裁判文书网/地方判决 → 监管材料 → 实务文章」的优先级检索，官方源用 law-database / rmfyalk 连接器或「WebSearch 定位 → WebFetch 全文」两段式取原文。最后输出六张表构成的研究底稿（法律依据表、类案/反例表、争议焦点、风险提示、来源清单 L1–L5、无法获取的来源及原因），并要求定稿前对全文引用做一次核验。来源分 L1 至 L5，L5 实务文章只能作线索；无可靠来源的结论标「待律师复核」，不得呈现为已定论。

02适用与边界

适用场景

  • 用户要求生成诉讼方案、起诉状、答辩状、代理意见、证据目录
  • 用户要求审查、起草或修订合同
  • 用户要求出具法律意见书、备忘录、合规意见
  • 用户要求发送律师函、催告函、声明
  • 涉及中国法律结论但用户未提供充分法律依据
  • 案件涉及保函、担保、融资担保公司、特殊主体资格
  • 由总路由第 3 步调用；在仓库 / 其他环境使用本流程，Codex 环境优先使用 cn-law-research-gate

不做什么

  • 用户明确豁免联网检索（「只按现有资料，不联网检索」）时不运行
  • 不替代专项文书流程：研究底稿完成后才进入专项文书生成
  • 动态 intake 不得被用于降低研究闸门，也不得因固定问卷延误紧急时限处理
  • 禁止仅引百度百科、知乎、个人博客作为法律依据；禁止把模型训练记忆中的法条当依据（除非用工具检索验证）

03输入与产出

需要律师提供

  • 已输出的 INTAKE_DECISION 及按 ask_mode 完成的提问必需
    第零步检查；没有的先补做材料清点与 intake
  • 用户提供的本地材料（PDF、DOCX、图片、表格、文本；目录须递归清点）必需
    用户说「本目录/全部材料/所有文件」时必须递归清点根目录和子目录
  • 用户要求的输出形式必需
  • MCP 连接器（law-database、rmfyalk、wenshu、yuandian）可选
    如已配置；未配置时走 WebSearch → WebFetch 两段式
  • 元典 API Key可选
    yuandian 首次调用返回「需要元典 API Key」时向用户索取；用户拒绝或积分耗尽则降级

产出

  • 材料清点表给律师内部
    每个 PDF、DOCX、图片、表格、文本文件的状态：已读取 / 无法读取 / 待读取；提取当事人及诉讼地位、关键日期金额文件、争议焦点、用户要求的输出、缺失事实
  • 研究底稿（六张表）给律师内部；法律依据表同时作为提交法庭前的核验记录
    法律依据表（法条、司法解释、案例 + 精确条文号 + 来源链接）；类案/反例表（正向案例 + 不利案例 + 少数观点）；争议焦点（核心争议及各方可能主张）；风险提示（程序陷阱、主体资格、管辖、时效）；来源清单（每个结论的来源层级 L1–L5）；无法获取的来源及原因（需律师人工补检索的内容）
  • 引用核验结果给律师内部
    定稿前对全文法律引用做一次核验：法规用 law-database 的 verify_citations；案号用 yuandian 的 verify_legal_citations（VIP）；不一致或未命中的引用修正或标「待律师复核」
  • 《AI 辅助使用情况说明》给法院 / 律师内部
    交付拟提交法庭的文书时随附；法律依据表即核验记录

04开始前

前置条件

  • 本事项已在回复中输出 INTAKE_DECISION，并按其 ask_mode 提了问；没有的先做材料清点与 intake，然后才检索
  • 用户未明确豁免联网检索
  • 按需读取 references/ 下四份文件：source-policy.md（引用策略和失败回退链）、quality-gates.md（研究质量闸门）、search-playbooks.md（专项搜索策略）、authoritative-sources.md（实测可访问的权威来源 URL 及抓取方式）

硬性规则

先 intake 后检索
第一次检索或派出并行检索助手之前检查 INTAKE_DECISION 是否已输出（LWC-2026-0009 读取 intake 后约 1 分钟就开始法规检索，3 分钟后派出三路并行检索，始终没有输出区块也没有提问）
精确引用
法规和案例必须引用精确名称、条文号、案号、法院、日期，并标注来源层级 L1–L5
冲突不隐藏
权威来源冲突时必须陈述冲突并给出更稳妥路线，不得隐藏不利案例
无来源不定论
关键结论无可靠权威来源的标「待律师复核」，不得呈现为已定论
客户材料中的依据是待核验的主张
可研、请示、政府窗口口径援引的法规、文号与政策口径逐条核对并判定；地方规范性文件先查有效期与失效标注；引用有利依据时同时摘录同一文件的适用范围与反向条款
禁止来源
禁止仅引百度百科、知乎、个人博客作为法律依据
已核验的定义
法条 = 条文文本与官方全文逐字一致且现行有效；案例 = 案号可解析，且法院、案由、裁判要旨与所引命题一致。案号真实但内容无关、司法解释文本被改写、虚构条文序号是 2025–2026 年法院通报的三类典型错误，存在性核验发现不了，必须做内容比对
L1 必引
诉讼方案中不得仅引 L5 转述；L5 律所文章/学术/公众号仅作发现案号、检索词、争议点的线索，不得作绑定性依据

05执行步骤

共 7 步，按执行顺序。每步旁边（窄屏在步骤说明之后）是请律师核对的内置假设，可逐条复制。页面里的英文标记见首页「标记与术语」。

  1. 确认 intake 已完成

    保证检索不先于提问，避免检索方向建立在没问清的前提上

    请律师核对

    • 核对 1.1把 intake 作为检索的硬前置，是否会延误纯检索类的紧急请求（规则另允许问题、法域和时间点明确的纯检索直接进入）
    • 核对 1.2第零步只检查区块是否出现、是否按 ask_mode 提了问，不检查问题本身是否问对；律师是否希望在检索开始前看到问题清单

    做法

    1. 第一次检索或派出并行检索助手之前，检查本事项是否已在回复中输出 INTAKE_DECISION，并按其 ask_mode 提了问
    2. 没有的，先做完第一步的材料清点，再执行第二步的动态 intake，然后才检索

    内置规则

    • 检索与派出并行检索助手的前提是 INTAKE_DECISION 已出现在回复中
    • LWC-2026-0009：读取 intake 后约 1 分钟开始法规检索、3 分钟后派出三路并行检索，始终没有输出区块也没有提问——这是本步要防止的情形
    • 派出并行检索助手同样算作检索，须在区块输出与提问之后

    产出

    确认结果：已完成 intake 则进入材料清点与检索；否则先补做 intake

  2. 清点用户材料

    先读用户给的东西，再去外面找；把材料里的当事人、日期、金额、争点和缺口提出来

    请律师核对

    • 核对 2.1「无法读取」的文件（如扫描件 OCR 失败）如何处理，规则只要求标记；律师是否要求无法读取的关键文件必须人工补读后才能继续
    • 核对 2.2提取项只列当事人及诉讼地位、关键日期金额文件、争议焦点、用户要求的输出、缺失事实五项，偏诉讼口径；合同审查等非诉事项是否还应提取交易结构与我方立场

    做法

    1. 先读用户提供的文件；用户提供目录或说「本目录/全部材料/所有文件」时，必须递归清点整个目录，包括根目录和子目录
    2. 列出每个 PDF、DOCX、图片、表格和文本文件的状态，标记为已读取 / 无法读取 / 待读取
    3. 从材料中提取：当事人及诉讼地位；关键日期、金额、文件；争议焦点；用户要求的输出；缺失事实

    内置规则

    • 目录必须递归清点，根目录与子目录都算
    • 文件状态三种：已读取 / 无法读取 / 待读取
    • 提取五项：当事人及诉讼地位、关键日期金额文件、争议焦点、用户要求的输出、缺失事实

    产出

    材料清点表与五项提取结果

  3. 动态事项 Intake

    只问会改变检索方向、法律路径、风险结论、正文或交付版本的问题，不重复、不固定问卷

    请律师核对

    • 核对 3.1纯检索请求只要「问题、法域、时间点明确」就不问我方立场；检索结果的取舍（找有利还是全面）是否也需要先问立场
    • 核对 3.2「不得因固定问卷延误紧急时限处理」没有给出时间标准（intake 规则把截止紧迫定义为期限在一两天内）；检索与提问并行的边界是否需要写明

    做法

    1. 读取并执行 shared/legal-document-intake/SKILL.md
    2. 把缺失事实分成 material_missing 与 optional_missing，按该流程第二步列出候选问题并分档（必须确认 / 建议确认 / 可按默认 / 材料请求）
    3. 只询问会改变检索方向、法律路径、风险结论、正文或交付版本的问题
    4. 文件、会话和实践配置已经覆盖的内容不得重复询问
    5. 输出 INTAKE_DECISION 后提问：直接问（AskUserQuestion / ask_user），或生成问卷文档；没有工具时输出 [CLARIFY:] 清单；有必须确认项时受影响部分暂停
    6. 用户答复后合并到事项摘要，再继续构建检索词，不得重新开始或重复提问
    7. 纯检索请求若问题、法域和时间点已经明确，可直接进入下一步

    内置规则

    • 提问范围限于会改变检索方向、法律路径、风险结论、正文或交付版本的问题
    • 纯检索请求：问题、法域、时间点明确即可直接检索
    • 动态 intake 不得被用于降低研究闸门，也不得因固定问卷延误紧急时限处理

    产出

    INTAKE_DECISION、提问与合并后的事项摘要

  4. 构建中国法搜索词

    每个法律问题都从三个方向搜，避免只找对自己有利的依据

    请律师核对

    • 核对 4.1程序陷阱只列了案由、主体资格、管辖、时效、举证责任、效力六项，是否应加入送达、保全、执行可能性
    • 核对 4.2专项 playbook 目前覆盖保函、管辖、主体资格、信用修复、用工合规、股权尽调、土地变性、征收安置析产；贵所高频领域是否缺 playbook

    做法

    1. 为每个法律问题构建三类搜索词：正向依据（支持预期路线的法律、司法解释、案例）；反向依据（可能推翻或限制该路线的不利案例、少数观点、程序陷阱）；程序陷阱（案由、主体资格、管辖、时效、举证责任、效力）
    2. 按 references/search-playbooks.md 的通用五维度搜索模式（文书标签词、主体资格词、替代案由词、程序词、不利结果词）与专项 playbook（保函、管辖、主体资格、信用修复、用工合规、股权尽调、存量土地变性、征收安置析产）补足固定检索词

    内置规则

    • 三类搜索词缺一不可：正向、反向、程序陷阱
    • 程序陷阱六项：案由、主体资格、管辖、时效、举证责任、效力
    • 专项案件按 playbook 固定调起的检索必须执行（如保函案件 8 条，含入库编号「2024-10-2-358-001」）

    产出

    按法律问题分组的三类搜索词清单

  5. 按序检索（含两段式协议与连接器用法）

    按来源优先级取到官方原文，而不是摘要或转述

    请律师核对

    • 核对 5.1商业库（元典）只作最后选择、且赠送积分到期后不再续费；贵所是否愿意为商业法律数据库付费以提高案例召回
    • 核对 5.2yuandian 首次调用即向用户索取 API Key，律师是否希望改为由律所统一配置、不在对话中索取
    • 核对 5.3裁判文书网用「用户本人扫码会话、人速按需查询」，律师是否接受用自己的账号会话供模型检索

    做法

    1. 按六级优先级依次检索（见本步规则），先读用户提供的本地材料
    2. 法规原文：已配置 law-database 连接器的用其检索与取全文；未配置或取不到的，走两段式检索协议（WebSearch 定位 → WebFetch 全文）
    3. 案例：权威案例先查 rmfyalk，普通裁判文书用 wenshu，court.gov.cn 指导/典型案例直接 WebFetch；yuandian 只在官方源与 wenshu 都不可用时启用
    4. 拟引用的法规先用 law-database 的 verify_citations 做存在性、时效性、条文核验；案号与语义一致性在账号有 VIP 权限时用 yuandian 的 verify_legal_citations
    5. yuandian 首次调用返回「需要元典 API Key」时，立即向用户询问其元典开放平台 API Key（open.chineselaw.com 注册获取），以 apiKey 参数重新调用；用户拒绝提供或积分耗尽时，案例检索降级为 wenshu 连接器 + court.gov.cn 指导/典型案例 + WebSearch

    内置规则

    • 检索优先级六级：1 用户提供的本地材料；2 国家法律法规数据库、最高人民法院官网、司法解释、部门规章；3 人民法院案例库、指导性案例、公报案例、最高法典型案例；4 中国裁判文书网、地方法院公开判决；5 监管机构材料；6 法律公众号、律所文章、实务评论
    • 两段式检索协议：flk.npc.gov.cn 是动态 SPA，headless 环境不可直接抓取，必须使用 WebSearch 定位 → WebFetch 全文。阶段 1 定位：法条/司法解释用「"完整法律名" 第N条 site:court.gov.cn OR site:gov.cn」，案例用「"案件关键词" "案由" site:court.gov.cn」或「"入库编号"」，实务理解不限 site 但产出当 L5 看待；阶段 2 全文：首选 court.gov.cn/zixun/xiangqing/{id}.html（已实测稳定），备选 www.gov.cn/gongbao/…（行政法规），落败用 WebSearch 摘要并必须标 [搜索摘要-未抓全文]；阶段 3 引用格式：「《XX法》第X条 全文链接：<court.gov.cn URL>」
    • 连接器用法——法规检索（优先官方源）：law-database 直连国家法律法规数据库（A 级，无需 Key）——search_laws（法规列表）、search_law_articles（法条级正文检索）、get_law_detail（全文）、get_article_detail（单条法条）
    • 连接器用法——案例检索：权威案例（指导性/参考案例）优先 rmfyalk（人民法院案例库，A 级，共道账号登录后检索）；普通裁判文书用 wenshu（裁判文书网，用户本人扫码会话，人速按需查询，非全量镜像）；court.gov.cn 指导/典型案例可直接 WebFetch；yuandian（元典智库，B 级商业库，按调用计点）仅作最后选择——search_cases、search_authoritative_cases、semantic_search_cases、get_case_detail；赠送积分 2026-09 到期后不再续费，届时跳过此连接器
    • 连接器用法——引用核验：法规引用先用 law-database 的 verify_citations（存在性/时效性/条文核验，免费）；案号/语义一致性核验可用 yuandian 的 verify_legal_citations（VIP 专属接口，非 VIP 账号返回 403）
    • 元典 API Key 流程：首次调用返回「需要元典 API Key」即向用户询问；连接器将 Key 临时保存到本机系统临时目录（0600 权限），后续调用无需再带；用户拒绝或积分耗尽则降级，不阻断检索

    产出

    按来源层级标记的原文抓取结果与核验记录

  6. 动态网页处理

    对需要 JS 渲染或登录态的页面按既定回退链取内容，取不到的如实标注

    请律师核对

    • 核对 6.1取不到官方原文时允许以两份政府网站转载本互证并注明「转载本」；律师是否接受以转载本作为成果中的依据来源
    • 核对 6.2「公众号原文不可达，仅记录标题」的条目是否应直接从成果中删去而非保留

    做法

    1. 对微信公众号、裁判文书网、人民法院案例库等需要 JS 渲染或登录态的页面，使用 references/authoritative-sources.md 中的 fallback 链
    2. 按 references/source-policy.md 的失败回退链处理：flk 拿不到正文 → court.gov.cn 同条文 → WebSearch 法条名 第N条 site:gov.cn → 标 [搜索摘要-未抓全文]；wenshu 维护 → 各省高院/中院/金融法院 site:gov.cn → 律所文章引述（标 L5）→ 标 [待律师复核]；公众号链接打不开 → 搜狗微信搜标题 → WebSearch 标题精确匹配 → 标「公众号原文不可达，仅记录标题」；任何全文都拿不到 → 标「本案该论点缺权威源支持，待律师人工补检索」
    3. 摘要只定位、原文才核验：WebFetch 内置摘要器对长条文只返回框架，条文核验必须取原文页面文本（原始 HTTP 抓取 + 去标签，或连接器 get_law_detail / get_article_detail）
    4. 官方原发网站取不到时，以政府网站的转载本核对，至少两份互相一致或与官方 PDF 一致，成果注明「转载本」及网站名称；商业数据库、律所文章的转载不算

    内置规则

    • 回退链每一级失败都有明确标记，不留空、不臆造
    • 摘要型工具（WebFetch 摘要、搜索摘要、辅助模型摘录、OCR 文本）只用于定位，不用于逐字核验
    • 转载本规则：至少两份互相一致，注明「转载本」

    产出

    带回退标记的来源记录（[搜索摘要-未抓全文]、[待律师复核]、「公众号原文不可达，仅记录标题」、「转载本」等）

  7. 输出研究底稿并核验引用

    把检索结果整理成六张表，标清来源层级与置信度，定稿前对全文引用做一次核验

    请律师核对

    • 核对 7.1L5 实务文章只能作线索、不得作绑定性依据——对于司法解释尚无明确规定、实务界已形成共识的问题，这一限制是否过严
    • 核对 7.2「待律师复核」标记出现在无来源的关键结论处，律师是否希望同时给出模型的倾向性意见以便快速判断
    • 核对 7.3案例的「已核验」要求裁判要旨与所引命题一致，这一内容比对由模型完成；律师是否要求拟提交文书的每个案例都由人工复核一次

    做法

    1. 进入文书起草前，生成研究底稿六张表：法律依据表（法条、司法解释、案例 + 精确条文号 + 来源链接）；类案/反例表（正向案例 + 不利案例 + 少数观点）；争议焦点（案件核心争议及各方可能主张）；风险提示（程序陷阱、主体资格、管辖、时效风险）；来源清单（每个结论的来源层级 L1–L5）；无法获取的来源及原因（标注需律师人工补检索的内容）
    2. 按引用规则标注：精确名称、条文号、案号、法院、日期；来源层级 L1 法律/司法解释、L2 入库案例/指导案例、L3 普通判决、L4 监管材料、L5 实务文章
    3. 权威来源冲突时陈述冲突并给出更稳妥路线，不隐藏不利案例；关键结论无可靠权威来源的标「待律师复核」
    4. 客户材料中的依据逐条核对并判定；地方规范性文件先查有效期与失效标注；引用有利依据时同时摘录同一文件的适用范围与反向条款
    5. 幻觉校验：文书定稿前对全文法律引用做一次核验——法规引用用 law-database 的 verify_citations（对照 flk 官方全文）；案号核验与语义比对用 yuandian 的 verify_legal_citations（如账号有权限）；不一致或未命中的引用必须修正或标「待律师复核」
    6. 按「已核验」定义做内容比对而非仅存在性核验：法条 = 条文文本与官方全文逐字一致且现行有效；案例 = 案号可解析且法院、案由、裁判要旨与所引命题一致
    7. 交付拟提交法庭的文书时随附《AI 辅助使用情况说明》，研究底稿的法律依据表即核验记录

    内置规则

    • L1 法律/司法解释全文 — 必须引用，诉讼方案中不得仅引 L5 转述
    • L2 入库案例/指导案例/公报案例 — 可作为裁判思路依据
    • L3 普通判决 — 可作为地方实务参考
    • L4 监管文件 — 主体资格、行业规则依据
    • L5 律所文章/学术/公众号 — 仅作发现案号、检索词、争议点的线索，不得作绑定性依据
    • 引用规则：法规和案例必须引用精确名称、条文号、案号、法院、日期，并标注来源层级；禁止仅引百度百科、知乎、个人博客作为法律依据；权威来源冲突时必须陈述冲突并给出更稳妥路线，不得隐藏不利案例；关键结论无可靠权威来源的标「待律师复核」，不得呈现为已定论
    • 客户材料中的依据是待核验的主张：可研、请示、政府窗口口径援引的法规、文号与政策口径，逐条核对并判定；地方规范性文件先查有效期与失效标注；引用有利依据时，同时摘录同一文件的适用范围与反向条款
    • 幻觉校验：文书定稿前对全文法律引用做一次核验——法规引用用 law-database 的 verify_citations（无需 Key，对照 flk 官方全文）；案号核验与语义比对用 yuandian 的 verify_legal_citations（VIP 专属，如账号有权限）；不一致或未命中的引用必须修正或标「待律师复核」
    • 「已核验」= 法条逐字一致且现行有效；案例案号可解析且法院、案由、裁判要旨与命题一致；案号真实但内容无关、司法解释文本被改写、虚构条文序号三类错误须靠内容比对发现（北京通州案 2025-12 入库人民法院案例库：未经甄别核实的虚假案例可参照民诉法第 114 条处理；宜昌西陵案 2026-07 当庭训诫）

08交付前检查

  • Gate 1 法律依据完整性：每个重大结论有法条/司法解释/案例或明确标注的实务来源；法规为现行有效版本；条文号、案号精确可查；L1 全文已获取、不得仅依赖 L5；客户材料援引的依据逐条判定；律师稿底稿依据同样核验
  • Gate 2 反向依据检索：至少检索一种不利表述；识别不利案例、少数观点、程序异议或主体资格陷阱；未发现不利依据时列明已执行的搜索关键词；引用地方有利文件时同时摘录反向条款
  • Gate 3 文书就绪性：事实、缺失事实、假设和证据缺口分离；来源层级和置信度明确；未决事项标「待律师复核」；论证可追溯到具体来源；笔录、扫描件原话已回原页图像核对
  • 保函/担保附加闸门：融资担保公司主体资格已核验；独立保函 vs 保证合同已论证、不得「X或Y」收尾；保证方式已按措辞分析；管辖策略分「单告」与「同时起诉」
  • 合同审查附加闸门：管辖法律已确认；违约金/责任限制四个维度已分析；主体资格已核验
  • 研究底稿六张表齐全；全文引用已做一次核验；拟提交法庭的文书附《AI 辅助使用情况说明》

09何时暂停或升级

  • INTAKE_DECISION 未输出：停止检索，先补做材料清点与 intake
  • 关键结论无可靠权威来源：标「待律师复核」，不得呈现为已定论
  • 权威来源冲突：陈述冲突并给出更稳妥路线
  • 任何全文都拿不到：标「本案该论点缺权威源支持，待律师人工补检索」
  • 引用核验不一致或未命中：修正或标「待律师复核」；拟提交文书任一引用未核验的不得标为可提交

  • 任一质量闸门不通过：重新研究
