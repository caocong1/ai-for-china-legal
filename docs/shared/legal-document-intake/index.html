01概要

在法律研究、合同审查/起草、诉讼文书、意见书或律师函开始前，先读完律师发来的材料、会话答复和实践配置，重建已知事项并逐个数字对账，再从七类来源找出会改变成果的问题，分为必须确认 / 建议确认 / 可按默认 / 材料请求四档；只有必须确认项未解决时才暂停。决策必须以 INTAKE_DECISION 区块写在回复里，然后立刻提问：直接问（AskUserQuestion / ask_user，每轮 2–6 题）或一次性生成问卷文档发给律师，没有工具时输出 [CLARIFY:] 清单。律师答复粘贴回来后按题号合并、列合并表、从暂停处继续。每个事项同时判定 standard / high / critical 执行档，high / critical 交付前输出 REVIEW_STATUS 说明有没有做不同模型的独立复核。目标是把「律师发需求和文件 → 操作员交给模型 → 模型问清楚 → 律师补充 → 继续执行」做成可恢复的流程，纯机械任务且关键信息齐全时不提问。

02适用与边界

适用场景

  • 中国法律研究、合同审查/起草、诉讼文书、法律意见书或律师函开始前（由总路由第 1 步调用，也可被研究闸门第二步调用）
  • 第一次实质检索、派出并行检索助手或开始起草之前
  • 律师中途发来自改稿、新材料或新指令，改变了底稿或任务时，重新执行一次
  • 操作员忘记如何发起、恢复或分派任务时，读 references/operator-quickstart.md 取可直接复制的提示词

不做什么

  • 纯格式转换、拆分、提取或机械校对、没有法律判断的任务：仍输出区块但不提问（ask_mode: none）
  • 材料、会话与实践配置已覆盖全部问题来源的事项：不提问
  • 不是固定问卷：问题是候选清单，材料里已有答案的不问；不问「还有其他要求吗」，不为凑题数或展示区块而制造问题
  • 不替代研究闸门与人审：动态 intake 只减少无效追问，不降低研究闸门和人审要求；高风险法律结论和正式对外文书仍须律师复核
  • 不把客户原文、律师答复原文和敏感材料写入日志、案例库或遥测；问卷文档不进任何 git 仓库

03输入与产出

需要律师提供

  • 用户消息与律师指令必需
  • 全部指定文件（目录、文件类型、关键文件）可选
    先做只读清点；资料包很大时不必读完全部细节，但要读到能判断每个候选问题在材料里有没有答案
  • 会话既有答复可选
    derived 与已答事项不得再次询问
  • 适用实践配置可选
    有具体稳定值则用；「视情况而定」是事项级路由信号，不等于配置缺失
  • 操作员对提问方式的指示（「直接问」「出问卷」「不用问」）可选
    没有时按选择顺序请操作员选
  • 律师带回的答复（微信文字、回填问卷文本或文件路径、提问工具结果）可选
    第五步合并与恢复的输入

产出

  • INTAKE_DECISION 区块给律师内部（操作员可见的流程凭证，不写入最终法律文书；不复制客户原文，每项只写脱敏短语）
    [INTAKE_DECISION] intake_status: ready|ask|clarify；reason 一句话；questions: 必须确认 N · 建议确认 N · 可按默认 N · 材料请求 N；ask_mode: interactive|questionnaire|none|pending；draft_mode: complete|conditional|not_applicable；execution_profile: standard|high|critical；deferred_items 列表 [/INTAKE_DECISION]
  • 提问：AskUserQuestion / ask_user 调用，或 [CLARIFY:] 文本清单给律师 / 操作员 / 客户（题目标明谁能回答）
    [CLARIFY:] 分四段：必须确认（问题、影响、A（推荐）/B 选项）；建议确认（不回复则按推荐处理，写推荐或「未答复时：……」）；可按默认值处理（默认值）；请提供的材料（文件 —— 用途）；末尾「我们对材料的理解（如有误请指出）」不超过五条 [/CLARIFY]
  • 问卷文档《<事项简称>》待确认问题清单（致承办律师）给承办律师（内部文件，不发客户）
    按 references/questionnaire-mode.md 生成，含全部问题（四档）与「我们对材料的理解」，保存在事项资料目录；回复中给出文件路径、可转发律师的一两句话、题量、等待期间做什么，并贴出同内容的 [CLARIFY:] 文本
  • 合并表与会话内事项摘要给律师内部（仅用于会话连续性）
    合并表：题号｜答复要点｜处理（采纳 / 按默认 / 仍缺 / 与材料不一致）。摘要 YAML：intake_status、ask_mode、task_type、draft_mode、execution_profile、deliverable、party_role、audience、questions（id、tier、status）、confirmed、assumptions_authorized、deferred_items、open_items
  • REVIEW_STATUS 区块给律师内部
    [REVIEW_STATUS] execution_profile: high|critical；independent_review: done|skipped；reviewer（脱敏标识或 none）；disagreements_unresolved（数量或 none）；reason [/REVIEW_STATUS]；不写入最终法律文书，可写入交付说明

04开始前

前置条件

  • 先做只读的材料清点：目录、文件类型、律师指令、关键文件
  • 在第一次实质检索、派出并行检索助手或开始起草之前完成第一步至第三步，输出 INTAKE_DECISION，再按第四步提问
  • 设计背景：v1.3.0 及以前提问与暂停是一回事，结果 2026-10-14 至 11-01 在 Claude Code 中执行的 11 项法律任务没有一次提问，INTAKE_DECISION 从未出现在回复里；开场一句话能问清的事（租金基数两种读法、律师已有自改稿、原仲裁是否已出裁决、两份模板）变成了返工或交付后的待确认项

硬性规则

先读材料再问
材料、会话和配置里已有的信息不问；derived 不得再次询问；推断置信度不足的改列 material_missing
问与停分开
会改变成果的问题在起草前就问；只有必须确认项才停下来等答复
区块必须可观察
INTAKE_DECISION 写在给用户看的回复里，只在思考中作出判断不算输出（LWC-2026-0008 的记录写「已按时输出」，转录显示判断只出现在思考中）；区块之后紧接着提问
必须确认未解决不出结论
[CLARIFY:] 中有必须确认项未解决前，不得生成结论性文书，也不得声称文书已完成；必须确认项只能由答复或律师明确授权（assumption_authorized）解决
不重复确认输出位置
用户已明确格式、源文件和目标位置的，禁止重复确认；实践配置有稳定默认且不会覆盖原件的可直接采用；只有目标不明、可能覆盖原件、涉及外部发送或存在特权风险时才询问
保密
客户原文、律师答复原文和敏感材料不得写入日志、案例库或遥测；问卷与成果文件保存在事项资料目录，不写入任何 git 仓库
不降低闸门
动态 intake 只减少无效追问，不降低研究闸门和人审要求

05执行步骤

共 8 步，按执行顺序。每步旁边（窄屏在步骤说明之后）是请律师核对的内置假设，可逐条复制。页面里的英文标记见首页「标记与术语」。

  1. 重建已知事项

    把材料、会话和配置里已经有的信息整理清楚，避免问已知的事，并把律师给的数字与原件对上

    请律师核对

    • 核对 1.1「可以可靠推出」的 derived 不再问——例如从文件名推出我方身份、从指令推出落款与口吻；律师是否接受这种推断不确认
    • 核对 1.2数字对账要求逐一核对金额、单价、面积、期限、日期，是否还应包括利率、比例、人数等

    做法

    1. 读取用户消息、全部指定文件、会话既有答复和适用实践配置
    2. 把信息分为四组：known（律师明确提供的事实和偏好）；derived（可从文件、文件名、上下文或配置可靠推出的信息）；material_missing（不同答案会改变法律路径、立场、修订力度、请求权、风险分配、数字或交付物）；optional_missing（只影响细节，可用配置默认值或保守默认值）
    3. derived 不得再次询问；推断置信度不足的改列 material_missing
    4. 数字对账：律师指令里的金额、单价、面积、期限、日期，逐一与原合同、原件或计算结果核对
    5. 对不上的，写出全部合理读法并量化差额，作为第二步的候选问题

    内置规则

    • 四组状态：known / derived / material_missing / optional_missing
    • material_missing 的判定标准：不同答案会改变法律路径、立场、修订力度、请求权、风险分配、数字或交付物
    • 数字对不上时写出全部合理读法并量化差额（LWC-2026-0008：「10 月份的租金标准」有两种读法，差额约 10 万元，起草者只记了「不一致」，另一读法由复核者发现）

    产出

    四组状态清单与数字对账结果（含各读法与差额）

  2. 列出候选问题并分档

    从七类来源找出会改变成果的问题，每个先在材料里找答案，找不到的归入四档之一并标明谁能回答

    请律师核对

    • 核对 2.1必须确认项的范围（我方身份、文书类型、适用程序、拟提交或供第三方依赖文书的核心事实、硬时限、整份成果依赖的前提、差额重大的读法）是否合理，是否还应加入利益冲突核查、授权与委托范围
    • 核对 2.2「对我方有利、律师几乎必然同意的起草选择」归入可按默认而不问（如明示排除对我方不利的原合同条款），律师是否同意由模型替律师做这类选择
    • 核对 2.3材料请求「通常不超过 5 项」的上限是否够用

    做法

    1. 按七类来源逐项找问题：1 指令（两种以上合理读法、数字对不上、两个模板或格式指令冲突、「参考」「不要参考」范围不清）；2 底稿与版本（律师是否已有自己的稿或修改稿、哪一份是基准、上一轮成果律师改过没有）；3 只有律师或客户知道的状态（程序进展如是否已裁决、撤回、反诉、举证期限；对方履约状态如是否已逾期、欠费多少、押金是否足额；谈判进展；政府或对方的口头意见；内部决策与审批；关键文件是否存在）；4 整份成果所依赖的前提；5 客户目标与取舍（偏好方案、可接受风险、措辞语气、已锁定条件）；6 受众与交付（直接发客户还是内部审阅、出具日期与落款、截止时间）；7 材料缺口（缺了会改变正文的文件）
    2. 每找到一个问题，先在材料里检索答案，有答案的不问；各来源典型问题见 references/question-routing.md 第 0 节
    3. 把每个问题归入一档：必须确认 / 建议确认 / 可按默认 / 材料请求
    4. 做《成稿说明》测试：如果不问，这一项会不会写进《成稿说明》的「发送前请确认」等律师或客户决定后再改正文？会，就至少是建议确认，应在起草前问；对我方有利、答案可预见的起草选择不算，按可默认处理并在《成稿说明》说明
    5. 处理两条边界：材料里有相反说法（双方各执一词、同一材料前后口径不一）而结论取决于哪个为真的，不算「材料已有答案」——律师或客户能确认的列为建议确认，不能的在分析中列明两种说法与证据；能从指令或材料可靠推出的事项（落款、口吻、交付形式）不作为题目，写进问卷的「我们对材料的理解」
    6. 每个问题标明谁能回答：操作员、律师或客户
    7. 尽职调查 / 合规调查的必答与可后置事项另见 shared/references/due-diligence-playbook.md 第 1 节

    内置规则

    • 必须确认 — 判定：答错会让成果方向错误或不能用：我方身份、文书类型、适用程序；拟提交法院、仲裁机构、监管机关或供第三方依赖的文书的核心事实；硬时限；整份成果依赖的前提；差额重大且材料无法判定的读法。未答复时：受影响部分暂停起草
    • 建议确认 — 判定：答案会改变具体章节、结论、数字或措辞，而且需要律师或客户取舍（我方让步、客户偏好、商业判断），或者只有他们知道；不问就只能写成条件句、两套方案或《成稿说明》待确认项。未答复时：按推荐答案起草；没有推荐答案的（如只有客户知道的事实），正文用条件句或来源句；答复到达后修订
    • 可按默认 — 判定：有安全默认值：只影响细节，或者是对我方有利、律师几乎必然同意的起草选择（如明示排除对我方不利的原合同条款）。未答复时：采用默认值，在区块与《成稿说明》中写明
    • 材料请求 — 判定：提供后会改变正文的文件；先把资料包与材料中引用的文件对账，只请求缺失且影响正文的，通常不超过 5 项。未答复时：正文用来源句、条件句处理
    • 《成稿说明》测试：会写进「发送前请确认」的至少是建议确认，起草前问，不等交付时才问
    • 材料里有相反说法不算「材料已有答案」
    • 能可靠推出的事项不出题，写进「我们对材料的理解」

    产出

    分四档、标明回答人的候选问题清单

  3. 决定是否暂停

    用三种 intake_status 决定是停下等答复、问了先写，还是直接继续

    请律师核对

    • 核对 3.1「截止紧迫」定义为期限在一两天内即可按推荐答案先写，这一宽松度是否合适
    • 核对 3.2咨询型备忘录可写附条件结论而拟签署的合同（如补充协议）不行、拟提交法院的文书不行；这一划分是否符合贵所实践

    做法

    1. 有必须确认项 → intake_status: clarify：提问，受影响部分暂停起草
    2. 无必须、有建议确认项 → intake_status: ask：起草前提问；等答复，或按推荐答案先写
    3. 只有可默认项或没有问题 → intake_status: ready：直接继续，写明采用的默认值
    4. clarify 期间可继续不依赖答案的准备工作（材料提取、OCR、法条与原文核对），不得生成结论性文书，也不得声称文书已完成
    5. ask 时，操作员或律师回复「先写」，或截止紧迫（政府、法院或交易设定的期限就在一两天内），按推荐答案起草，答复到达后修订（LWC-2026-0007：政府要求月底签约）
    6. 判断是否可用 draft_mode: conditional：既有文书的内部审阅和经律师转发客户的咨询型备忘录，可以写附条件结论；条件性继续回答的是「要不要停」，不是「要不要问」，会改变正文的缺口仍在起草前提问

    内置规则

    • intake_status: clarify — 有必须确认项；提问；受影响部分暂停起草
    • intake_status: ask — 无必须、有建议确认项；起草前提问；等答复，或按推荐答案先写
    • intake_status: ready — 只有可默认项或没有问题；直接继续，写明采用的默认值
    • 必须确认项只能由答复或律师明确授权（assumption_authorized）解决
    • 拟提交法院、仲裁机构或监管机关的文书，向第三方出具、供其依赖的法律意见书，要求无保留结论，以及缺口会改变委托问题或我方身份的，核心缺口一律为必须确认
    • 截止紧迫的定义：政府、法院或交易设定的期限就在一两天内
    • draft_mode: conditional 只用于既有文书的内部审阅和经律师转发客户的咨询型备忘录

    产出

    intake_status 与 draft_mode 的判定

  4. 判定执行档（execution_profile）

    按事项风险决定用一个模型自检，还是加不同模型独立复核，还是分角色执行并由律师人审

    请律师核对

    • 核对 4.1默认 critical 的任务清单（正式意见书、对外尽调/合规报告、拟提交法院/仲裁/监管的文书、行刑衔接/上市公司/国资）是否完整——例如重大并购交易文件、涉外事项、金额超过某一门槛的合同是否也应默认 critical
    • 核对 4.2「大额」没有数字门槛，由模型判断；贵所是否要给出金额标准

    做法

    1. 为每个事项写入与品牌无关的 execution_profile：standard / high / critical
    2. 判断是否属于默认 critical 的任务
    3. 判断是否存在不低于 high 的情形
    4. 不猜测用户额度，不硬编码模型品牌；宿主提供复核工具（如独立复核助手）时 high / critical 的复核经该工具执行，人工操作员模式下由不同模型盲审
    5. 需要规划多模型分工时读取 references/operator-orchestration.md

    内置规则

    • standard：单一主模型 + 自检
    • high：强主模型起草 + 不同模型独立复核
    • critical：材料提取、权威检索、起草、独立复核分角色执行，最后仍由律师人审
    • 默认 critical：正式法律意见书；对外尽调报告 / 合规调查报告；拟提交法院、仲裁机构或监管机关的文书；涉及行刑衔接、上市公司或国资主体的事项（指我方或客户是上市公司、国资主体，或事项可能使我方或客户承担行政、刑事责任，包括对方提出的此类指控）
    • 不低于 high：存在大额、特殊主体、担保、客户敏感数据、不可逆外部发送或重大期限

    产出

    execution_profile 值，写入 INTAKE_DECISION

  5. 输出可观察的 INTAKE_DECISION（必须）

    把前面的判断写成操作员看得见的区块，作为流程凭证，然后立刻提问

    请律师核对

    • 核对 5.1区块是给操作员看的流程凭证，不进最终文书；律师是否也希望在交付说明里看到它
    • 核对 5.2操作员说「不用问」时模型照列问题但不问、答不了的进《成稿说明》；律师是否接受操作员可以替律师关闭提问

    做法

    1. 完成第一步至第三步后、进入实质研究或正文之前（包括派出并行检索助手之前），在回复正文中输出 [INTAKE_DECISION] 区块：intake_status、reason、questions 四档题量、ask_mode、draft_mode、execution_profile、deferred_items
    2. 区块之后紧接着提问：interactive 调用提问工具，questionnaire 生成文档，没有工具时输出 [CLARIFY:]
    3. 任务属于起草、出具意见、诉讼文书或尽调而 questions 全为 0 的，在 reason 中写明材料已覆盖哪些问题来源
    4. 有必须确认或建议确认项而 ask_mode: none 的，在 reason 中写明原因（如「操作员要求不问」）
    5. 不复制客户原文，每项只写脱敏短语；区块不写入最终法律文书
    6. 操作员尚未选择提问方式时先以 ask_mode: pending 输出区块，再弹选择题；选定后不必重出区块，在提问消息里写明所选方式

    内置规则

    • 区块写在给用户看的回复里；只在思考中作出判断不算输出
    • 时间点：第一次实质检索、派出并行检索助手或开始起草之前
    • ask_mode 取值：interactive / questionnaire / none / pending（等操作员选择方式）
    • deferred_items：不阻断、将在正文、批注或《成稿说明》处理的事项；没有则写 none
    • 下列情形仍输出区块但不提问（ask_mode: none）：纯格式转换、拆分、提取或机械校对；材料、会话与实践配置已覆盖全部问题来源；操作员明确说「不用问」「直接写」或律师授权「按你的判断处理」——问题照列，答不了的写进 deferred_items 与《成稿说明》

    产出

    回复正文中的 [INTAKE_DECISION] … [/INTAKE_DECISION] 区块

  6. 选择提问方式并提问

    用最合适的方式把问题送到能回答的人手里，题量可控、每题只解决一个决定

    请律师核对

    • 核对 6.1问卷「必须确认加建议确认通常不超过 10 题、可默认不超过 5 题」，复杂尽调或多问题备忘录是否够
    • 核对 6.2推荐答案排第一并标「（推荐）」是否会诱导律师；拿不准时不标推荐的做法是否足够
    • 核对 6.3直接问时「可默认项不逐题问，只在文字里列其余按默认」，律师是否希望默认项也逐题过一遍

    做法

    1. 两种 ask_mode：interactive（直接问，用宿主的提问工具逐题问、当场作答；适合操作员能回答、问题少、律师在线）；questionnaire（问卷文档，全部问题一次写成一份文档，操作员发给律师填写后粘贴回来；适合多数问题需律师或客户回答、经微信转达）
    2. 按选择顺序决定提问方式（见本步规则）；操作员未指定、且问题并非全部由操作员能答时，先输出 ask_mode: pending 的区块，再用一道单选题请操作员选
    3. 直接问：Claude Code 用 AskUserQuestion（延迟加载时先用 ToolSearch 加载），每次 1—4 题、每题 2—4 个选项，推荐项放第一个并标「（推荐）」，「其他」由工具自动提供；题干写清所依据的材料事实、不依赖前文；先问必须确认再问建议确认，超过 4 题分两次调用；可默认项不逐题问，在文字消息中列「其余按默认：……」；墨律桌面端用 ask_user（见 shared/inkstatute-integration/ASK-USER-PROTOCOL.md）；操作员对某题答「不确定」「问律师」的，把这些题汇总成一份只含这些题的问卷文档
    4. 问卷文档：按 references/questionnaire-mode.md 生成，包含全部问题（必须确认、建议确认、可按默认、材料请求）和「我们对材料的理解」，保存在事项资料目录、不进 git；回复中给出文件路径、可直接转发律师的一两句话、题量、等待期间做什么，并贴出内容相同的 [CLARIFY:] 文本便于粘贴微信
    5. 生成问卷后可继续不依赖答案的准备工作，做完即停下等答复；ask 且截止紧迫的按推荐答案继续起草

    内置规则

    • 两种 ask_mode：interactive（直接问）——用宿主的提问工具逐题问，当场作答，适合操作员能回答、问题少、律师在线；questionnaire（问卷文档）——全部问题一次写成一份文档，操作员发给律师填写后粘贴回来，适合多数问题需律师或客户回答、经微信转达
    • 选择顺序第 1 条：操作员已经说明的照办——「直接问」「问我」用 interactive；「出问卷」「问题发给律师」「出问题清单」用 questionnaire；「不用问」「直接写」用 none
    • 选择顺序第 2 条：会话或实践配置中已有默认方式的，沿用
    • 选择顺序第 3 条：都没有时，问题全部是操作员能答的（哪份文件是基准、保存位置、律师原话的含义）直接问；否则有提问工具的先用一道单选题请操作员选——前两个选项是「生成问卷文档」「直接问我」，第三个选项没有必须确认项时是「不问，按推荐先写（问题列入《成稿说明》）」、有必须确认项时是「只问必须确认的 N 题，其余按推荐」；多数问题需律师或客户回答时推荐第一项；选第三项不等于授权，必须确认项仍须答复；没有提问工具时输出 [CLARIFY:] 清单，并说明「回复『出问卷』可生成 Word 问卷」
    • 先输出区块（ask_mode: pending）再弹选择题；操作员选定后不必重出区块，在提问消息里写明所选方式即可
    • 题量：直接问每轮 2—6 题；AskUserQuestion 每次 1—4 题、每题 2—4 个选项，超过 4 题分两次调用；问卷文档一次列全，必须确认加建议确认通常不超过 10 题，可默认不超过 5 题；超过时合并同类，删去能从材料推出的
    • 每题只解决一个决定，有稳定编号，写明影响什么；推荐答案排第一；必须确认题也可以标推荐，但推荐不是默认，未答复不按推荐处理；拿不准哪个更合理时不标推荐，不诱导答案
    • 轮次：第一轮答复后，只有新事实暴露新的关键分支时再问一次；通常最多两轮
    • 不问材料里已有答案的事，不问「还有其他要求吗」，不为凑题数或展示区块而制造问题
    • [CLARIFY:] 中有必须确认项未解决前，不得生成结论性文书，也不得声称文书已完成

    产出

    AskUserQuestion / ask_user 调用，或问卷文档（.docx / .md）+ 可转发话语 + [CLARIFY:] 文本

  7. 合并答复并恢复

    律师答复回来后按题号合并、从暂停处继续，不重问不重来，并维护一份会话内摘要

    请律师核对

    • 核对 7.1对必须确认题回复「按推荐」即视为选择推荐项——律师是否接受以这种简短方式确认关键事项
    • 核对 7.2「其余按默认」不覆盖必须确认题，必须逐题答复；这一要求对律师是否过于严格

    做法

    1. 接收答复：粘贴的微信文字、律师回填的问卷文本或文件路径，或宿主返回的 ask_user / AskUserQuestion 结果
    2. 按题号合并到事项摘要：只给字母的按选项解释；对某一题回复「同意」「按推荐」就是选了该题的推荐项，必须确认题也一样；笼统的「其余按默认」「都按建议」只覆盖建议确认题和可按默认题，必须确认题须逐题答复
    3. 在回复中列一张简短的合并表：题号｜答复要点｜处理（采纳 / 按默认 / 仍缺 / 与材料不一致）
    4. 仍缺的必须确认题和与材料矛盾的答复，只就这些追问一轮
    5. 必须确认项解决后从暂停处继续：不重新清点材料，不重复问已答的题
    6. 律师明确交由模型判断的事项记为 assumption_authorized，并写明采用的假设
    7. 答复带来新材料，或改变了底稿、任务的，重新输出 INTAKE_DECISION
    8. 恢复后维护会话内摘要 YAML（intake_status、ask_mode、task_type、draft_mode、execution_profile、deliverable、party_role、audience、questions、confirmed、assumptions_authorized、deferred_items、open_items）；该摘要只用于会话连续性

    内置规则

    • 「同意」「按推荐」= 选推荐项，必须确认题同样适用
    • 「其余按默认」「都按建议」不覆盖必须确认题
    • 追问只针对仍缺的必须确认题和与材料矛盾的答复，一轮
    • 不重新清点材料、不重复提问、不重新开始整个工作流
    • task_type 取值：contract_review / contract_drafting / litigation / opinion / correspondence / research
    • 客户原文、律师答复原文和敏感材料不得写入日志、案例库或遥测

    产出

    合并表 + 更新后的会话内事项摘要，随后从暂停阶段继续

  8. 交付前输出 REVIEW_STATUS（必须）

    high / critical 事项交付时，把「有没有做不同模型的独立复核」变成一个可观察的决定，不得沉默交付

    请律师核对

    • 核对 8.1独立复核允许 skipped 只要写明原因；律师是否要求 critical 事项一律不得跳过
    • 核对 8.2未消解分歧以 [HUMAN_REVIEW] 标记留在成果中（或《成稿说明》），律师是否希望改为单独的分歧清单

    做法

    1. execution_profile 为 high 或 critical 的事项，在交付成果的进度消息中输出 [REVIEW_STATUS]：execution_profile、independent_review: done | skipped、reviewer（不同模型 / 不同厂商复核者的脱敏标识或 none）、disagreements_unresolved（数量或 none）、reason（为何跳过，或复核如何执行：新鲜上下文、传入案情与初稿）
    2. 原定复核模型不可用（额度、限流）时换另一个不同模型执行，reviewer 写实际复核者；按复核意见修改后未再做第二轮复核的在 reason 中写明
    3. 复核者在新鲜上下文中工作，只接收案情事实、已确认事项与候选成果，不接收起草者的推理过程
    4. 复核者引入的法律依据同样经研究闸门核验后才能写入成果
    5. 未消解的分歧逐条列入成果并标 [HUMAN_REVIEW: 模型间存在未消解分歧 —— <争点>]；客户成稿模式下列入给律师的《成稿说明》，不进客户正文

    内置规则

    • 没有做独立复核必须是一个可观察的决定，不得沉默交付（LWC-2026-0004 / 0005 / 0006 三件 critical 任务均未做独立复核且未显式声明，是最常见的流程缺口；LWC-2026-0007 首次执行不同模型、新上下文复核，发现 1 处金额口径错误与 3 处论证缺口，均在交付前修正）
    • 复核者只接收案情事实、已确认事项与候选成果
    • 复核者引入的依据也要过研究闸门
    • 未消解分歧标 [HUMAN_REVIEW]；客户成稿模式下放《成稿说明》
    • 区块不写入最终法律文书，可写入交付说明

    产出

    [REVIEW_STATUS] … [/REVIEW_STATUS] 区块，附在交付进度消息中

07交付前检查

  • INTAKE_DECISION 出现在回复正文，且在第一次实质检索、派出并行检索助手或开始起草之前
  • 区块之后紧接着提问（工具调用、问卷文档或 [CLARIFY:]）
  • questions 全为 0 的起草/意见/诉讼/尽调任务，reason 写明材料覆盖了哪些问题来源
  • 有必须/建议确认项而 ask_mode: none 的，reason 写明原因
  • 问卷题量：必须+建议通常不超过 10 题、可默认不超过 5 题、材料请求通常不超过 5 项
  • 合并表已列出，未重复提问已答事项，未重新清点材料
  • high / critical 事项交付时输出 REVIEW_STATUS
  • 区块与摘要不含客户原文，每项只写脱敏短语

08何时暂停或升级

  • 有必须确认项：intake_status: clarify，受影响部分暂停起草，直到答复或 assumption_authorized
  • 拟提交法院、仲裁机构或监管机关的文书，供第三方依赖的法律意见书，要求无保留结论，缺口会改变委托问题或我方身份：核心缺口一律升为必须确认
  • 操作员对某题答「不确定」「问律师」：把这些题单独做成问卷
  • 答复仍缺必须确认题或与材料矛盾：只就这些追问一轮
  • 律师中途发来自改稿、新材料或新指令改变了底稿或任务：重新执行 intake 并重新输出 INTAKE_DECISION
  • 目标不明、可能覆盖原件、涉及外部发送或存在特权风险：询问输出与保存位置
  • 独立复核未执行：REVIEW_STATUS 写 skipped 并说明原因，不得沉默交付

  5. 「截止紧迫」被定义为政府、法院或交易设定的期限就在一两天内，此时 ask 状态可按推荐答案先写；这一宽松度是否合适？相关批注：核对 3.1
  6. ask_mode 的选择顺序把操作员的指示放在第一位，操作员说「不用问」即 ask_mode: none，问题改进《成稿说明》；律师是否接受操作员可以替律师关闭提问？相关批注：核对 5.2
  7. 默认 critical 的清单为：正式法律意见书；对外尽调/合规调查报告；拟提交法院、仲裁机构或监管机关的文书；涉及行刑衔接、上市公司或国资主体的事项。是否完整？「大额」「重大期限」（不低于 high 的情形）没有数字门槛，而 shared/CLAUDE.md 另对存量土地变性事项规定「国有企业主体或亿元级价款」默认 critical；是否要统一给出贵所的金额标准？相关批注：核对 4.2、核对 4.1
  8. draft_mode: conditional（附条件结论）允许用于既有文书的内部审阅和经律师转发客户的咨询型备忘录，但补充协议等拟签署合同和拟提交法院的文书不允许；这一划分是否符合贵所实践？相关批注：核对 3.2
  9. 推荐答案排在第一个并标「（推荐）」，必须确认题也可标推荐；对必须确认题回复「按推荐」即视为选择。律师是否担心推荐会诱导答案，或者简短回复会被过度解读？相关批注：核对 7.1
  10. REVIEW_STATUS 允许 independent_review: skipped 只要写明原因；对 critical 事项是否应改为一律不得跳过？相关批注：核对 8.1
  11. 本流程文件不引用任何法条，所有法律判断延后到研究闸门与专项流程；是否需要在 intake 阶段就提示诉讼时效、举证期限等法定期限的法律依据？
  12. 会话内摘要与案例库只记题量、答复率和答复是否改变成果，不记律师答复原文；日后回查某个决定为何如此时，这种记录是否够用？
