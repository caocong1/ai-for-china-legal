01概要

律师对 AI 成果的意见从三处来：墨律 App 里的好评、差评和留言，微信或面谈转达的评价，以及律师在 AI 成稿上改定的定稿。本流程不重新训练 AI，只把意见变成 skill 规则的小幅修改：先登记脱敏案例；有定稿的与原稿逐段比对，删改分照做、偏好、不学三类，定稿不当标准答案；再把差评归纳成 3–5 个问题模式，找到对应规则，每次只改 1–3 处。改动经评测或人工核对确认有改善才发布，律师下次打开 App 自动更新。全程不删研究闸门的强制步骤、不编造法条，案例库只存脱敏概括。

02适用与边界

适用场景

  • 收到从墨律后台导出的一批律师反馈
  • 操作员或维护者要求「根据最近某个流程的反馈更新规则」「处理某类文书质量的差评」
  • 拿到同一法律任务几个 AI 模型分别做出的成果和律师的评价，要沉淀成案例、改进流程
  • 新版 skill 包发布前，对照真实的律师意见做最后一轮修正
  • 律师以 AI 成稿为底稿改定后发回（定稿、改稿或已发客户的版本），要比对学习、改进规则

不做什么

  • 不重新训练 AI 模型：律师的意见只转化为 skill 规则文字的修改
  • 同步失败、上传、崩溃、设置界面等墨律 App 本身的问题不在本流程修改，转墨律 App 一方处理
  • 维护用的评测和优化工具不放进律师用的 App 和正式发布的 skill 包
  • GitHub 与墨律后台的访问密钥不写进 skill 规则或 App
  • 未经律师授权，不上传、不扩散案情全文；案例库默认只存脱敏概括、文件校验记录和评价标签

03输入与产出

需要提供

  • 墨律 App 里律师对单次成果点的好评、差评，以及留言和勾选的问题方面可选
    维护者从墨律后台导出，可只取差评、未处理的或某个流程的
  • 律师经微信或面谈给的评价，以及被评价的成果文件可选
    按律师原话记录，不用 AI 打分代替
  • 律师改定的定稿，以及 AI 当初交付的原稿（Word 文件）可选
    两稿逐段比对；定稿是最完整的反馈，但不当标准答案
  • 处理范围：时间段、领域或流程、指定的反馈编号可选
    如「过去 7 天诉讼仲裁的差评」；不指定时只处理未处理的差评

产出

  • 完成报告读者：律师内部 / 维护者
    七项：处理了哪些反馈、问题模式、改了哪些规则及怎么改、验证结果（评测得分或人工核对结论）、发布的版本号与校验记录、已标为「已处理」的反馈、案例编号与律师评价
  • 脱敏案例记录读者：律师内部
    案例编号、任务类型、脱敏事项概括、文件校验记录、页数等统计、律师评价原话、可复用经验、对应的规则改动、开工前确认核查；有定稿的另附第 2 步的比对结果
  • 定稿比对结果读者：律师内部 / 维护者
    逐节差异稿和统计（保留、改写、删除、新增各多少段，脚注变化）；删改逐条归为照做、偏好、不学；定稿本身的残留问题清单
  • skill 规则的小幅修改读者：维护者
    只有两种改法：替换原文某一段，或在末尾追加一段；每次 1–3 处，每处写明理由和对应的反馈

04开始前

前置条件

  • 至少要有一类反馈：墨律 App 里的好评、差评和留言，律师经微信或面谈给的评价，或律师改定的定稿。
  • 先分流（必做）：涉及法条、案由、文书结构、检索、文书质量、流程逻辑的意见，改 skill 的规则；同步失败、上传、崩溃、设置界面、待发送内容积压等 App 本身的问题，转墨律 App 一方处理。拿不准的默认按规则问题处理，App 问题另行单独登记。
  • 每条反馈处理完，都在墨律后台登记分流结果：标为「已处理」，写明转给了哪一方、做了什么（例如「替换了保函路径的规则」）。
  • 本流程在维护者一侧执行：律师只管提意见；改动验证通过后随新版 skill 包推送，律师端无需任何操作。

硬性规则

客户信息脱敏
不复制客户合同、提示词全文、案情全文、批注全文或可识别的个人信息；提到文件只用脱敏后的名称，不写存放位置
律师评价分量最重
页数、表格数等统计只作说明；律师本人的评价分量最重，按原话记录，不用 AI 打分代替
只提炼窄规则
从一次案例只提炼适用范围窄的规则，不把一次偏好扩大成所有案件都适用的绝对规则
定稿不当标准答案
律师定稿里的删改分照做、偏好、不学三类处理；偏好要有第二个事项印证，才改默认写法
每次小幅修改
不整篇重写；只用替换原文某一段、在末尾追加一段两种改法，每次 1–3 处，每处写明对应哪条反馈
不削弱研究闸门
不删除中国法研究闸门的强制步骤；找规则时先读研究闸门的规则，确认检索要求没被破坏
不编造法条
新增规则里拿不准的地方，标 [待律师复核]
以对话记录为准
开工前确认结论是否写进回复，以对话记录为准、不以 AI 自述为准；只在思考过程里出现的记为没写（曾有两个案例的记录记成了「已写出」）

05执行步骤

共 7 步，按执行顺序。每步旁边（窄屏在步骤说明之后）是请律师核对的内置判断，可逐条复制。

  1. 脱敏案例登记

    拿到成果和律师评价时，先把这次任务记成一条可复用、可比对、不泄密的案例

    请律师核对

    • 核对 1.1案例记录只留文件校验记录和页数、表格数等统计，不存原文；律师日后回查某份成果，这样是否够用？
    • 核对 1.2律师评价按原话记录：一句话的评价是否够用，还是应请律师分方面（如法条、结构、检索、文书质量）评价？

    做法

    1. 给案例编号，登记任务类型、脱敏后的事项概括、输入材料和成果的校验记录（能确认是哪份文件，不存原文）、所用的 AI 模型及设置、页数和表格数等统计。
    2. 按原话记下律师的评价，写出可复用的经验，以及据此要改哪条规则。
    3. 核查这次的开工前确认，以对话记录为准：开工前确认结论是否写进了回复；是直接提问、出问卷文档还是没问；四档问题（必须确认、建议确认、可按默认、材料请求）各几个、律师答了多少，答复是否改变了成果。
    4. 不复制客户合同、提示词全文、案情全文、批注全文和可识别的个人信息；提到文件只用脱敏后的名称，不写存放位置。
    5. 使用方已建案例库的，按案例库的格式登记；没有的，只在对话里写出待保存的记录，并问清保存到哪里。

    内置规则

    • 页数、表格数等统计只作说明；律师本人的评价分量最重。
    • 一次案例只提炼适用范围窄的规则，不把一次偏好扩大成所有案件都适用的绝对规则。
    • 开工前确认做没做，以对话记录为准，不以 AI 自述为准：只在 AI 思考过程里出现的结论记为没写——曾有两个案例的记录，把这种情形记成了「已写出」。

    产出

    一条脱敏案例记录：存入案例库，或先在对话里写出待保存

  2. 律师定稿比对

    律师在 AI 成稿上改定后，把定稿当作最完整的反馈：找出保留了什么、删改了什么、为什么

    请律师核对

    • 核对 2.1律师的删改分照做、偏好、不学三类，偏好要有第二个事项印证才改默认写法；贵所是否认可这一读法？
    • 核对 2.2哪些删改其实是贵所的统一要求，应当直接照做，而不是记为一位律师的偏好？
    • 核对 2.3照做一类列举的成稿规范（概率语气、去掉内部称谓、去重复、人名最小化），是否都是贵所认同的通用要求？
    • 核对 2.4定稿残留问题只向操作员列出、不改律师的文件；是否需要同时出一份修正稿供律师选用？

    做法

    1. 把 AI 原稿和律师定稿按标题逐节对齐、逐段比对，标出原样保留、改写、删除、新增的段落；表格逐行比，脚注按在正文中出现的顺序比（WPS 存回后脚注编号会被重排，不能按编号对）。
    2. 先看总量：整节删去和新增了哪些，保留、改写、删除、新增各多少段，脚注有什么变化。
    3. 再把删改逐条归类：标题与结构、整节删除、过程性内容、风险评级、确定性措辞、指令性措辞、术语、点名与人名、交叉引用、事实更正、依据更正。
    4. 每条删改按照做、偏好、不学三类处理，落到具体要改的 skill 规则，写进案例记录的规则改进清单；律师原样保留的部分同样记录，作为不应改动的写法。
    5. 顺带检查定稿本身的残留：删去附件后仍写着「见附件×」、空表格骨架、已删释义的简称仍在使用、同一表述改了一处漏了别处；在给操作员的回复里列出，不改律师的文件。

    内置规则

    • 定稿不当标准答案：律师的删改可能受客户关系、内部考量、时间等现实因素影响，也只是一位律师的做法，所以分三类处理。
    • 照做：任何律师都会认同的成稿规范，如裁判预测用概率语气、不用绝对化措辞，去掉内部称谓，去重复，人名最小化；以及事实和依据的更正。更正前要回查来源，并检查 skill 现有内容里的同类表述。
    • 偏好：合理、但也可以有别的做法的取舍（是否做风险评级、附件取舍、用语）。写进本领域实践配置的相应配置项，或作为《成稿说明》里的选项，不改默认写法。
    • 不学：照做会降低质量或掩盖风险的删改，例如删去影响认定的事实、框架要求的内容、实质缺口，或弱化高风险结论；在案例记录里写明不学的理由。
    • 判断线索：删去而没有改正的，多为取舍；删去的是事实或风险本身时，先考虑情境因素；同一类表述只改了一部分的，多为低优先级的偏好；偏好要有第二个事项印证，才改默认写法。
    • 保留比例高，说明结构和写法被接受；删改集中的地方就是学习重点。首次使用时，定稿保留 751 段、改写 120 段、删除 21 段，整节删去 3 个附件，36 条脚注原样保留。

    产出

    比对差异稿和统计；删改归类清单及对应的规则改动；定稿残留问题清单

  3. 归纳问题模式

    把零散的差评归并成少数几个可以处理的问题模式

    请律师核对

    • 核对 3.1默认只处理差评：好评里「哪里做得对」是否也应沉淀为规则？
    • 核对 3.2每轮最多 3–5 条问题模式，是否会漏掉出现次数少但后果严重的问题？

    做法

    1. 取尚未处理的差评；操作员指定了反馈编号的，按指定的处理。
    2. 按所属领域、具体流程和律师勾选的问题方面（如法条、结构、检索）把反馈归类。
    3. 写出 3–5 条问题模式，每条注明出自哪几条反馈（反馈编号）。

    内置规则

    • 默认只处理尚未处理的差评；好评等其他反馈，只有指定编号时才处理。
    • 每轮 3–5 条问题模式，每条都能追溯到具体的反馈编号。

    产出

    3–5 条问题模式，每条附对应的反馈编号

  4. 找到要改的规则

    找到反馈对应的那份 skill 规则，并确认改动不会破坏中国法研究闸门

    请律师核对

    • 核对 4.1反馈落到哪条规则由维护者判断；律师是否希望反馈时直接指明是哪一步出了问题？
    • 核对 4.2这一步只要求确认研究闸门没被破坏，没有要求同时确认开工前确认的提问规则、Word/PDF 交付前的检查规则没被削弱；是否应一并检查？

    做法

    1. 按领域找到反馈对应的 skill，定出拟修改的段落。
    2. 诉讼类反馈，优先到诉讼仲裁领域（如案件录入流程）里找。
    3. 动手前先读中国法研究闸门的规则，确认其强制步骤完整、检索要求没有被破坏。

    内置规则

    • 诉讼类反馈优先定位到诉讼仲裁领域，如案件录入流程。
    • 任何改动之前，先确认研究闸门的强制步骤完整。

    产出

    要改的 skill 规则和拟改段落

  5. 小幅修改规则

    用最小、可追溯的改动落实反馈，不整篇重写

    请律师核对

    • 核对 5.1每次只改 1–3 处是否太慢，还是恰好能防止反馈被过度解读？
    • 核对 5.2新增规则标 [待律师复核] 后，由谁、在什么时候复核并去掉标记？

    做法

    1. 只用两种改法：替换原文某一段（写明原文和改后的文字），或在规则末尾追加一段。
    2. 每次只改 1–3 处，每处写明理由和对应的反馈。
    3. 不删除中国法研究闸门的强制步骤。
    4. 不编造法条；新增规则里拿不准的地方标 [待律师复核]。

    内置规则

    • 不整篇重写，只用替换、追加两种改法。
    • 每次 1–3 处，每处都能对回一条反馈编号。
    • 研究闸门的强制步骤不删，法条不编造。

    产出

    改动清单：每处是替换还是追加、改成什么、理由和对应的反馈

  6. 验证改动

    用评测或实际场景证明改动确实改善了反馈指出的问题，而不是凭感觉

    请律师核对

    • 核对 6.1评测以律师审定的样稿为参照答案：贵所能否持续提供审定样稿？
    • 核对 6.2没有评测用例时只要求人工核对 1 条场景，是否足够？

    做法

    1. 有评测用例的，用评测专用、经过授权的材料实测：按用例自带的评分标准打分，以律师审定的样稿作参照答案。
    2. 比较改动前后的得分：改后必须高于改前，持平不算通过。
    3. 没有评测用例的，至少拿一条差评对应的场景重做，人工核对是否改善。
    4. 确认改动后整套 skill 仍能正常加载。

    内置规则

    • 有评测用例的：改后得分必须严格高于改前，否则不得发布。
    • 没有评测用例的：至少人工核对 1 条差评对应的场景。
    • 评测只用评测专用、经过授权的材料。

    产出

    评测得分（与改前对比）或人工核对结论

  7. 记录修改并发布

    把通过验证的改动记入修改记录、打包发布，律师端自动更新

    请律师核对

    • 核对 7.1新版自动推送到律师端：律师是否希望在 App 里看到「本次更新改了什么」？
    • 核对 7.2没有规定发布后发现质量下降时怎样退回；律师端无需操作、自动更新，是否需要能退回上一版本？

    做法

    1. 把通过验证的改动记入 skill 的修改记录，注明是根据律师反馈、就哪个主题做的修改。
    2. 打包成新版本的 skill 包发布，附上「根据律师反馈改了什么」的说明。
    3. 律师端无需任何操作：下次打开墨律 App 时自动更新到新版本。
    4. 在墨律后台把处理过的反馈标为「已处理」，写明转给了哪一方、改了什么。

    内置规则

    • 修改记录注明「根据律师反馈修改」及主题。
    • 发布的版本号和校验记录写进完成报告。
    • 处理过的反馈逐条标为「已处理」。

    产出

07交付前检查

  • 案例记录里没有客户原文、批注全文、文件存放位置、个人信息、账号或 AI 使用额度
  • 每处修改都写明理由，并能对回一条反馈编号
  • 研究闸门的强制步骤完整，整套 skill 改后仍能正常加载
  • 有评测用例的，改后得分严格高于改前；没有的，至少人工核对了 1 条差评场景
  • 定稿比对中「不学」的删改，案例记录里写明了理由
  • 完成报告七项齐全：处理的反馈、问题模式、改动的规则、验证结果、发布版本、分流处理标记、案例库登记

08何时暂停或升级

  • 分不清是 skill 规则问题还是 App 问题：默认按规则问题处理，App 问题另行单独登记
  • 新增规则有拿不准的地方：标 [待律师复核]
  • 使用方没有案例库：只在对话里写出待保存的记录，并问清保存到哪里
  • 评测得分没有高于改前：不得发布

09审阅清单

请律师重点核对：下面是这个流程内置的法律判断、立场、阈值和清单，每一条都可以同意、反对或补充。条目里「供核对」之后的内容是本站整理时对照现行条文补充的提示，不是 skill 原文。条目下的「相关批注」按文字重合自动匹配到步骤旁的核对条目，可能不全。

  1. 律师的反馈要便于处理，按本流程的归类和分流方式，最好写明：哪个领域、哪个流程；问题属于法条、案由、结构、检索、文书质量还是流程逻辑（这些改 skill 规则，同步失败、上传、崩溃等才改 App）；律师原话（按原话记录，不用 AI 打分代替）；对应的成果文件。贵所是否愿意按这个粒度反馈，还是只点好评、差评？
  2. 默认只处理尚未处理的差评，好评不进入规则修改；律师认为「做对了的地方」是否也应固化为规则？相关批注：核对 3.1
  3. 「从一次案例只提炼窄规则，不把一次偏好扩大成所有案件的绝对规则」：律师某次的偏好（如「乙方立场不够强」）应落到具体的触发情形，而不是让审查全面变强硬。是否同意这种保守取向？
  4. 律师定稿里的删改（如风险评级、整改期限、过程性内容）不一律照学：通用成稿规范和事实、依据的更正，一次就改进规则；偏好要等第二个事项印证，才改同类报告的默认写法。一位律师一次定稿的删改能改变多少默认写法，贵所是否同意这条分界？相关批注：核对 2.1
  5. 即使是律师在定稿里删的，只要照做会降低质量或掩盖风险——删去影响认定的事实、框架要求的内容、实质缺口，或弱化高风险结论——就「不学」，只在案例记录里写明理由。贵所是否同意对律师的这类删改不学？
  6. 每次只改 1–3 处、不整篇重写，改得慢，但每处改动都能追溯到具体反馈；贵所更看重改得快还是改得稳？
  7. 验证标准是「评测得分严格高于改前」或「人工核对 1 条差评场景」，评测要以律师审定的样稿为参照；律所能否持续提供审定样稿？相关批注：核对 6.1
  8. 核查开工前确认以对话记录为准、不以 AI 自述为准，只在思考过程里出现的结论记为「没写」；是否认可把「回复里看得到开工前确认结论和提问」作为流程合规的硬指标？
  9. 案例库只存脱敏概括、文件校验记录和评价标签，不存客户原文；律师日后要回查某份成果为什么被评差，这样的记录是否够用？相关批注：核对 1.1
  10. 反馈分流到两处（skill 规则或墨律 App），律师看不到分流结果；是否需要在 App 里告诉律师「您的意见已转化为哪条规则」？
