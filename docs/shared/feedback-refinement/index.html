01概要

律师在墨律桌面 App 中对成果点的好评/差评，或经微信、面谈给出的定性评价，由本流程转化成对规则文件（SKILL.md）的有界改动，而不是改模型权重。流程先把成果与律师评价记成脱敏案例（任务类型、输入/输出哈希、结构指标、律师原意评价、可复用经验），再对差评聚类成 3–5 条问题模式，定位到对应插件的规则文件，用 REPLACE / APPEND 两种格式做每次 1–3 处的有界编辑，经评测用例或人工核对验证后提交、打包发布；律师端 App 无需操作，下次启动自动拉取新包。全程保证研究闸门的强制步骤不被删、不编造法条、新增规则的不确定点标「待律师复核」、案例库只存脱敏摘要。

02适用与边界

适用场景

  • 收到 feedback-export.md，或调用 GET /api/feedback/export.md 导出反馈
  • 用户说「根据最近 XXX 反馈更新规则」「处理某类文书质量 down 反馈」
  • 用户提供同一法律任务的多模型成果及律师人工评价，希望沉淀案例并改进工作流
  • 规则包发布前需要对照真实律师意见做最后一轮修正

不做什么

  • 不改模型权重，只改规则文件（SKILL.md）
  • 同步失败、上传、崩溃、设置 UI、outbox 等 App 问题不在本流程处理，分流到 lawyer-desktop 仓库
  • 不在律师 App 或生产包中运行 SkillOpt 管理面板逻辑
  • 不把 GitHub token / sync API 密钥写入规则文件或 App
  • 未经律师授权不上传或扩散案情全文；案例库默认只保存脱敏摘要、哈希和评价标签

03输入与产出

需要律师提供

  • 同步服务导出的 feedback-export.md（推荐；可按 rating=down、status=open、skill=<流程名> 参数过滤）可选
    四种输入来源至少一种
  • 本地 CLI 导出：lawyer-desktop/tools/sync-service 下 bun run feedback:export可选
  • Dev 环境：lawyer-desktop 内 Ctrl+Shift+O 面板的本地 skill_feedback 表（仅开发机）可选
  • 人工操作员反馈：律师经微信/面谈给出的定性评价 + 本地成果文件可选
    律师评价必须原意记录，不用模型分数替代
  • 时间范围 / 流程名 / remote_id 列表（如：过去7天 litigation-legal down反馈）可选
    参数提示

产出

  • 完成报告（7 项）给律师内部 / 维护者
    1 处理的反馈 remote_id 列表；2 问题模式聚类摘要；3 改动文件路径 + REPLACE/APPEND 摘要；4 验证结果（val 分数或人工核对结论）；5 发布版本 manifest version + sha256；6 已标记 handled 的 remote_id；7 案例库 case id、脱敏记录路径及人审标签
  • 脱敏案例记录给律师内部
    案例 id、任务类型、脱敏事项摘要、输入/输出 sha256、模型/推理档、结构指标、律师原意评价、可复用经验、规则改动映射、intake 审计（INTAKE_DECISION 是否出现、提问方式、题量、答复率、答复是否改变成果）
  • 规则文件的有界编辑给维护者
    REPLACE:旧文本|||新文本 或 APPEND:追加段落；每处附 rationale 对应哪条反馈

04开始前

前置条件

  • 仓库分流（必做）：法条、案由、结构、检索、文书质量、流程逻辑的反馈改 ai-for-china-legal 对应规则文件；同步失败、上传、崩溃、设置 UI、outbox 改 lawyer-desktop；不确定时默认改规则文件，App 问题单独开 issue
  • 处理后在 sync-service 标记 triage（remote_id、status: handled、target_repo、notes）
  • 可在 Cursor、Codex、Claude Code 等任意本地 AI 编程助手中加载，无特定工具依赖

硬性规则

脱敏
不复制客户合同、提示词全文、案情全文、批注全文或可识别个人信息；文件路径只保留脱敏 label，不写绝对路径
律师评价权重最高
结构指标只用于解释，律师人审标签权重最高；律师评价必须原意记录，不用模型分数替代
窄规则
从单次案例提炼窄规则，不把一次偏好扩张为所有案件的绝对规则
有界编辑
禁止整篇重写；只用 REPLACE / APPEND 两种格式，每次 1–3 处编辑
闸门不可破
不删除 research-gate 强制步骤；定位时读取 shared/research-gate/SKILL.md 确认检索闸门未被破坏
不编造法条
新增规则的不确定点用「待律师复核」标注
intake 审计以转录为准
INTAKE_DECISION 是否出现以会话转录为准，不以模型自述为准；只在思考里出现记为未输出（LWC-2026-0006、0008 的记录曾把只出现在思考中的判断记成「已输出」）

05执行步骤

共 6 步，按执行顺序。每步旁边（窄屏在步骤说明之后）是请律师核对的内置假设，可逐条复制。页面里的英文标记见首页「标记与术语」。

  1. 脱敏案例捕获（第 0 步）

    用户提供本地成果和律师评价时，先把这次任务记成可复用、可比对、不泄密的案例

    请律师核对

    • 核对 1.1案例记录保存了输入/输出哈希与结构指标但不存原文，律师是否认为这足以日后回查
    • 核对 1.2律师评价「原意记录」的粒度：一句话评价是否足够，还是应要求分维度评价

    做法

    1. 生成案例 id
    2. 记录：任务类型、脱敏事项摘要、输入/输出 sha256、模型/推理档、结构指标、律师原意评价、可复用经验和规则改动映射
    3. 做 intake 审计，以会话转录为准：INTAKE_DECISION 是否出现在回复中（只在思考里出现记为未输出）；提问方式（直接问 / 问卷文档 / 未问）；题量（必须确认 / 建议确认 / 可默认 / 材料请求）、答复率，以及答复是否改变了成果
    4. 不复制客户合同、提示词全文、案情全文、批注全文或可识别个人信息；文件路径只保留脱敏 label
    5. 若消费者项目已有 docs/legal-ops/case-library/，按其 schema 记录；否则只在会话中生成待保存记录并询问目标仓库

    内置规则

    • 结构指标只用于解释，律师人审标签权重最高
    • 从单次案例提炼窄规则，不把一次偏好扩张为所有案件的绝对规则
    • intake 审计不以模型自述为准

    产出

    一条脱敏案例记录（会话内或 docs/legal-ops/case-library/）

  2. 聚类

    把零散差评归并成少数可处理的问题模式

    请律师核对

    • 核对 2.1默认只处理差评：好评中「哪里做得对」是否也应沉淀为规则
    • 核对 2.2每轮 3–5 条问题模式的上限是否会漏掉低频但严重的问题

    做法

    1. 只处理 rating=down 且 status=open 的反馈（除非用户指定 remote_id）
    2. 按 plugin_name / skill_name / dimensions 聚类
    3. 写出 3–5 条问题模式，每条引用 remote_id

    内置规则

    • 默认只处理差评且未处理的反馈
    • 问题模式 3–5 条，每条可追溯到 remote_id
    • 聚类维度三个：plugin_name / skill_name / dimensions

    产出

    3–5 条带 remote_id 的问题模式

  3. 定位规则文件

    找到反馈对应的具体规则文件，并确认改动不会破坏检索闸门

    请律师核对

    • 核对 3.1反馈归到哪个规则文件由维护者判断，律师是否希望在反馈时直接指明是哪一步出的问题
    • 核对 3.2定位时只要求确认研究闸门未被破坏，SKILL.md 未要求同时确认 intake 提问与交付 QA 规则未被削弱；是否应一并检查

    做法

    1. 在 ai-for-china-legal 中按插件目录找目标规则文件
    2. 诉讼类反馈优先定位 litigation-legal、matter-intake 等
    3. 读取 shared/research-gate/SKILL.md，确认检索闸门未被破坏

    内置规则

    • 诉讼类反馈优先定位 litigation-legal / matter-intake
    • 任何改动前先确认研究闸门强制步骤完整
    • 按插件目录定位目标规则文件

    产出

    目标规则文件路径及拟改段落

  4. 有界编辑（禁止整篇重写）

    用最小、可审计的改动落实反馈

    请律师核对

    • 核对 4.1每次只改 1–3 处是否过慢，还是正好防止反馈被过度解读
    • 核对 4.2新增规则标「待律师复核」后，由谁、何时复核并去掉标记

    做法

    1. 只使用两种格式：REPLACE:旧文本|||新文本；APPEND:追加段落（放在文档末尾）
    2. 每次 1–3 处编辑，每处 rationale 写清对应哪条反馈
    3. 不删除 research-gate 强制步骤
    4. 不编造法条；新增规则用「待律师复核」标注不确定点

    内置规则

    • 格式仅 REPLACE / APPEND 两种
    • 每次 1–3 处
    • 每处附 rationale → remote_id
    • 不删研究闸门强制步骤；不编造法条

    产出

    带 rationale 的 REPLACE / APPEND 编辑清单

  5. 验证（闸门）

    证明改动确实改善了反馈对应的场景，而不是凭感觉

    请律师核对

    • 核对 5.1Gold reference 是「律师审定样稿」：贵所能否持续提供审定样稿作为评测基准
    • 核对 5.2无评测用例时只要求人工核对 1 条场景，是否足够

    做法

    1. 有评测用例时：材料用评测专用目录（需 skillopt_eval_data_roots 授权）；Gold rubric 为评测用例内的评分标准；Gold reference 为律师审定样稿；在 lawyer-desktop dev 环境用 run_eval_case / SkillOpt 面板，val 分数必须严格高于基线
    2. 一般规则：至少人工核对 1 条差评对应的场景是否改善
    3. 检查 .claude-plugin/marketplace.json 仍有效

    内置规则

    • 有评测用例的，val 分数必须严格高于基线
    • 无评测用例的，至少人工核对 1 条差评场景
    • 市场清单必须仍合法

    产出

    val 分数或人工核对结论

  6. 提交与发布

    把通过验证的改动提交、打包，让律师端自动拉取

    请律师核对

    • 核对 6.1规则包自动推送到律师端，律师是否希望在 App 内看到「本次更新改了什么」的说明
    • 核对 6.2SKILL.md 未规定发布后发现质量下降时如何回滚；律师端「无需操作」自动更新，是否需要可回退到上一版本

    做法

    1. 在 ai-for-china-legal 仓库提交：git commit -m "refine(skills): address lawyer feedback on <topic>"
    2. 在 lawyer-desktop 仓库打包到 sync-service：node tools/publish-skill.mjs --root ../ai-for-china-legal --version <版本> --notes "反馈驱动：..."（或 publish-skill.ps1）
    3. 律师端 App 无需操作，下次启动自动拉取新规则包
    4. 在 sync-service 标记 triage：remote_id、status: handled、target_repo、notes

    内置规则

    • 提交信息前缀 refine(skills)
    • 发布版本号与 sha256 写入完成报告
    • 处理过的 remote_id 标记 handled

    产出

    提交记录、规则包版本与 sha256、triage 标记

06引用的共享规则

  • shared/research-gate/SKILL.md
    定位与编辑时必须确认检索闸门的强制步骤未被删除
  • shared/legal-document-intake/SKILL.md
    intake 审计的对象：INTAKE_DECISION 是否出现、提问方式与题量

07交付前检查

  • 案例记录不含客户原文、批注全文、绝对路径、个人信息、账号或额度
  • 每处编辑有 rationale 对应 remote_id
  • 研究闸门强制步骤完整
  • 有评测用例的 val 分数严格高于基线；无评测用例的至少人工核对 1 条差评场景
  • .claude-plugin/marketplace.json 仍有效
  • 完成报告含 7 项：处理的反馈、问题模式、改动文件、验证结果、发布版本、Triage、案例库

08何时暂停或升级

  • 反馈特征不确定属于规则还是 App：默认按规则处理，App 问题单独开 issue
  • 新增规则存在不确定点：标「待律师复核」
  • 消费者项目没有 docs/legal-ops/case-library/：只在会话中生成待保存记录并询问目标仓库
  • val 分数未严格高于基线：不得发布

09请律师重点核对

下面是这个流程内置的法律假设、立场、阈值和清单，每一条都可以同意、反对或补充。条目下的「相关批注」按文字重合自动匹配到步骤旁的核对条目，可能不全。

  1. 律师反馈要便于处理，按本流程的聚类与分流方式，至少应包含：哪个插件、哪个流程（聚类按 plugin_name / skill_name / dimensions）；问题属于法条、案由、结构、检索、文书质量还是流程逻辑（这些特征决定改规则文件，同步失败、上传、崩溃等才改 App）；律师原话评价（「必须原意记录，不用模型分数替代」）；对应的成果文件。贵所是否愿意按这个粒度反馈，还是只点好评/差评？
  2. 流程默认只处理 rating=down 且 status=open 的反馈，好评不进入规则改动；律师认为「做对了的地方」是否也应固化为规则？
  3. 「从单次案例提炼窄规则，不把一次偏好扩张为所有案件的绝对规则」：律师的某次偏好（如「乙方立场不够强」）应落到具体触发项，而不是全局变强硬；是否同意这种保守取向？
  4. 有界编辑每次只改 1–3 处、禁止整篇重写，改动速度慢但可审计；贵所更看重改得快还是改得稳？
  5. 验证标准为「val 分数严格高于基线」或「人工核对 1 条差评场景」，Gold reference 需要律师审定样稿；律所能否持续提供审定样稿？相关批注：核对 5.1
  6. intake 审计以会话转录为准、不以模型自述为准，并把只在思考里出现的判断记为「未输出」；律师是否认可用「有没有在回复中看到 INTAKE_DECISION 和提问」作为流程合规的硬指标？
  7. 案例库只存脱敏摘要、哈希和评价标签，不存客户原文；若律师日后要回查某个成果为什么被评差，这种记录是否够用？
  8. 本流程把反馈分流到两个仓库（规则 vs App），律师端看不到分流结果；是否需要在 App 里反馈「您的意见已转化为第 X 条规则」？
在 GitHub 提 issue怎么提意见

复制后粘到微信给操作员即可；每条前的编号让意见能对回源文件。

10示例提示词

  • 根据过去 7 天 litigation-legal 的差评反馈更新规则：导出 feedback-export.md 在 /路径/feedback-export.md，请聚类、定位并做有界编辑。
  • 这是同一份租赁合同修订任务的两个模型成果 /路径/成果A.docx、/路径/成果B.docx，律师评价：「A 的乙方立场够，但在先抵押那条漏了；B 太软」。请沉淀脱敏案例并提出规则改动。
  • 处理 remote_id 为 <uuid1>、<uuid2> 的两条反馈，改完后标记 handled 并打包发布。

11源文件

说明与源文件不一致时，以源文件为准，并请告知我们。

本站把 ai-for-china-legal 仓库里的 skill 文件改写成给律师看的说明。所有 skill 的输出都是供律师审查的草稿，不是法律意见。页面由 scripts/build-docs-site.py 从 docs/data/skills/parts/ 生成；生成日期 2026-11-02。

发现说明与源文件不一致、或对 skill 的规则有意见：见怎么提意见。
