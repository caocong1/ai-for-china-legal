01概要

凡是中国大陆法律任务——审查或起草合同、出意见书、写诉讼文书、回答「是否合法／风险多大／该怎么办」、处理上传的起诉状判决书——本流程自动接管，不需要律师或操作员点名。它按固定顺序把事项送过四道关：先做动态 intake（读材料、列出会改变成果的问题、输出 INTAKE_DECISION 后在起草前问清），再按交付物路由到最具体的专项中国法流程，再过研究闸门同时找支持依据、反向依据和程序陷阱，最后按 Word/PDF 交付清单出稿并在 high/critical 事项附 REVIEW_STATUS。默认按「资深中国大陆执业律师的工作产物标准」执行，但专业角色与我方立场是两个字段：立场推不出且会改变成果时仍要问。律师带回答复后从暂停处继续，不重问、不重来。

02适用与边界

适用场景

  • 由内容判断触发，不靠口令：用户提出中国大陆法律任务，或上传合同、起诉状、判决书、章程、备忘录等法律文件要求处理，即自动接管，无需说出流程名称或固定短语
  • 要求审查、修订、起草合同、协议、条款、章程、函件
  • 要求出具或审阅法律备忘录、法律意见书、律师函、起诉状、答辩状、代理词
  • 询问中国法下某项安排是否合法、是否有效、风险多大、如何救济
  • 涉及劳动用工、婚姻家事、继承、建设工程、房地产、土地使用权（划拨、出让、改变用途、作价出资）、知识产权、数据与刑事合规
  • 上传法律文书要求总结、核对、修订、翻译或提取风险点
  • 用户提到法条、司法解释、法院、仲裁委、违约、侵权、解除、赔偿、担保、抵押、股权、竞业限制、工伤、抚养费、诉讼时效等术语
  • 明确提到 ai-for-china-legal 或本工作流名称

不做什么

  • 非中国大陆法域的事项
  • 与法律无关的通用写作和编程任务
  • 不得因为请求已经附带文件就跳过 intake；也不得把 intake 理解为每次都要向用户提问
  • 不替代执业律师最终审定：默认角色是「资深律师工作标准」，不是声称模型具有律师身份或代替最终签字律师
  • 用户未提角色视角时，禁止为此额外询问

03输入与产出

需要律师提供

  • 用户的法律需求描述（任务、交付物）必需
  • 法律文件：合同、起诉状、判决书、章程、备忘录等（路径或附件）可选
    有文件也不能跳过 intake；允许先只读清点和提取
  • 实践配置（各插件 CLAUDE.md、律所默认值）可选
    先利用材料、会话答复和实践配置，禁止重复询问已有信息
  • 我方立场（甲方/乙方、原告/被告、发包人/承包人等）可选
    默认角色不能替代立场；立场无法从材料可靠推断且会改变成果时，由动态 intake 询问
  • 角色视角覆盖（对方律师视角、法官/仲裁员视角、仅做事实提取、仅做格式处理）可选
    仅对本事项覆盖默认值，不回写长期配置

产出

  • INTAKE_DECISION 区块与提问给律师内部（操作员可见的流程凭证，不写入最终文书）
    在第一次实质检索、派出并行检索助手或开始起草之前，在回复中输出可观察的 INTAKE_DECISION；随后直接问（AskUserQuestion / ask_user）或生成问卷文档
  • 研究底稿给律师内部
    由研究闸门产出：法律依据表、类案/反例表、争议焦点、风险提示、来源清单（L1–L5）、无法获取的来源及原因
  • 专项法律文书给律师内部 / 客户 / 对方 / 法院（按事项）
    按路由到的专项流程及 shared/references/document-structures.md 的结构模板成文
  • Word / PDF 交付稿给律师内部 / 客户
    不覆盖原件；真实 Track Changes 可接受可拒绝；正文确定性与批注一致；经结构检查与渲染/视觉 QA；high / critical 事项附 REVIEW_STATUS
  • 客户成稿 + 《成稿说明（致承办律师）》给客户成稿给客户；《成稿说明》给承办律师
    律师要求「可以直接给客户」或用律所模板出具时：律所口吻、律所模板、正文无内部标记；写给律师的事项另出《成稿说明》（document-delivery-qa.md 第 5 节九节结构）

04开始前

前置条件

  • 路径解析：本文中 shared/… 与 <plugin>/skills/… 都相对语料仓根目录；经符号链接安装到 ~/.claude/skills 或 ~/.codex/skills 时，先解析本目录的真实路径再定位语料仓
  • 默认角色配置 professional_role: senior_prc_lawyer_work_product：按资深中国大陆执业律师的工作标准完成材料审阅、问题识别、法律检索、反向观点、风险分级、文书表达和交付 QA
  • 默认行为：先区分用户提供事实、可验证材料、推断、假设和法律结论；对关键结论检索现行法、权威案例及不利路径；未核实事实使用条件性表述或待核实标记；形成供执业律师快速复核的工作产物而非法律科普
  • 在实质研究、法律判断、起草或修改文件前，读取并执行 shared/legal-document-intake/SKILL.md

硬性规则

内容触发
由内容判断，不靠口令；接管后不得因请求附带文件就跳过 intake，也不得把 intake 理解为每次都要提问
角色与立场分离
专业角色与我方立场是两个不同字段。默认「资深律师工作标准」不能替代甲方/乙方、原告/被告、发包人/承包人等立场；立场推不出且会改变成果时由 intake 询问；用户未提角色时禁止额外询问角色
可观察的 intake
必须在回复中输出 INTAKE_DECISION，时间点在第一次实质检索、派出并行检索助手或开始起草之前。只在思考里判断「信息够了」不算完成 intake：2026-10-14 至 11-01 的 11 项任务都读了 intake 规则、判断也做了，但没有一次输出区块或提问
专项优先
按交付物选择最具体的可用中国法流程；不得用通用写作流程替代专项法律技能
研究闸门不可省
除非用户明确要求「只按现有资料，不联网检索」，在形成或修改实质法律结论前执行研究闸门；无法核验的依据标记为待律师复核，不补造引用
文档交付底线
不覆盖原件；真实 Track Changes 应可接受、可拒绝；核心事实待核实时正文确定性须与批注一致
人审恒在
正式成果恒由执业律师复核。客户成稿模式下这一要求由《成稿说明》与 REVIEW_STATUS 承载，不因正文无标记而取消

05执行步骤

共 6 步，按执行顺序。每步旁边（窄屏在步骤说明之后）是请律师核对的内置假设，可逐条复制。页面里的英文标记见首页「标记与术语」。

  1. 动态 Intake（开工前问清）

    在实质研究、法律判断、起草或修改文件前，读完材料，把会改变成果的问题在起草前问清，并留下可观察的决策记录

    请律师核对

    • 核对 1.1intake 区块出现在每个法律事项的回复里，是否影响律师阅读体验；是否同意把它作为操作员可见的流程凭证
    • 核对 1.2立场无法推断时才问立场、角色视角从不问——这一取舍是否符合贵所习惯

    做法

    1. 读取并执行 shared/legal-document-intake/SKILL.md；允许先只读清点和提取用户指定的全部材料
    2. 先利用材料、会话答复和实践配置，禁止重复询问已有信息
    3. 按 intake 第二步列出候选问题，分为必须确认 / 建议确认 / 可按默认 / 材料请求；会改变成果的在起草前问
    4. 在回复中输出 INTAKE_DECISION 区块，时间点在第一次实质检索、派出并行检索助手或开始起草之前
    5. 选择提问方式：直接问（宿主提问工具，如 Claude Code 的 AskUserQuestion、墨律的 ask_user），或问卷文档（全部问题一次写成文档，操作员转给律师填写后粘贴回来）；操作员没有指定时请其选择
    6. 按 intake_status 分流：clarify 提问并暂停受影响部分的起草；ask 提问后等答复，或在操作员要求、截止紧迫时按推荐答案先写；ready 直接继续，不要求用户回复「同意继续」

    内置规则

    • intake_status: clarify → 提问，受影响部分暂停起草
    • intake_status: ask → 提问；等答复，或在操作员要求、截止紧迫时按推荐答案先写
    • intake_status: ready → 直接继续，不要求用户回复「同意继续」
    • 两种提问方式：直接问（宿主提问工具）或问卷文档；操作员未指定时请其选择
    • 只在思考里判断「信息够了」不算完成 intake

    产出

    回复中的 INTAKE_DECISION 区块（intake_status、reason、四档题量、ask_mode、draft_mode、execution_profile、deferred_items）及随后的提问或问卷

  2. 中国法律路由（选最具体的专项流程）

    Intake 通过后，按交付物把事项送到最具体的可用中国法专项流程，而不是用通用写作流程处理

    请律师核对

    • 核对 2.1路由表只列了合同、建设工程、劳动、数据、知产、尽调、信用修复、土地变性几类；贵所高频事项（如婚姻家事、刑事合规）是否也应有明确的路由条目
    • 核对 2.2「有 cn-lawyer-docs 时以其为总路由」依赖一个本仓库之外的流程，是否接受这种外部依赖

    做法

    1. 有 cn-lawyer-docs 时，以其作为诉讼/合同/意见书/函件总路由
    2. 合同审查或起草继续使用 commercial-legal 相关流程
    3. 建设工程、劳动、数据、知识产权等专业事项使用对应领域流程
    4. 股权交易/并购的目标公司法律尽调用 commercial-legal/skills/equity-transaction-dd；整家公司或用工群体的劳动用工合规调查用 employment-legal/skills/workforce-compliance-dd；两者共用 shared/references/due-diligence-playbook.md
    5. 重大税收违法失信、信用修复类意见使用 regulatory-legal 流程，并先读 shared/research-gate/references/search-playbooks.md 的信用修复 playbook
    6. 存量土地变性（划拨补办出让、改变用途）、城市更新与低效用地再开发、以土地作价出资或合作开发房地产，使用 construction-legal/skills/land-use-redevelopment；涉及国有企业投资与参股的，并读 commercial-legal/skills/_shared/transaction-procedure-citations.md 第八节
    7. 不得用通用写作流程替代专项法律技能

    内置规则

    • 路由标准是「交付物」：按交付物选择最具体的可用中国法流程
    • 尽调类两条路由（股权尽调 / 用工合规调查）共用一份尽调 playbook
    • 信用修复类须先读专项 playbook 再进专项流程
    • 土地变性涉及国资的，加读国资交易程序锚点第八节

    产出

    确定本事项进入的专项流程与须一并读取的共享文件

  3. 研究闸门（形成结论前检索）

    在形成或修改任何实质法律结论之前，用可用的中国法研究闸门同时找到支持依据、反向依据和程序/效力陷阱

    请律师核对

    • 核对 3.1豁免联网检索只认用户的明确表示，律所是否需要一个「默认不联网」的配置项（如涉密事项）
    • 核对 3.2「不补造引用」在没有可核验来源时的替代写法是「待律师复核」，这种标记在成果中出现的密度是否可接受

    做法

    1. 除非用户明确要求「只按现有资料，不联网检索」，执行可用的中国法研究闸门
    2. Codex 环境优先使用 cn-law-research-gate；仓库/其他环境使用 shared/research-gate/SKILL.md
    3. 同时检索支持依据、反向依据和程序/效力陷阱
    4. 无法核验的依据标记为待律师复核，不补造引用

    内置规则

    • 豁免口径只有一种：用户明确要求「只按现有资料，不联网检索」
    • 三类依据必须同时检索：支持、反向、程序/效力陷阱
    • 不补造引用；无法核验的标待律师复核

    产出

    研究底稿（见 research-gate 流程第六步），供专项文书引用

  4. 文档交付（Word/PDF 与复核状态）

    按律师要求的形式交付可直接使用的 Word/PDF，并把人审要求和复核状态放在正确的位置

    请律师核对

    • 核对 4.1只有 high / critical 事项才输出 REVIEW_STATUS，standard 事项不输出——这一界线是否合适
    • 核对 4.2客户成稿正文完全不放人审标记、把要求全部移到《成稿说明》，贵所是否接受这种交付方式

    做法

    1. 用户要求 DOC/DOCX、修订痕迹、批注或版式保留时，调用可用的 Word/Documents 能力
    2. 不覆盖原件；真实 Track Changes 应可接受、可拒绝
    3. 核心事实待核实时，正文确定性须与批注一致
    4. 完成结构检查及渲染/视觉 QA 后再交付，清单见 shared/references/document-delivery-qa.md
    5. high / critical 事项交付前输出 legal-document-intake 规定的 REVIEW_STATUS，独立复核未执行时如实写明
    6. 律师要求「可以直接给客户」或使用律所模板出具的，按客户成稿模式交付：律所口吻、律所模板、正文没有内部标记；写给律师的事项另出《成稿说明》（document-delivery-qa.md 第 5 节；备忘录骨架见 document-structures.md）
    7. 正式成果恒由执业律师复核；客户成稿模式下由《成稿说明》与 REVIEW_STATUS 承载这一要求

    内置规则

    • 不覆盖原件
    • Track Changes 必须是真实修订，可接受可拒绝
    • 正文确定性与批注一致
    • 先结构检查与渲染/视觉 QA，后交付
    • high / critical 事项必须输出 REVIEW_STATUS；复核没做要如实写
    • 客户成稿模式：律所口吻 + 律所模板 + 正文无内部标记 + 另出《成稿说明》

    法律依据

    • 最高人民法院《关于依法审理涉人工智能纠纷案件的意见》（法发〔2026〕10号）第（十九）项 — 拟提交法庭的文书随附《AI 辅助使用情况说明》并逐条核实引用（经 document-delivery-qa.md 第 5.3 节）

    产出

    Word/PDF 交付稿（修订稿或净稿或模板包成稿）；high/critical 事项附 REVIEW_STATUS；客户成稿模式下为客户成稿 + 《成稿说明（致承办律师）》两份文件

  5. 条件性继续（draft_mode: conditional）

    不因每个事实缺口都停下来，在安全的范围内先写附条件的稿，同时不把未核实事实写成无保留结论

    请律师核对

    • 核对 5.1把「经律师转发客户的咨询型备忘录」纳入可条件性继续的范围，依据是一个案例的律师评价（LWC-2026-0007）；贵所是否同意客户成稿也可以先写附条件结论
    • 核对 5.2升级为阻断项的四种情形是否完整——例如拟直接外发给对方当事人的律师函、涉及刑事风险的事项，是否也应阻断

    做法

    1. 判断请求是否属于三类之一：内部审阅稿；实践配置明确默认先供律师内部复核；经律师转发客户的咨询型备忘录（客户成稿）
    2. 判断缺口能否安全处理：内部稿用条件性结论、明确假设、批注和证据清单；客户成稿用来源句（「根据……记载」「截至……尚未向我们提供……」）、条件性结论，并把取得关键文件列为实施前提，待补材料列入《成稿说明》
    3. 确认不会把未核实事实写成无保留结论，且成果交付给律师、由律师决定是否与何时转发
    4. 满足以上条件时使用 draft_mode: conditional；会改变正文的缺口仍按 intake 在起草前提问，只是不必等答复才动笔
    5. 遇到升级情形时，把同一核心缺口升级为阻断项，先向律师确认

    内置规则

    • 允许条件性继续的三类请求：内部审阅稿；实践配置默认先内部复核；经律师转发客户的咨询型备忘录
    • 咨询型备忘录写附条件结论是律师认可的正常写法（LWC-2026-0007）
    • 条件性继续回答的是「要不要停」，不是「要不要问」
    • 升级为阻断项的四种情形：拟提交法院、仲裁机构或监管机关；向第三方出具、供其依赖的法律意见书；用户要求无保留结论；缺口会改变委托问题本身或我方身份

    产出

    带条件性结论、明确假设、批注与证据清单（内部稿）或来源句、实施前提与《成稿说明》待补材料（客户成稿）的稿件

  6. 恢复规则（律师带回答案后继续）

    律师答复到达后从暂停处继续，不重问、不重来

    请律师核对

    • 核对 6.1补充提问只允许最后一轮，复杂事项是否需要放宽
    • 核对 6.2律师中途发来自改稿视为「换底稿」并重跑 intake，是否符合贵所的协作习惯

    做法

    1. 接收答复：微信文字、律师回填的问卷或其文件路径、提问工具的结果
    2. 按题号合并到原事项摘要，列出合并表
    3. 从暂停阶段继续；不得重新询问已解决事项，也不得重新开始整个工作流
    4. 只有新答案产生新的实质分支时，才允许最后一轮补充提问
    5. 律师中途发来自改稿或新材料、改变了底稿或任务的，重新输出一次 INTAKE_DECISION

    内置规则

    • 合并按题号，输出合并表
    • 不重新询问已解决事项；不重新开始整个工作流
    • 补充提问最多一轮，且只在新答案产生新的实质分支时
    • 换底稿或任务变化 → 重新输出 INTAKE_DECISION

    产出

    合并表（题号｜答复要点｜处理）与从暂停处继续的后续成果

08交付前检查

  • 回复中已出现 INTAKE_DECISION 区块，且在第一次实质检索、派出并行检索助手或开始起草之前
  • 已按交付物进入专项流程，没有用通用写作流程代替
  • 实质法律结论形成前已过研究闸门，支持依据、反向依据、程序/效力陷阱都检索了
  • 交付前完成结构检查及渲染/视觉 QA（document-delivery-qa.md）
  • high / critical 事项交付前输出 REVIEW_STATUS，未做独立复核的如实写明
  • 客户成稿正文无内部标记，写给律师的事项全部在《成稿说明》
  • 核心事实待核实时，正文确定性与批注一致

09何时暂停或升级

  • intake_status: clarify：有必须确认项，提问并暂停受影响部分的起草
  • 我方立场无法从材料可靠推断且会改变成果：由动态 intake 询问
  • 同一核心缺口在四种情形下升级为阻断项先向律师确认：拟提交法院、仲裁机构或监管机关；向第三方出具、供其依赖的法律意见书；用户要求无保留结论；缺口会改变委托问题本身或我方身份
  • 律师中途发来自改稿或新材料改变了底稿或任务：重新输出 INTAKE_DECISION
  • 无法核验的依据：标记待律师复核，不补造引用
  • 独立复核未执行：在 REVIEW_STATUS 中如实写明，不得沉默交付
